# FEATURE：桌面聊天回复助手 v1（微信单聊）

- 状态：规划中
- 创建：2026-10-06
- 域语言见 [`CONTEXT.md`](../../CONTEXT.md)
- 决策见 [`docs/adr/`](../../docs/adr/)

---

## Problem Statement

被替代的参考实现（`examples/jev-chat-windows`，Python + PySide6）在产品方向上是
对的：只截自己的窗口、离线 OCR、轻量模型判意图、起草候选、一键填入。

但**使用体验不佳**，根因不在性能，而在三处：

1. **交互层是负担**。候选、开关、会话选择、设置全挤在一个悬浮窗里；调试信息
   要开另一个窗口；「填入」要走一次焦点切换和粘贴，用户要自己再点发送。
2. **适配层是写死的**。气泡颜色规则、消息区像素锚点、OCR 引擎按 App 硬编码，
   换微信版本就可能失效，且失效时不告诉你。
3. **维护层是 Python**。Win32 调用全是裸 ctypes，靠注释维持正确性；
   一次 OCR 250–800ms 被迫拆子进程；打包 146 MB。

这三处让"改一个阈值"变成"重读 2000 行 Python 并重新打包"。

---

## Solution

用 Rust 重写为一个**常驻托盘、贴着聊天窗口工作的副驾**：

- **纯 Rust 核心**：窗口捕获、帧调理、OCR、意图推理、输入注入，全部在 webview
  之外，Tauri 只做壳。
- **Tauri 2 + Svelte 5 前端**：交互重做——候选卡片、档位切换、调试画布
  都是一等公民。
- **帧调理作为独立管线**：把"送多少像素"变成可以用 token 直接算的显式决策，
  而不是隐含在 OCR 参数里的模糊开关。
- **所有判定可解释**：每一个被丢弃的像素区域都能说出是哪一级、依据什么丢的。

## User Stories

### 采集与窗口管理

1. 作为用户，我希望程序自动找到我正在用的微信窗口，而不用我去配置 HWND，
   这样换一次电脑、重启一次都不用重设。
2. 作为用户，我希望按**进程名 + 窗口标题规则**挑主窗口，而不是按面积挑最大的，
   因为微信同进程还有工具窗和看图窗，面积可能更大。
3. 作为用户，我希望在微信被其他窗口盖住时仍然能读到对话，
   因为我经常一边聊天一边干别的。
4. 作为用户，我希望最小化的聊天窗口能以"看着像收起来了"的方式继续被读取，
   而不是被强行弹到前台。
5. 作为用户，我希望窗口被拖动/缩放后不用重启程序就能重新认准消息区。
6. 作为用户，我希望在混合 DPI 的多显示器环境下坐标不跑偏。
7. 作为用户，我希望微信窗口关闭时程序不崩溃、不刷错误，而是安静地等下一个窗口。

### 帧调理（降噪 / 成本控制）

8. 作为用户，我希望静止的聊天窗口**一次模型和 OCR 都不调**，这样不聊天的时候
   零 token、零耗电。
9. 作为用户，我希望只识别新出现的部分，而不是每次把整个聊天区重读一遍。
10. 作为用户，我希望即使聊天区里有一堆表情包、引用块、时间戳，也不会被当成
    对方说的话。
11. 作为用户，我希望对方的头像、表情包、图片里的文字不会混进对话上下文。
12. 作为我，我要能把"识别精度 / 成本"调高一档，因为重要对话我愿意多花 token，
    闲聊时我愿意省。
13. 作为我，我要在调试视图里看到"这一帧到底有多少像素被送去识别、花了多少视觉
    token"，因为不然我没法判断该调哪一档。
14. 作为我，我要看到每个被丢弃的区域是因为什么被丢的，因为认错了要一眼看出
    是哪一步的锅。

### 感知与消息提取

15. 作为用户，我希望程序能分清哪句是我说的、哪句是对方说的。
16. 作为用户，我希望程序能读出**会话名**，并且自动跟着当前会话切换。
17. 作为用户，我希望 OCR 抖一下（「小分队」↔「小分认」）不会把我切成两个会话。
18. 作为用户，我希望滚动聊天时翻出来的旧消息不会被当成新消息重复上报。
19. 作为用户，我希望切走再切回来不会把已经看过的消息重新当成新消息。
20. 作为用户，我希望同一个气泡里的多行文字能合并成一条消息，而不是拆成三条。
21. 作为用户，我希望程序认不出会话名时不要把消息全丢掉，
    至少沿用上一次的会话身份。

### 上下文管理

22. 作为用户，我希望模型看到的是**连续的对话**，而不是孤立的最后一句。
23. 作为用户，我希望能控制给模型看最近多少条消息，因为长对话和短对话需要
    不同的上下文长度。
24. 作为用户，我希望历史太长时能自动摘要，而不是硬截断导致语境丢失。
25. 作为用户，我希望摘要**不消耗额外调用**，因为它本身也是一次模型调用，
    会让"静默期零调用"这条承诺破掉。
26. 作为用户，我希望我自己的说话风格能被学到，
    因为回得像我自己比回得"完美"更重要。
27. 作为用户，我希望对方发来的**图片**能被描述出来，
    因为"对方发了张图"是我需要回复的重要信息。

### 意图识别与回复生成

28. 作为用户，我希望有一条很快的路径先判断对方意图，
    因为起草不该在读错意图的情况下瞎写。
29. 作为用户，我希望判断结果是**可读的**，而不是一个黑盒标签。
30. 作为用户，我希望看到至少三条候选，因为我不一定想要模型的第一选择。
31. 作为用户，我希望候选是**按概率排序**的，并且推荐那条排在最上面。
32. 作为用户，我希望三条候选是"同一个我、在三种心情下随手写的"，
    而不是"温暖版/负责版/行动版"这种明显的凑数结构。
33. 作为用户，我希望候选里允许只有几个字，因为真实聊天就是这么回的。
34. 作为用户，我希望选择纯文本模型时，也能让它知道对方发了张图，
    因为我不想被模型能力绑架。
35. 作为用户，我希望切换模型供应商时只需要填一把新 key，
    而不是重配整个应用。
36. 作为用户，我希望判断那一步挂了时仍然能拿到候选，
    因为我不想因为一个判断服务限流就完全用不了。

### 投递与发送

37. 作为用户，我希望能一键把候选填进输入框，并且**停在那里**，
    因为发不发是我决定。
38. 作为用户，我希望连续填入多条候选时内容总是追加在最后，不会串行错乱。
39. 作为用户，我希望在明确确认之后，可以让程序把消息发出去，
    因为有些对话我已经想清楚了，只是不想手动点。
40. 作为用户，我希望**唯一会把话发出去的那一档**在界面上一直写清它是什么、
    升上去时有一次警示闪，因为这是最容易出不可挽回后果的地方。
    ⚠ 2026-10-14 改写。这一条原先写的是「我希望**自动发送档位**每条都可见、
    可随时打断」——它描述的 `Auto` 档（填入即发、不打断）已于 2026-10-13
    **整档取消**（`docs/设计规范.md` §10 第 3b 条）。**照原文去做会把第三档
    长回来。** 关心的事没变（发出去那一档必须显眼），载体换成了现在
    唯一会发出去的 `Confirm`：切上去时闪一次，设置页里那行说明常驻可见。
41. 作为用户，我希望任何时候切回只填入的档位都是一步操作，
    并且会话结束会自动回落到最低档。
42. 作为用户，我希望投递失败能重试，并且重试有退避，不要疯狂点。
43. 作为用户，我希望程序**绝不重放一条可能已经发出的消息**，
    因为重发一条已经发出去的聊天是无法撤销的。
44. 作为用户，我希望注入输入时不移动我的鼠标指针，
    因为我可能正在用同一个屏幕干别的事。
45. 作为用户，我希望输入框被别的窗口盖住时，程序能自己解决焦点问题，
    因为 SetForegroundWindow 在普通后台进程里经常被系统拒绝。

### 安全与边界

46. 作为用户，我希望 API key 不出现在任何文件里，也不出现在日志里。
47. 作为用户，我希望程序对转账、红包、收款相关的界面元素**完全不碰**。
48. 作为用户，我希望这些话题在起草时被明确禁止，而不是靠模型自觉。
49. 作为用户，我希望抓到的截图不落盘、不进日志、不上传。
50. 作为用户，我希望有一个显式的调试命令可以把一帧写到磁盘，
    因为排查时我需要看像素，但我要知道这件事发生了。
51. 作为用户，我希望在 `Auto` 档位下程序误判了说话人时能立刻看见，
    因为把对方的话当成我说的发出去是最糟的失败。

### 界面

52. 作为用户，我希望有一个贴在聊天窗口旁边、可拖可缩、永远置顶的小面板，
    因为它不该挡住我工作。
53. 作为用户，我希望面板窄的时候自动进入紧凑模式，而不是把文字挤成两行。
54. 作为用户，我希望看到当前识别到的对话记录，
    因为 OCR 认错了我要能立刻发现。
55. 作为用户，我希望调试视图画出色框（我 / 对方 / 被过滤 / 发言人名 / 图片丢掉），
    因为认错了要一眼定位。
56. 作为用户，我希望设置改动即时生效，不用重启。
57. 作为用户，我希望模型 key 输入框在已配置时留空等于保留，
    因为我不想每次改别的设置都要重新粘一遍 key。

## Implementation Decisions

### 模块边界

六个阶段，每阶段只依赖上游的输出结构：

```
capture → condition → perceive → context → reason → present/act
```

- `capture`：不认识聊天软件，只认识 HWND 和窗口帧
- `condition`：不发网络请求，不认识"消息"
- `perceive`：不发网络请求
- `context`：**唯一**允许出网做模型调用的阶段，且只被 `Novelty` 为真的新消息触发
- `present` / `act`：不出网

### 帧调理管线的五级（见 ADR-0002）

按杠杆从大到小排序：

1. **变化门控** — 只比较 `ChatPane` 区域，排除会自己动的元素（置顶公告会滚动，
   算进 diff 会导致画面永远停不稳）
2. **增量 ROI** — 维护"已提交水位线"，新消息永远从底部出现
3. **语义遮罩** — 按底色众数占比、对底色对比度、字号比剔除头像/表情包/
   图片文字/时间戳/引用块/发言人名/链接卡片/置顶公告/系统提示
4. **尺度归一** — 按 DPI 归一到逻辑布局，再按 token 预算缩放；
   大图缩到预算内，小图不盲目放大
5. **轻度几何规整** — 贴边裁剪、背景合成纯色、按需灰度化

**明确不做**：高斯/双边模糊、二值化、锐化后再放大、去色/直方图均衡、
形态学开闭做文本行分割。这些在传统图像预处理里常见，但对神经 OCR/VLM
是负收益或零收益。前提是"下游是神经网络模型"；换下游要重评。

### token 预算模型

视觉 token 数与图像**面积**成正比、对**边长**二次。
以 Qwen2-VL 为例（**只作成本公式的样本，不代表本项目选它**）：
14×14 patch + 2×2 merger，一个 visual token 覆盖 28×28 像素，
于是 1024×1024 = 1369 token，512×512 = 361 token。宽度给两倍 → token 花四倍。

不同厂商的分块尺寸不同，但"成本随面积线性增长"这条通性不变。
所以本项目把预算抽象成**模型无关的「视觉 token 数」**，接具体模型时才换算成
它家的参数名（有的叫 `max_pixels`，有的给分块上限，有的直接限制图片张数/尺寸）。

「识别精度/成本」滑块底层就是这个数字，可以直接换算成钱，
设计里必须把它显示出来，而不是藏成"质量：高/中/低"。

### 推理链路

三段式：**判断 → 带着判断起草 → 排序**。

- 判断失败 → 退回"盲起草 + 一次合问"，行为不变但仍可用
- 排序失败 → 按第一条推荐，判断摘要照常显示
- 起草返回空候选 → 报错，**不**退化成 `IndexError`

### 模型清单：默认 2 个模型

整个系统**只有两个模型角色**，读聊天内容不占模型位：

| 角色 | 是什么 | 干什么 |
| --- | --- | --- |
| **A · 意图识别决策模型** | jev 类轻量决策模型 | 答 7 道判断题 + 给候选排序。要快、要便宜 |
| **B · 回复生成模型** | 默认多模态 | 生成候选回复；自身多模态时也能读图 |

**读聊天内容不用模型。** 那条链路是 `Windows.Media.Ocr`，纯离线、零 token。
气泡文字无论在哪种配置下都走 OCR——**配了视觉模型也一样**。

所以**只有 2 个模型**。按三段式链路，每条新对方消息触发：

- 2 次调用打给模型 A（判断 1 次 + 排序 1 次）
- 1 次调用打给模型 B（起草 1 次）
- 0 次视觉调用

降级路径会减少而不是增加调用数：判断挂了走"盲起草 + 一次合问"，
仍是 A×1 + B×1。

### 视觉是 B 的配置项，不是第三条平级链路

```
模型 B 具备视觉能力
  └─ 图片消息随文本一起进 B。VisionBridge 不存在、不出现、不参与。

模型 B 是纯文本 LLM
  ├─ 开启 VisionBridge：对方发的【图片消息那一小段区域】→ 视觉模型 → 描述 → 进 B
  │   此时确实多一个模型，但它是用户显式配置的，不是系统常驻的。
  └─ 未开启：图片消息降级为占位描述「对方发来一张图片」，链路不断。
```

VisionBridge **默认关闭**，且仅在 B 无视觉能力时才出现在设置界面里。

它的输入**永远只是对方发的图片消息那一小段 `Bubble`**，
绝不是整个聊天窗口，也不是气泡文字。

### 上下文裁剪与摘要

- 默认取最近 N 条（用户可调）
- 超出预算时**惰性摘要**：只在有触发事件（对方来了新消息）时才摘要一次，
  摘要结果缓存。**不在静默期做任何调用**——这条是硬约束。
- 自己的口吻样本单独一路：最近若干条短消息原样喂给起草

### 投递两档

| 档 | 行为 | 进入方式 |
| --- | --- | --- |
| `Manual` | 只填入，停在光标处 | 默认；会话结束自动回落 |
| `Confirm` | 填入后二次确认才发送 | 候选卡片上显式选择 |

⚠ 2026-10-13 取消第三档 `Auto`（填入即发送）。取消它顺带删掉了
「`Auto` 是『不打断』的承诺」这条产品承诺，以及它独占的
`Next::NeedsConfirmation`（失败时停下来问人，而不是自己降档重试）。
决定见 `docs/设计规范.md` §10 第 3b 条，票 20。

`DeliveryReceipt` 不是布尔值，是状态机：
`NotSent` / `Sent` / `PossiblySent` / `Failed(reason)` / `TimedOut`。

**`PossiblySent` 禁止自动重放**——这是整个系统最重要的单条安全不变量。
`TimedOut` 结果未知，按 `PossiblySent` 对待。

注入策略：剪贴板 + 定位输入框 + 粘贴，**不移动真实鼠标**。
焦点被拒时走 AttachThreadInput 路径，并在失败时如实上报而不是假装成功。

### 前端

- `ui/` 是 Svelte 5 + Vite，前端拿不到 API key，也不需要知道模型路由
- 所有网络调用在 Rust 侧
- 后台走 `invoke` / `emit`，不轮询
- 写任何 `.svelte` / `.svelte.ts` 前用 `npx -y @sveltejs/mcp svelte-autofixer` 迭代到零告警

### Tauri 窗口的已知坑（必须在实现时处理）

- 懒加载窗口写成 `visible: true` + 停在 `x: -10000`，不能写 `visible: false`
  （WebView2 只在首次被 DWM 合成时注册 drop target）
- `dragDropEnabled` 只在 `tauri.conf.json` 声明才生效，设到 Rust builder 会被静默忽略
- `decorations: false` 时圆角要自己调 `DwmSetWindowAttribute`
- Acrylic/Mica 在 `hide()` → `show()` 后会丢失，需重新 apply

## Testing Decisions

### 什么算好测试

只测**外部可观察行为**。不测内部函数、不测私有字段、不为了可测性把逻辑拆碎。

### 三个接缝

**① 管线接缝** — 录制的真实 `Frame` 夹具 → `Message[]`

- 中间全部真跑：锚定、调理、OCR、归类、去重。不 mock 任何东西。
- 只换帧来源。
- 夹具来自 `xtask probe` 的产出，第一天用来肉眼核对，之后冻结。
- 需要覆盖：深色/浅色主题、125%/150% DPI、有表情包、有引用块、有图片消息、
  滚动到中途、切会话。

**② 推理接缝** — `Message[]` + 配置 → `DraftSet`

- 只换模型传输。假传输返回预置的 intent / draft / rank JSON。
- 测的是：上下文裁剪与摘要的边界、三段式的降级路径（判断失败 / 排序失败 /
  起草空）、候选清洗、语音桥接的拼装。
- 不测"回复好不好"——那是模型的事，不是代码的事。

**③ 投递接缝** — 派发策略 + 上次回执 → 下一步动作

- 纯函数，不碰 Win32。
- 必须单独锁住的不变量：
  - `PossiblySent` 之后**永不**重放
  - `TimedOut` 按 `PossiblySent` 对待
  - 会话结束一定回落到 `Manual`
  - 任何档位下「可能已发送」都**不**自动重放（这条取代了原
    「`Auto` 失败时不自动降级重试」——`Auto` 取消后没有降档可做）
  - 档位集合恰好两档（`the_tier_set_is_exactly_two_and_named`）
  - 重试有退避上限

### 端到端（真跑，开发机上，不进 CI）

治的是接缝测试治不了的集成性故障。断言全部是行为性的：

- 帧非黑、尺寸符合窗口、缓冲区是合法 BGRA
- `PaneAnchor` 解出来且矩形在窗口内、高度超过下限
- OCR 返回 ≥ N 行，且至少 1 条 `Attribution` 为 `Them`
- 完整推理在超时内返回 ≥ 1 条候选
- **投递后回读验证**：剪贴板内容与候选原文字节级相等

最后一条是真正的判据。**投递函数的返回值不算证据，只有回读算。**

### 先有探针，后有夹具

工程上第一个 ticket 是探针，不是测试。理由：WGC 能否在目标机器上抓到
GPU 合成的微信窗口、`Windows.Media.Ocr` 是否装了对应语言包、
气泡颜色规则在当前微信版本上是否成立——这三个未知**任何单元测试都回答不了**。

探针的产出同时就是接缝 ① 的夹具来源。同一批帧，两种用途。

## Out of Scope

- **群聊**。发言人归属、"回复给谁"、@ 前缀全部推迟。v1 只做单聊。
- **多平台**。v1 只有 Windows。代码里预留 `ChatSurface` 抽象，但不为 macOS/Linux
  写实现——没实测过的平台适配是负债不是资产。
- **第二个聊天软件**。Telegram / WhatsApp / KakaoTalk 都不在 v1。
- **模型托管/代理服务**。本项目不自建服务器，出网只到用户自己配置的供应商。
- **更新检查**。参考项目有的 GitHub 版本轮询，v1 不做。
- **把回复自动发出去且不通知用户**。`Auto` 档必须每条可见可打断。
- **多模态模型的本地部署**。视觉一律走 API 或本地 OCR，不在 Rust 侧跑 VLM 推理。
- **把微信窗口的 UIA 树接进来**。参考项目已实测该窗口 UIA 树只有 2 个节点、
  无控件树，Accessibility 路线在微信上已被证伪。本产品只对**新接入的、UIA 可达的**
  App 保留语义优先的余地；微信走纯像素路线。
- **训练或微调任何模型**。

## Further Notes

- **隐私表述要与代码一致。** 硬约束里"截图不落盘"有一条显式例外
  （`xtask probe` 写 `target/probe/`），使用这个命令时必须提示用户。
  任何文档、日志、错误文本都不得把 key 或聊天内容带出去。
- **参考项目是可以读的结论来源，不是代码来源。**
  `examples/jev-chat-windows/app/ocr.py` 里的颜色规则和
  `app/capture.py` 里的像素锚点是**实测过的**，值得继承假设再在 Rust 里重新标定；
  但 `app/fill.py` 的裸 ctypes 和 `overlay.py` 的 58 KB 事件循环处理不要移植。
- **`.agent/skills/` 的三份 ComputerUse 资料**在写捕获、窗口查找、输入注入之前
  必须读。三份资料的共同结论是：语义动作优先、视觉像素兜底、
  `action_sent` 之后禁止盲目重放——最后一条和我们的 `PossiblySent`
  是同一条原则的两种说法。
- **第一个可交付物不是能用的程序，是三个实测结论。**
  在拿到「WGC 能抓」「OCR 认得出中文」「气泡规则成立」这三个答案之前，
  后面所有架构都只是纸面推演。
