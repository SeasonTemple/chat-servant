# 09: 输入注入与回读验证——以回读为唯一判据

**What to build:** 把选中的候选送进微信输入框，并且**停在那里**。
同时提供"确认后发送"这一档。

真正的验收标准不是注入函数的返回值，而是**回读**：注入后读回剪贴板内容，
与候选原文**字节级相等**。投递函数返回成功而没有回读，等于没有证据。

注入要移动真实鼠标的问题也在这条里解决：优先不移动鼠标的路径，
焦点被系统拒绝时走备用路径，并在失败时如实上报。

## 实机验证（`cargo run -p xtask -- inject-probe`）

6 类样本逐字节往返相等：ASCII 15B / 中日文 53B / 换行制表 29B /
emoji 代理对 30B / 空串 0B / 长文本 **150000B**。指针纹丝未动。

## 回执的诚实分级

最高只给到 `PossiblySent`，**给不了 `Sent`**——「输入框里出现了这段文本」
这种真正的送达证据需要 OCR 输入框区域，那是 ticket 16 的调试窗口。
`Sent` 会让上层认为不需要回读，所以宁可保守。

`Confirm` 档点「确认发送」时**不注入**，只回「已准备好，等你再点一次」。

## 单元测试抓到的真 bug：堆损坏

`cargo test` 报 `STATUS_HEAP_CORRUPTION`。根因：**剪贴板是进程全局资源**，
而 Rust 测试默认并行跑。两个线程各自 `EmptyClipboard` + `SetClipboardData`，
线程 B 的清空会让系统释放线程 A 刚交出去、还在读的内存块。

这不只是测试问题——dispatch 可以从 UI 点击、快捷键、定时器三处同时触发。
加了进程级 `Mutex`，锁中毒不算致命（剪贴板状态还在，继续用比进程崩掉好）。

**并行测试抓到了串行跑抓不到的 bug。**

## 不移动鼠标

`SetForegroundWindow` + `Ctrl+V`，不用鼠标点输入框。
焦点被拒时用 `AttachThreadInput` 挂到目标输入队列再试（系统提供的正规机制），
仍然失败就**报失败**——动鼠标是「偷偷替用户做了他没要求的事」，宁可失败。

## 三个 Win32 签名的坑（查源码确认，不是靠报错反推）

- `GlobalFree` 在 `Win32::Foundation`，不在 `System::Memory`
- `AttachThreadInput` 在 `System::Threading`，不在 `UI::Input`
- `HANDLE` 与 `HGLOBAL` 是**两个不同的 newtype**（底层都是 `*mut c_void`），
  剪贴板 API 在两者间来回传
