# 16: 端到端——抓到、读懂、填入、回读验证

**What to build:** 一条命令走完整条真链：微信窗口开着 → 抓到帧 → 调理 → OCR →
判断 → 起草 → 填入输入框 → **回读验证**。

这是整条链路的验收，也是唯一一个能同时证明六个阶段都成立的证据。

它在开发机上真跑，需要微信窗口开着和真实的模型 key，**不进 CI**。
它治的是接缝测试治不了的集成性故障：WGC 在这台机器上的实际行为、
webview 窗口层的问题、上游模型 API 契约的变化。

断言全部是行为性的，不写"回复质量好"。

      单点早先由 `xtask inject-probe` 覆盖（6 类样本逐字节往返相等，鼠标指针不动），
      但那只证明了剪贴板，**没证明粘贴发生**。全链这次补上的是**真的证据**：
      注入后**再抓一帧 OCR 输入框那块像素**。实机：

      ```
      剪贴板   与注入内容字节级相等（51 字节，没被别的程序换走）
      输入框   像素回读：「看起来尔分享了一一拄度进屣如何0」
      ```

      OCR 认错了好几个字（你→尔、一些→一一、追→拄、进展→进屣），
      所以判据是**字符重合率**而非字节相等。肉眼复核输入框里确实是
      `看起来你分享了一些进度，进展如何？`，**没有发出去**。

      ⚠ 途中挖出一个真 bug：`send_keys([VK_CONTROL, VK_V])` 对每个键各发
      「按下+抬起」，实际序列是 `Ctrl↓ Ctrl↑ V↓ V↑`——**Ctrl 在 V 之前就松开了，
      粘贴从未发生过**，微信输入框里敲进去的是一个字母 `v`。
      `inject-probe` 只验剪贴板往返、没碰按键序列，所以一路绿灯。
      已修成和弦顺序，并加了一条钉住事件顺序的回归测试。

## 两个刻意的设计

**dry-run 不许假装注入过。** 早期版本 dry-run 也打印「回读字节级相等」，
而它根本没注入——那是在**说谎**。现在 `ChainOutput` 带
`injected_and_read_back: false`，报告明说「没跑」。

**段位清单只点亮走过的段。** 全亮的清单在 dry-run 下同样是骗人的。

## 预置传输必须自曝

真实 HTTP 传输还没接，所以 `PresetReasoner` 返回的候选**带
「【预置候选，未接真实模型】」字样**。全链因此**必然失败**——
不能让用户以为模型接通了。前四段（抓帧/锚定/OCR/归类）不依赖模型，是真跑的。
