# 18: 切换微信会话后，面板内容不更新

**Status:** ready-for-agent —— 根因已从源码定位并修掉一处，**但症状未在实机复现过**

⚠ **本票从另一台设备的快照并入（`docs/HANDOFF.md` §11.6）。
2026-10-10 用户实机报出，2026-10-11 本机复跑时微信会话状态不同，没有复现。**
下面写的是**代码分析结论**，不是复现结论。别当成已验。

## 一、复现前先分清

这是「**面板停在旧内容**」，还是「**面板清空了**」？
**两者的根因完全不同**，先分清再动手。这条不确认清楚，
后面四条方向全是猜。

## 二、2026-10-11 从源码读出的结论

### 观察循环是活的（排除方向 1）

`step()` 第一件事是 `load_frame(&s.source, &mut s.last_hwnd)`，
它按 **HWND** 取帧，而切换会话**不换 HWND**——同一个微信主窗口，
内容变了而已。循环既不靠句柄变化驱动，也没有一次性捕获，
所以「切会话触发不了新一轮」不成立。

### 去重也没吃掉（排除方向 2）

闸关着那一支在 `watch.rs` 里**直接 `return`**，压根没走到推进水位线的代码，
而 `PaneWatcher` 的增量 ROI 是在函数更前面的 `watcher.observe(&full)`
里算的。切会话让画面大变 → ROI 覆盖新内容 → `Decision::Read` →
一路走到闸，**不会被判成「跟上一帧一样」丢掉**。

### 真正的问题：闸管住了推理，没管住消息累积

身份闸在 `step` 里的位置**原来排在消息累积之后**：

```rust
// ① 先把本轮读到的消息累积给面板
s.messages = merge_into_stream(&s.messages, &messages);   // ← 原来在这

// ② 然后才判身份闸
let peer_ok = match (&s.locked_print, &print) { … };
if !peer_ok {
    s.candidates.clear();     // 候选清了
    s.reason = "……本轮不动手";
    // ⚠ 但 s.messages 没清
    return Ok(...);
}
```

于是用户在微信里切到会话 B 时，**B 的消息先被并进了 A 的消息流**，
闸才关。闸挡住的是推理与投递，**消息累积已经发生了**。

雪上加霜的是 `s.peer` 每轮都在更新（它在闸之前跑），所以面板此时的状态是：

> 标题写着 **B** 的会话名 · 下面挂着 **A 的历史夹着 B 的新消息** · 一句「本轮不动手」

这正是 `watch.rs` 里那段注释原本要防的
「看起来在处理 A，其实已经在看 B」——**注释写了，代码没做到**。

### 为什么这可能就是「内容不更新」

⚠ **以下是推测，没有实机证据。** 两种可能的表现：

1. 用户盯着消息列表，切会话后列表**混进了 B 的新消息**而不是「停在旧内容」
   ——但那些 B 的消息往往落在水印线以下、或与 A 的旧消息在同一行区间，
   `merge_into_stream` 的唯一化/窗口裁剪可能让它们看不出来，于是用户描述成
   「不动」。
2. 另一台设备上 `merge_into_stream` 的行为与我这边读到的不同，
   于是确实一个字都没变。

**分清的办法只有一个：实机切一次会话，看消息列表是「混了 B 的」还是「没动」。**
下面第三项验收就是它。

### 没有变成隐私事故

闸在推理之前就 return 了，`history` 也只在闸开的那一支追加，
`collect_images` 同样在闸之后。所以**另一个会话的内容没有出网**，
这只是一处**界面诚实性**缺陷，不是硬约束第 1 条的破口。

## 三、已改（2026-10-11）

1. **把消息累积挪到身份闸之后**（`watch.rs` 的 `step`）。
   闸关着的那一轮，别的会话的消息不再进消息流。
   切回锁定会话时水位线没推进过，整块消息区会重读，消息自然长回来，不需要补偿逻辑。
2. **`apply_gate_closed()` 抽出成独立函数**，并在「指纹确实不同」那一支
   **清掉 `s.messages`**。理由：`s.peer` 已经跟着窗口更新成新名字了，
   这时候下面还挂着锁定会话的历史，读起来就是「这是新会话的对话」——
   而它不是。
3. **「认不出头部」那一支不清**。认不出不等于换了会话（标题栏被裁掉、
   动画没画完都会短暂认不到），此时清空会让消息列表闪一下。
4. 三条回归测试（40 passed）：
   `closing_the_gate_on_a_different_conversation_drops_the_messages` /
   `a_gate_that_stays_closed_only_pushes_one_readout` /
   `losing_the_header_is_not_a_conversation_change`

## 五、已知缺口（老实说）

**§三 的第 1 条（顺序）没有任何自动化测试守着。**
`step` 需要真帧、真 OCR、真 Reasoner 才跑得起来，
而本仓库没有「读自己的源码做结构断言」这种测试（`include_str!` 全仓 0 处）。
所以那处顺序只有一行注释在解释它为什么重要。
**将来谁把 `merge_into_stream` 挪回闸前面，不会有任何测试变红。**
要么补一条感知层的 golden，要么接受这个缺口——别假装有覆盖。

## 六、方向 3 的后续（没做，但值得看一眼）

闸锁的是**头部像素指纹**，不是会话标识。指纹的相似度阈值
（`perceive::identity::SAME_THRESHOLD`）**在 `identity.rs` 里明确写着
「未实测到会话切换时的真实分布」**。也就是说「A 和 B 被判成不是同一个」
这件事本身也只在合成测试里验过（`a_different_name_prints_differently`
用的是两块纯色图）。真实微信头部带未读角标、时间戳、在线状态，
**没测过**。如果实机切会话后闸压根没关、或者乱关，根因在这里，不在上面。
