# 18: 切换微信会话后，面板内容不更新

**Status:** 已修 —— 2026-10-11 实机复现、定位、修复、复验通过

⚠ **本票从另一台设备的快照并入（`docs/HANDOFF.md` §11.6）。
2026-10-10 用户实机报出，2026-10-11 本机复现了，而且比报出来的严重得多。**

## 一、复现（2026-10-11）

在「古文山」和「文件传输助手」之间切了一次会话：

```text
切之前  emit readout tick=…  peer="古文山"      messages=8  candidates=3
切之后  emit readout tick=…  peer="文件传输助手" messages=12 candidates=3
```

面板截图：标题变成「文件传输助手」，`对方 4 · 我 8`，
底下还是**在等文件传输助手的新消息**。

**闸一次都没关。程序在给一个用户从未锁定的会话起草回复。**
这是硬约束第 1 条（「只对锁定会话动手」）被实测突破。

## 二、根因：指纹的量化太粗，测试又只测了亮度差

`identity.rs` 的指纹是「每通道压到 2 bit → 64 桶颜色直方图」。
拿真实帧逐块量下来（探针在 `target/probe/idmeasure*.ps1`）：

```text
区域 x308..708 y31..71（现状用的那块，16000 px）
  最大桶占比 = 98.8%          ← 几乎所有颜色塌进同一个桶
  直方图相似度 = 0.982        ← 阈值 0.90，永远判「同一个」
```

`rgb(17,17,17)`、`rgb(34,34,51)`、`rgb(51,51,51)` 在每通道 2 bit 下
**全落进第 0 号桶**——微信深色界面九成的像素挤在一个桶里，
会话名那 189 个亮像素（1.2%）根本推不动它。

**而旧测试一直是绿的**：`a_different_name_prints_differently` 用的是
`tint 225` 对 `tint 120`——**亮度差 105 级**。
真实会话名之间亮度**完全一样**（都是白字），差的是**字形**。
那条测试一直在证明一件与真实情况无关的事。

## 三、修法（`crates/perceive/src/identity.rs`）

改成**二值墨迹掩码 + Sørensen–Dice**：

- 背景取本区域的**众数亮度**，与它差过 60 的像素算「墨」。
  取众数而不是写死阈值，是为了深色主题（亮字暗底）与浅色主题（暗字亮底）都能用。
- 比对时**只放宽「命中」一侧**（±1 px 内有墨就算命中），分母仍是各自的真实墨迹数。
  ⚠ 不先膨胀：膨胀会把两个**不同**名字的重叠也拉起来（实测 0.2793 → 0.5483 → 0.6354），
  那是往危险方向走；只放宽命中这一侧就没有这个问题。
- 一片纯底色**返回 `None`**（认不出），不给空指纹——空指纹会让「认不出」
  读成「换了人」，闸会莫名其妙一直关着。

实测（真实微信帧，同一对）：

| 量 | 同一会话 | 不同会话 |
|---|---|---|
| 旧：64 桶直方图 | — | **0.982**（判成同一个，闸失效） |
| 新：墨迹 Dice | **1.0000** | **0.2793** |

阈值仍是 0.90，落在 0.28 与 1.00 之间，两侧余量都宽。

## 四、复验（2026-10-11 实机，同一对会话）

```text
切到 文件传输助手 → emit readout tick=96  peer="文件传输助手" messages=0 candidates=0
切回 古文山→ emit readout tick=114 peer="古文山"      messages=6 candidates=0
```

面板行为：

- 切走时：`对方 0 · 我 0`，正文**「不认这个人，就不动手」**，
  副标题是 Rust 推来的原因，下面是**「锁定当前会话」**按钮
- 切回后：闸自动开，消息重读回来，回到正常的「在等古文山的新消息」

⚠ **第三点是一并修的**：闸关着的时候界面原来一个字都不说
（`reason` 写着「本轮不动手」，而前端理由栏只放行含
「失败/错误/抓不到/收不到/异常」的条目）。
硬约束第 1 条要求这道闸是**看得见**的。现在 `Readout` 多了显式的
`gate_open` 字段，前端据此显示那一屏——**不靠中文串匹配**。

## 五、一个观察，没定位（不猜）

切回古文山之后消息数是 `对方 0 · 我 6`，而切走之前是 `对方 1 · 我 7`。
闸重新打开时水位线是退过的，整块消息区会重读一遍——
**少读一条**可能是重读范围的差异，也可能不是。
本轮没追，也没有把它写成已知根因。

## 六、方法论：合成夹具会骗人

这一轮里**四处测试夹具**都在骗人，而且都是同一个骗法：
用**亮度差**造「另一个会话」。

```rust
header(225) vs header(120)          // identity.rs
frame_with(225) vs frame_with(120)  // watch.rs × 3
```

真实名字亮度一样、差的是字形，所以这些测试全绿而闸从来没关过。
**教训：造「另一个会话」的夹具，差别必须在字形/位置上，不许在亮度上。**
现在统一用 `named(tint, style)`：三个 style 的亮度完全一样，只改笔画落点。

## 附录：这一轮**之前**排除过的方向（仍然有效）

### 观察循环是活的（排除方向 1）

`step()` 第一件事是 `load_frame(&s.source, &mut s.last_hwnd)`，它按 **HWND** 取帧，
而切换会话**不换 HWND**——同一个微信主窗口，内容变了而已。
循环既不靠句柄变化驱动，也没有一次性捕获，所以「切会话触发不了新一轮」不成立。

### 去重也没吃掉（排除方向 2）

闸关着那一支在 `watch.rs` 里**直接 `return`**，压根没走到推进水位线的代码，
而增量 ROI 是在更前面的 `watcher.observe(&full)` 里算的。切会话让画面大变
→ ROI 覆盖新内容 → `Decision::Read` → 一路走到闸，
**不会被判成「跟上一帧一样」丢掉**。

### 还有一个已修但当时没被实测证实的缺陷：闸管住了推理，没管住消息累积

`step` 里 `merge_into_stream` 原来排在身份闸**前面**，于是切到会话 B 时
B 的消息先被并进 A 的消息流，闸才关。这条在 22e1fb2 里已修
（累积挪到闸之后 + 抽出 `apply_gate_closed()` 清消息）。
这一轮的实测把它**顺带证实了**：切走时 `messages=0`——
要是累积还在闸前面，这里会是 12 而不是 0。

### 已知缺口（仍然没补）

**`step` 里「累积必须在闸之后」这个顺序没有任何自动化测试守着。**
`step` 需要真帧、真 OCR、真 Reasoner 才跑得起来，而本仓库没有
「读自己的源码做结构断言」这种测试（`include_str!` 全仓 0 处）。
谁把 `merge_into_stream` 挪回闸前面，不会有任何测试变红。

⚠ **2026-10-12 补的 golden 用例没有覆盖这一条**，它调的是
`park_on_other_conversation()`，不经过 `step`。它覆盖的是
「帧 → 指纹 → 闸」这半条链和闸在帧序里的开关时机；
「累积排在闸后面」仍然只有实机证据（§四 切走时 `messages=0`）。
这个缺口还在。
