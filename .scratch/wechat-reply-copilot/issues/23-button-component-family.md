## forced-colors 实测：测到一半，边界要说清楚（2026-10-14）

**做法**：把 `@media (forced-colors: active)` 临时改成
`(forced-colors: active), (min-width: 0px)`（第二条恒真），无头 Chrome 出图，
量完回退。**探针已回退，`app.css` 与 HEAD 逐字一致**（`git diff` 空）。

### 量到了什么

| | 结果 |
|---|---|
| token 替换生效 | ✅ `--cs-paper` `#EDF0F1` → `#FFFFFF`，**2068 / 3952** 采样像素变了 |
| 顺带发现 | `#EDF0F1` 与 `Canvas` 白**肉眼几乎分不出来**——所谓「冷灰配置底」的视觉区分度比想象中小得多 |
| 药丸（墨底）在探针态下 | **仍是 `#000000`，没变** |

### ⛔ 测不到的那一半（这条别当已验）

**像素没变，恰恰说明探针只测到了一半。**
它触发的是**本项目自己那段媒体查询里的 token 替换**，
而 forced-colors 真正的机制是**浏览器在绘制层接管作者的 `background-color`**
——这要求真的进入 `forced-colors: active` 媒体特性，
无头 Chrome **不会因为一条 CSS 媒体查询恒真就进入**。

⇒ 所以「药丸在高对比度下会不会整个消失」**是规范推理，不是实测**。
本轮**没有**验证过绘制层接管。验收项里那一条仍然留着。

### 因此做的改动（是保险，不是修复）

`SegSlider` 的选中态原本只有两条通道：药丸满铺墨底 + `font-weight: 600`。
若墨底失效，12.5px 中文里 400 / 600 差得很轻。

⇒ 在 `@media (forced-colors: active)` 里给 `.cs-seg-btn.on` 加一条
**下划线**：`text-decoration` 的存在与粗细**不是颜色属性**，系统不会抹掉。
常态不画（平时墨底已经说清楚了）。

⚠ **本节下面那条「仍然没测」已被作废**——真开系统主题后验过了，
见下一节。下划线最终保留，是因为它在真主题下确实能扛过绘制层接管
（15.13 : 1 那张图里，选中项既有描边也有下划线）。

## ✅ forced-colors 实测完成（2026-10-14，真机系统主题）

**无头 Chrome 会继承系统对比度主题**，于是绘制层接管**可以真截图**。
（之前的推断「测不到」是因为只改了 CSS 媒体查询，那只是本项目自己的

### 量到并修掉的三个真缺陷

| # | 缺陷 | 实测 | 修法 |

## ⚠ 禁用态口径：三方对不上，本轮把它**算**出来了（2026-10-14）

新量具 `ui/scripts/disabledsep.py`。**不碰浏览器**——`opacity` 是 CSS 合成运算，
结果只由前景色 / 背景色 / alpha 三个数决定，与「元素此刻在不在页面上」无关。
⇒ 于是绕开了票里记着的那个死结（`.cs-btn:disabled` 绑 `busy[p.id]`，没配 API key
时恒 false，**页面上根本不会出现禁用按钮**，所以真机验不了），直接把三组数算出来。

| 方案 | `.cs-btn-ink` 文字/底 | `.cs-btn-ink` 底/页底 | `.cs-btn-mini` 文字 | `.cs-btn-mini` **边框/页底** |
|---|---|---|---|---|
| enabled（基线） | 16.74 : 1 | 15.31 : 1 | 15.31 : 1 | **1.57 : 1** |
| `opacity: .34` | 2.18 : 1 | 2.11 : 1 | 2.11 : 1 | **1.16 : 1** |
| `opacity: 0.45` | 2.94 : 1 | 2.82 : 1 | 2.82 : 1 | **1.21 : 1** |
| `border-style: dashed`（不淡） | 16.74 : 1 | 15.31 : 1 | 15.31 : 1 | **1.57 : 1** |

### 两条结论

1. **`opacity` 稀释的是整个元素**——文字、**边框**、底色一起淡，不只是文字。
   这正是 `debug/+page.svelte` 当初反对它的理由，现在有数字了：
   `debug` 注释里写的「掉到 1.5:1 上下」**偏乐观**，`.34` 实算是 **1.16 : 1**。
2. **`border-style: dashed` 是零代价方案**：所有对比度**与正常态完全相同**，
   只改边框线型。代价只是「虚线」这个形态本身好不好看。

### ⚠ 落地时才发现的坑：`dashed` 对墨底药丸**不生效**

定案写「改成 `dashed`」，真改的时候才发现 `.cs-btn-ink` 是本屏**唯一没有边框**
的按钮（墨底药丸），`border-style` 对它完全无效——只写一条 `.cs-btn:disabled`
规则会**漏掉这个按钮**，而它恰恰是唯一的危险开关。
⇒ 照 `debug/+page.svelte` 的先例（那边是 `dashed` + 换 `background`）分两种处理。

⚠ **判据的边界必须说清**：WCAG 1.4.3 / 1.4.11 对 `disabled` 控件是**明确豁免**的
（disabled 元素不要求满足对比度）。所以上表**不是合规判据**，而是
「用户还能不能看出这里有个按钮、知道它不能点」这一条**设计可读性**。
把它当硬门槛会逼出一个没人真需要的数字。

⚠ 顺带查出一条**与禁用态无关**的事实：`.cs-btn-mini` 的边框**正常态就只有 1.57 : 1**，
低于 UI 组件边界常用的 3 : 1。因为文字有 15.31 : 1，组件本身完全可辨，
所以不构成 WCAG 问题——但它解释了为什么「再叠一层 opacity」格外致命：
本来只有 1.57 的那条线，被淡一次就没了。
