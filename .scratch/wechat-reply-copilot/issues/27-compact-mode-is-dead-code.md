# 27: 紧凑模式在真实窗口里是死代码

**What to build:** 面板窄到一定程度时真的切进紧凑布局。

**Blocked by:** None（但要改哪块面板取决于票 **25**）

**Status:** done · **2026-10-14 前提消失，改为回答它背后的真问题**

## 症状（2026-10-13 记录）

```text
tauri.conf.json              "minWidth": 340
(panel)/+page.svelte         const COMPACT_AT = 340;
(panel)/+page.svelte         compact = entry.contentRect.width < COMPACT_AT;
```

`340 < 340` **永远不成立** ⇒ 紧凑分支在真实窗口里是**死代码**。

而它的注释写着「实测 320px 时三栏并排会挤成两行」——那个 320 是
**在浏览器里把演示外框拖窄**量出来的，真实窗口拖不到那么窄。

## 为什么之前没人发现

这条**只记在 `docs/面板设计.md` 里，而那份文档第一行写着「已作废」**。
一个仍然成立的产品缺陷，唯一的记录处是一份没人会照着做的文档——
典型的「重要结论被埋在错误的信息层级里」。

2026-10-13 整理文档时才把它挖出来。

## ✅ 2026-10-14：票 25 选了「合并路由」，这个 bug 自己消失了

旧面板在 `5031ab3` 整体删除，`COMPACT_AT` / `compact` **全仓无引用**
（`ui/src` 里 `rg -i compact` 零命中）。票里原写的方案 A（降 `minWidth`）
与 B（抬 `COMPACT_AT`）都不必选了——**要改的那块面板已经不存在**。

⇒ 票里原写的「⚠ 在票 25 定下来之前不要动手：如果票 25 选了 C（合并路由），
这个 bug 会自己消失，改了反而白改」——正是这一条。

## 但它背后的真问题还在，换个问法重验了

票 27 真正想回答的是「**面板窄到 `minWidth` 会不会挤**」，
不是「紧凑开关可不可达」。所以：

- **给演示取景框加了 `?w=<px>` 探针**（`(panel)/+layout.svelte`）。
  原来取景框写死 380px，而 `tauri.conf.json` 的 `minWidth` 是 340
  ——**一个验不到自己下限的尺子不是尺子**。
- 出图核对 `w=340` 与 `w=380`（`target/shots/w340.png`、
  `state-confirm.png`）：正文正确重排（4 行 → 5 行），纸面不出框，
  档位行位置不变，**没有横向溢出、没有截断**。
  ⇒ 纸面板在窗口下限**不挤**，不需要紧凑分支。

⚠ 这次是**浏览器**里验的，不是真机。`?w=` 验的是「同样的 CSS 宽度下
布局对不对」，与真机 WebView2 的渲染差异仍在（票 22 第 4 条那个风险
同源）。真机那一步仍欠着。
