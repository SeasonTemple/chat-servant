# 30: 真机上 OCR 认不准，结构对但字不对；会话名压根认不出

**What to build:** 让「认会话」与「读正文」在真实微信帧上成立——
现在结构对、字不准，归属行整行不显示。

**Blocked by:** 需要本机微信在场（本票的证据就是这么来的）

**Status:** ready-for-agent · **2026-10-14 真机取证完毕，未动手改**

## 结论先写

**闸是好的，坏的是它旁边的两件事。**

`peer=""` 看着像安全闸出问题，其实不是。观察循环的闸认的是
**头部像素指纹**（`HeaderPrint::is_same`），不依赖 OCR。真机日志里
指纹区域 **16000 px（400×40，阈值 0.90）** 取得到，闸是开着的——
证据就是同一段时间里 `messages=5 candidates=3`，候选都产出来了，
闸关着的话一个字都不会起草。

会话名是**另一条路**（`watch.rs::refresh_peer` → `peer_name_from_header`）：
裁头带 → 放大 → OCR → 取第一条非空行。**任何一步失败就一直保持空串**，
而空串的初始值就是空。所以归属行整行不显示，是「一直没能读出来」，
不是「读出来是空的」。

## 证据（`cargo xtask perceive`，现场抓帧）

```
锚点 (304,31)-(1156,618)  配色 rgb(30,30,31)
OCR 读到的会话名：（没读出标题行）
闸用的像素指纹：16000 px（区域 400x40，阈值 0.90）
```

`cargo xtask layout` 的横带测量：

```
== 非面板底色横带（行占比 < 0.35 的连续段）==
  共 3 条：
  y    0 ..   32   高  32      ← 就在锚点上边缘
```

### 假设一：标题栏被切在捕获区之外（**未验**）

聊天区锚点从 `y=31` 起，而 `y=0..32` 是一条**不同底色的横带**。
`HEAD_BAND_H = 40` 裁的是聊天区**自己**的顶部 40px；如果微信 4.x 的
会话名其实住在框外那条带子上，`peer_name_from_header` 裁到的就是
一片空白面板，OCR 自然返回空。

⚠ **这条只是假设。** 要验它得看那张帧——而帧里有真实聊天内容。
`cargo xtask probe frame` 会把它写到 `target/probe/`（gitignored），
**动手前要用户点头**。

### 假设二：OCR 在这个尺寸下大面积认不准（**有证据**）

真机帧上 11 px 高的小字几乎全是乱码：

| 类别 | 实测 |
|---|---|
| 灰色时间戳行 | 11px，读成 `8用5日 《〕巧:33` / `g用10日 21：11` 一类 |
| 被判为「标题」的行 | 高 9，读成单个字符 `0` |
| 正文（中文） | 逐字替换，`引oome了deK0jinLesson Nandesuka!?` |
| 正文（拉丁 / URL） | **基本正确** |

⚠ 票 07 早就记过这件事（「11px 中文标题 OCR 把真实会话名读成 `G8W`」），
只是当时没有把它和 `peer=""` 连起来。

⇒ **判据：OCR 对拉丁字符可用、对中文小字不可用。**
任何「中文为准」的功能（会话名、中文草稿、意图判断）都在裸奔。

### 结构是对的，字是错的

这一条要分清，否则会得出「整条链路都坏了」的错误结论：

- 说话人归类（我 / 对方）**正确**——绿气泡 / 深气泡分得开；
- 消息条数与边界**正确**——换行的 URL 正确地并成了一条消息；
- 归类为「标题」的行**确实存在**（白字深底，对比 211.2），
  只是位置不在标题带内、文字被读成 `0`。

**所以链路是通的，精度不够。** 这两件事的修法完全不同。
