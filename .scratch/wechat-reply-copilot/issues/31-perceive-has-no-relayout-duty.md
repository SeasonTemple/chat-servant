# 31: 感知层只做了一半——没有「随布局变化重新对齐」这条职责

**What to build:** 让「头部在哪里」由感知层算出来并随布局变化，而不是让
调用方写死坐标去猜。

**Blocked by:** None（票 30 的修复是它的前置现场，但本票可以独立开）

**Status:** done · 2026-10-14 实现完成、九步门禁全绿、
真机往返验过（换会话 `peer` 跟着变、旧消息清空、切回后 6 条全部恢复）

## 症结：缺的是第二条职责，不是第一条

用户点出的抽象 UI 层有两条职责，对照代码：

| 职责 | 现状 |
|---|---|
| **① 对应实际窗口的虚拟布局，只反映本程序需要关注的部分** | ✅ **已有**。`capture::anchor::PaneAnchor` 就是它：`chat` / `panel` / `header_top` / `input_top` 全部**像素内容锚定**，注释里明写硬性要求「像素内容锚定，不写死坐标」（要扛 125%/150% DPI 与任意窗口尺寸），阈值全部来自真机测量 |
| **② 根据微信布局、窗口的变化实时调整** | ✅ **本票补上**。头部行由 `identity::HeaderPrint::discover` 从像素推出来 |

`anchor.rs` 顶部注释里留着一行说明，看得见当年的洞：

> 「标题栏与面板同色，靠文字区分，文字归属由 OCR 的活。所以 `PaneAnchor`
> 只把头部锚到**标题栏下沿**，精确的头部高度**留给 ticket 03 用文字行归定，
> 不在这里硬编一个比例**」

⚠ **而票 03 当时只做了 OCR 探针，没做「用文字行归定头部高度」这半截。**
⇒ 注释指向一张已经 done 的票，而那半截谁都没接。**没有任何地方算出过
「头部有多高」**，所以调用方只能猜。

## 为什么代价这么高：猜错三次，而且是静默的

`watch.rs` 自己拿锚点拼带子、自己 OCR，与感知层**平行实现**。
2026-10-14 真机复验（微信 `0x3D02FC`，深色主题，1267×930）：

| 版本 | 带子取法 | 真机结果 |
|---|---|---|
| 修复前 | `top = (header_top - chat.y0).max(0)` ⇒ 恒 0，落在消息区顶部 | `peer` 恒空 |
| 修复第 1 版 | `top = chat.y0 - 40` ⇒ 往上 | `peer` 仍恒空 |
| 修复第 2 版 | `top = chat.y0` ⇒ 往下 | 待验（已回滚） |

真机几何（实测，`chat.y0 = 31`）：

```text
y  0..48    空白            ← 第 1 版取的就是这里
y 49..59    会话名（高 11）  ← 真答案
y 80..97    首条消息
```

⚠ **三次都错，而且三次测试都绿**——因为夹具也按各自的错误假设画字块，
「夹具与生产一起错」。这与票 30 是同一个病：**没有一层说「头部在哪」，
于是每次都得有人改魔数，改对了也不知道对不对。**

## 做法：`HeaderPrint::discover`

在 `crates/perceive/src/identity.rs` 新增：

```rust
pub fn discover(frame: &Frame, chat: Rect, width_cap: i32) -> Option<(Self, Rect)>
```

- 只看 `chat.x0` 右侧、消息区顶部往下 `HEAD_SEARCH_H = 72` 的范围，
  逐行统计「与本块众数亮度差得够远」的像素数。
- 第一行**连续成行**、行高在 6..=24、墨数 ≥ 8 的，就是会话名那一行。
- **不用 OCR**：闸要赶在 OCR 之前跑（硬约束第 6 条的静默期零调用）。
  这里只看**几何**，不读字。
- 返回 `None` = **认不出**。调用方必须按「认不出」处理（关闸、不起草），
  **不是**当「是同一个」。

### 为什么高度必须量化

`similarity` 在两片掩码**尺寸不一致**时直接给 0。推导出的高度若逐帧抖动，
闸会每帧判成「换了人」。⇒ 高度对齐到 4px 栅格（`ROW_QUANT`）。

### ⚠ 量化必须**向上**取整（真踩到的）

`quantize_row` 原先写的是 `div_euclid`，即**向下**取整：真机会话名高 11px
⇒ 落到 **8px**，把字形下沿裁掉 3px。而它自己的文档注释明写
「11px → 落到 12px 那一档」——**代码和注释对不上**。

⚠ **裁字没被任何别的判据抓住**：实测把 `div_euclid` 退回之后，
`chat-servant-app` 侧 **73 条测试全绿**（含专门盯着像素量的那条）。
闸仍然关得对、仍然分得开两个会话——**判别力退化是静默的**。
⇒ 只能靠一条直接钉住不变量的判据兜住：
`quantization_may_round_up_but_must_never_crop_the_glyph`
（断言「推出行高 ≥ 实测行高」，且不把 `ROW_QUANT` 写死成常量）。

## 判据：夹具不许自带被测答案

⚠ **这是本票最要紧的一条**，也是前三轮全绿的直接原因。

| 判据 | 守什么 |
|---|---|
| `discover_follows_the_header_line_wherever_it_moves` | 头部行放在 `+18` / `+30` / `+8` 三个位置都要推对 ⇒ 证明 `discover` 里没写死 y |
| `the_discovered_height_is_quantized_so_the_mask_size_is_stable` | 行高差 1px 必须落到同一尺寸档，否则闸每帧判成换人 |
| `discover_returns_none_when_there_is_no_header_line` | **失败方向**：认不出必须给 `None`（否则闸会以为「还是同一个人」而继续动手，直接撞硬约束第 1 条） |
| `discover_is_stable_across_a_small_layout_shift` | 布局挪 3px 不能判成换人 |
| `discover_still_tells_two_conversations_apart` | 推导对了，**判别力不能丢** |
| `quantization_may_round_up_but_must_never_crop_the_glyph` | 量化只许向上，不许裁字形 |
| `the_watch_layer_does_not_hand_roll_the_header_rect` | 守**接线**：`watch.rs` 不许再出现 `header_band_rect`，生产代码不许直接 `HeaderPrint::of(`，必须含 `discover(` |

**这些判据都自证过会响**（量具自检必须能因为量具偏了而失败）：

| 把代码改成什么 | 哪条立刻红 |
|---|---|
| `discover` 退回写死 `chat.y0 + 18` | `discover_follows_the_header_line_wherever_it_moves` |
| `quantize_row` 退回 `div_euclid` | `quantization_may_round_up_but_must_never_crop_the_glyph` |

⚠ **判据自己也会匹配到自己**：`include_str!("watch.rs")` 查的是整个文件，
而判据就住在里面。匹配串必须 `format!` 拼出来——**连注释里也不许出现
完整字面量**（原先那条注释里就写着 `fn header_band_rect(`，结果判据被
自己的注释绊倒，永远红）。

## ⚠ 夹具踩到的第三个坑：行段粘连

首条消息行原本从 y=60 起，而会话名行是 y 58..69——**首尾相接、中间没有空行**。
`discover` 的行游程把两者**合并成一个 22px 的行段**（量化后 20），
取样带 8000 px 里消息文字占 5760、会话名字形差只剩 ~189
⇒ 相似度 **0.9704 ≥ 阈值 0.90** ⇒ 判成「同一个会话」。

真机是有间隙的（名字 y 49..59、首条消息 y 80..97，中间空 60..79）。
⇒ 夹具的首条消息一律从 **y 80** 起。**行粘连会让闸的判别力静默失效**，
所以夹具必须按真机几何造，不能只保证「有字在那儿」。

在真帧上（微信 `0x3D02FC`，1253×923，`chat.y0 = 31`）跑 `cargo xtask perceive`：

OCR 读到的会话名：G8W

- 实测行高 11 ⇒ 向上量化到 12，与票里写的档位对上。

## 时序取舍：走的是 A，但没改架构

⚠ 原票列了 A / B 两条路，并写明「不擅自选」。实际落地取的是 **A 的精神**：

- `discover` **不做完整 OCR**，只数「哪几行有墨」——所以它能**排在 OCR 之前**跑。
- ⇒ 硬约束第 6 条的静默期零调用优化**没被动**：指纹没变就不重读会话名。
- `refresh_peer` 仍是「指纹变 → 才取名字」，闸关着时零 OCR。

⚠ 代价要说清：`peer_name_from_header` 取名字时**仍要在推导出的那一行附近
裁一块做 OCR**（OCR 对 11px 窄行常返回 0 行，所以上下各留 `PEER_NAME_BAND_H`
的一半余量）。**会话名来自 OCR、闸来自像素，两条通道**——
这正是 `merge.rs::conversation_name` 那条判据「标题栏之外的 Header 绝不能
当会话名」的用武之地。

⇒ **B 明确不走**：那会让静默期每轮一次 OCR，与硬约束第 6 条直接冲突。
若将来要改这条硬约束，得显式拍板并写 ADR，不能顺手改。

## ✅ 真机往返验过（2026-10-14 17:20 前后，`pnpm tauri dev`）

起真 app，让微信在前台，观察循环跑起来后切换会话。日志原文：

```text
tick=64   phase=failed    peer="G8W"    messages=6 candidates=0
tick=65   phase=read      peer="古文山"  messages=0 candidates=0   ← 切到另一个会话
tick=141  peer="古文山"  candidates=0
tick=156  phase=drafted   peer="G8W"    messages=6 candidates=1   ← 切回来
tick=181  peer="G8W"    candidates=1
```

三项期望全部成立：

| 期望 | 实测 |
|---|---|
| 切走时 `peer` 换掉 | ✅ `G8W` → `古文山` |
| 切走时**旧会话的消息清空** | ✅ `messages` 6 → 0（`park_on_other_conversation`） |
| 切回时消息**全部恢复** | ✅ `messages=6`（不是只剩最后一条 ⇒ 水位线跟着回退了） |

⚠ **「切到新会话后不读它的消息」是设计，不是缺陷**：闸只服务锁定会话，
切到别的会话就停泊（park），不认领新会话。与硬约束第 1 条同向。

### ⚠ 这轮撞见但**没修**的一个问题（需要拍板）

停泊在别的会话时，面板正文显示的是**「对方说完话，这里才落笔。」**
可那个会话对方明明说过话——微信里看得很清楚。

⇒ 那句话**在这条路径上是假的**。面板其实处在「已停泊、没在读这个会话」，
不是「对方没说话」，而**界面没有为停泊态自己的说法**，
于是落进了 `fresh` 那一支（`messages: []` ⇒ 「对方没说话」）。

⚠ **没顺手改**：该说什么是设计决定（停泊要不要说、要不要区分
「锁着别的会话」与「这个会话对方真没说话」），不该在验收里夹带。
⇒ 与票 30「空态文案与上一行直接打架」是同一族，建议开票处理。

### 取证时踩到的一个坑（顺手记）

`scripts/shotwin.ps1` 走 `PrintWindow`，**连续两次截图 MD5 完全相同**
——它在回放同一张陈旧帧，若据此判断「点击没生效」会得出假结论
（`AGENTS.md` 里已有「要抓真实画面用屏幕 DC `BitBlt`」那条，这里是同一条的
又一个实例）。改用 `computer_desktop_state` 的**桌面合成画面**才拿到真相。

⚠ 另：微信是自绘 Qt 窗口，**UIA 取不到它的控件树**
（`computer_window_list` 对 `Weixin` pid 返回「No windows reported」），
且**会话列表项不吃合成点击**（连点 3 次都无效、坐标换算已核对无误）。
可行路径是**搜索框**：点搜索框 → 输入会话名 → 回车。
⚠ 中文被 IME 吞掉（框内空但候选出得来），**ASCII 如 `G8W` 正常**。

## 下次改这块之后的复验步骤（已跑通，存档）

⚠ 这一节原本写的是「机器自己验不了，要人手动点」——**不成立**，
`computer-use` 能点，只是要点对地方（上面「取证时踩到的一个坑」那节记了坑）。

```powershell
cd ui; pnpm tauri dev
```

1. 微信停在一个会话上，等面板出现归属行，**记下显示的名字**。
2. 切到另一个会话。⚠ **不要点列表项**（合成点击无效）——
   点**搜索框** → 输入会话名 → **回车**。
   中文会被 IME 吞，ASCII 会话名最省事。
3. 等一两轮观察循环（面板每秒一轮），看归属行：

| 期望 | 不对说明 |
|---|---|
| 旧名字消失，变成新会话名 | 闸没关上，或 `discover` 在新布局下推错了行 |
| 面板里的消息**清空** | `park_on_other_conversation` 没生效（闸关了但消息还挂着） |

4. 再切回来，确认消息**重新出现**且没有只剩最后一条
   （水位线没跟着退回顶部的话，只会读回 1 条）。

⚠ **判据别用 `shotwin.ps1`**：它走 `PrintWindow`，会回放陈旧帧
（实测连续两次截图 MD5 相同）。用 `computer_desktop_state` 看真实画面。

⚠ **若归属行变空**：先看 `cargo xtask perceive` 打的「推导出的头部行 y …」。
若它推出来的 y 与 OCR 读到会话名那一行**不一致**，就是推导在真实新布局上失灵了
——把这两个数记下来即可（**不要记名字**），那是下一轮的入口。
