# 36: 消息区 ROI 的左边界退化成 0，把会话列表框进了 OCR

**What to build:** 让 OCR 带子的左边界真的落在聊天区上，而不是 `x0 = 0`。
现在它把左侧整条会话列表（会话名、摘要、时间、静音铃）一起框进去，
OCR 读到几十行列表文本，归类器被带偏，**消息数从 6 掉到 3**。

**Blocked by:** None

**Status:** ready-for-agent

## 实测（2026-10-15，本机真机）

微信 `Weixin.exe` pid 25680，客户区 **1253×923 @ (817,157)**，会话 **G8W**。
操作路径：面板切档 → 微信用「搜索框输 `G8W` + 回车」切会话（见票 31 的复验步骤）。

```text
# 正常时（切走之前）
roi=Rect { x0: 0, y0: 171, x1: 940, y1: 637 } ocr总行=41 本轮行=6 归类=6 消息=4
tick=84 phase=drafted peer="G8W" messages=6 candidates=1

# 切到别的会话再切回来之后（稳定复现，连着十几轮一样）
roi=Rect { x0: 0, y0: 191, x1: 940, y1: 637 } ocr总行=48 本轮行=9 归类=9 消息=1
tick=1228 phase=read peer="G8W" messages=3 candidates=0
```

两个数同时变坏，方向一致：

| 量 | 之前 | 之后 | 说明 |
|---|---|---|---|
| `本轮行` → `消息` | 6 → **4** | 9 → **1** | 读到的行**变多了**，消息却**变少了** |
| `messages`（emit 的） | 6 | 3 | 上游看到的消息数腰斩 |

⚠ 「读到的行变多、消息反而变少」是这条的关键形状：
它不是漏读，是**读进了不该读的东西**——多出来的那几行不是消息，
于是 `归类=9` 里绝大多数被判成噪声。

## 为什么 `x0: 0` 不该是 0

`crates/perceive/src/pipeline.rs` 里 `expected_chat()` 写的期望锚点是：

```rust
Rect::new(SIDEBAR_W as i32, 26, W as i32, INPUT_TOP as i32)   // SIDEBAR_W = 192
```

⚠ 也就是说，**聊天区左边界至少要跳过 `SIDEBAR_W` 那一段侧栏**，
而真机的侧栏（会话列表）实测约 **307px** 宽。
`x0 = 0` ⇒ 带子从窗口最左边开始，**侧栏整条在里面**。

⇒ 下一步该看的是 `anchor::PaneAnchor` 怎么推出 `chat.x0`，
以及 `watch.rs` 拼 OCR 带子时有没有把 `chat.x0` 丢掉。

## 为什么票 31 的验收没抓到

票 31 验的是「换一个会话，`peer` 要跟着变」，三项期望是
`peer` 换掉 / 消息清空 / **消息全部恢复**。
⚠ 但那次的 `messages=6` 是**切回 G8W 之后立刻读到的**，
且是在**同一个窗口布局**下；本票是**跨了一次会话切换 + 窗口位置微变**
（`shotwin.ps1` 报 1267×930 @ (810,157)，`computer_window_list` 报
1253×923 @ (817,157)——含不含边框差 14px/7px）之后退化的。

⇒ 建议补一条判据：**切走→切回之后，`messages` 的条数要等于切走前的条数**
（不只是「大于 0」）。现在这条只能人工看日志。

## 影响面

- 直接后果：切回会话后不再起草（`candidates=0`、`phase=read`），
  动作行不出现 ⇒ **`Auto` 档的真机发送验收做不成**（它没有候选可点）。
- 安全性方向是**偏保守**的（读不到 ⇒ 不动作），不违反硬约束第 1 条；
  但它让整个产品看起来「失灵」。
