# 38: 黄金基线比微信旧了 8 天——夹具里的我方气泡绿，今天已经不生产了

**What to build:** 让「实测」和「基线」这两类证据各自说清自己是什么时候的。
现在两者混在一起，导致源码注释里的实测表**整行与本机现状对不上**，
而根因不是有人编了数，是**基线帧老到了微信都换版本了**。

**Status:** in-progress · **2026-10-15 已定位、已订正注释与演示夹具、已加守卫测试**
· **「基线已陈旧」这件事本身还需要人来定重生成策略（见「待定」）**

## 现象

2026-10-15 用 `scripts/shotwin.ps1 0x1F080A` 抓当前真机微信帧，
在消息区（`x 316..1256`，即 `anchor.rs` 实测的 `chat.x0`）做 1:1 调色板普查，
与 `attribute.rs` 文件头那张「实测表」逐行对：

| 项 | 注释里的「实测」 | 真机复测 | 判定 |
|---|---|---|---|
| 面板底色 | `rgb(30,30,31)` 彩度 1 | `rgb(30,30,31)` 彩度 1 | ✅ |
| 对方气泡底色 | `rgb(47,47,48)` 彩度 1 | `rgb(47,47,48)` 彩度 1 | ✅ |
| 对方气泡墨色 | `rgb(225,225,229)` 对比 178.4 | `rgb(225,225,229)`，`luma` 差 **178.3** | ✅ |
| 面板灰字 | `rgb(123,123,128)` 对比 93.5 | `rgb(123,123,128)`，`luma` 差 **93.5** | ✅ |
| 会话名（标题） | `rgb(225,225,229)` 对比 195.4 | `rgb(225,225,229)`，`luma` 差 **195.3** | ✅ |
| **我方气泡底色** | **`rgb(114,205,144)` 彩度 91** | **`rgb(53,210,141)` 彩度 157** | ❌ |
| **我方正文对比** | **162.6** | **133.2** | ❌ |

`rgb(114,205,144)` 在两张独立抓的帧里出现次数都是 **0**
（中间窗口移动过，`wechat-live.png` / `wechat-live2.png` 两次结果一致）。

顺带排掉量具陷阱：`crates/**` 里**没有任何改色/反色/归一化**处理，
帧是原样流到 `perceive` 的——不是「 perceive 看到的和截图不是一个东西」。

## ⚠ 我第一轮的结论是错的，已推翻

我第一版写的是：「`rgb(114,205,144)` 与本机两个主题的实测值都不相等，
它**不是任何一次测量会输出的值**，大概率是当年**手挑的数**被复述成了『实测』」。

**这个结论被黄金基线直接推翻。**
`crates/capture/tests/golden.rs` 断言消息区里
`rgb([114,205,144])` 的像素数是 **28956 / 19736**——那个数是**数出来的**，
来自 `crates/capture/fixtures/*.png`（时间戳 **2026-10-07**）。
把常量一改，三条 golden 测试当场红：

```
wechat-dark-2side：消息区里我方气泡 rgb([53,210,141]) 的像素数从 28956 变成了 0
wechat-dark-myside：消息区里我方气泡 rgb([53,210,141]) 的像素数从 19736 变成了 0
```

⇒ **那个绿是真的量出来的**，只是量于 **2026-10-07**。
⇒ 这 8 天里**微信换了版本或主题**，我方气泡从 `rgb(114,205,144)`（彩度 91）
变成了 `rgb(53,210,141)`（彩度 157）。

**真正的问题因此不是「有人编数」，而是「基线比微信旧了 8 天」**——
这正是 `AGENTS.md` 里那句「别把『CI 全绿』读成『黄金基线验过了』」的现实版：
夹具在本机**是存在的**（所以测试真的会跑），但它验的是一个**已经不存在的微信版本**。

⇒ 换个角度说：**守卫是响了的**。是 golden 测试抓住的漂移，
不是我在注释里发现的。把常量改成真机值之后它立刻红——
这说明这套基线在「颜色漂移」这一类问题上是有区分力的。

## 行为影响：产品代码零改动

两条依赖这个数的判据逐条复核（`attribute.rs:234-253` 的分支顺序）：

1. `SATURATED_MIN_CHROMA = 30` —— 量的是 `chroma(probe.bg)`。
   真值 **157**，比阈值高 5 倍多，比旧值 91 更高。**余量变大，不翻车。**
2. `HEADER_MIN_CONTRAST = 140` —— **只在 `on_panel` 分支**里比。
   我方气泡底色是饱和绿，`is_panel_bg((53,210,141), (30,30,31))` 为假
   ⇒ **永远走不到这条判据**，133.2 < 140 与代码无关。

注释里那句「对方正文对比 178.4 **比我方 162.6 还高**」在真值下变成
「178.3 比 133.2 高」——**结论方向没变**（对方那档确实高于 140，
所以「必须先判在不在气泡里」这条顺序依然钉死），但引用数字要一起改。

  串同步（8 文件，逐条自检过条数与 JSON 可解析性）

## 新增守卫：`the_dark_theme_chroma_separation_the_threshold_rests_on_is_pinned`

把真机量到的四档彩度钉死：我方 **157**、对方气泡 **1**、面板 **1**、头像 **26**，
并断言 `SATURATED_MIN_CHROMA` 夹在「非我方那一档里最高的」与「我方」之间。

⚠ 记这条是因为量到过一个**看着像缺陷的数**：`rgb(247,238,221)` 彩度 **26**，
离阈值 30 只差 4。差点当成「头像要被误判成我方气泡」。
**它是头像，不是气泡底色**——`probe.bg` 采的是文字框外一圈底色，采不到头像；
真要撞线还有 `RING_PURITY_MIN`（外圈众数占比 0.35）先挡。
⇒ 守卫里把 26 显式钉住，是为了让「差 4」在数据漂移时能报警。

## 待定（需要人拍板）

基线要不要重生成、怎么重生成，本票**不自己决定**：

| 候选 | 代价 |
|---|---|
| 保持现状 + 注释写明「基线是 2026-10-07 的」 | 零成本，但基线继续验一个死版本 |
| `cargo xtask fixture --name <n> --source <当前帧>` 重生成 | 基线会跟着**当前这段对话**走；且夹具源自真实聊天，脱敏与不入库策略要重新走一遍 |
| 只重生成颜色、不重生成对话内容 | 得先有办法把新帧里的对话换成合成文本，否则夹具来源又指向真实会话 |

⚠ 无论选哪条，**「黄金基线验过了」这句话在本机都已经不成立**，
这是本票最该被记住的一句。

## 量具上踩的两个坑（本轮）

1. **粗网格把「对方没有气泡」读成了事实**。用 64×24 网格取每格众数，
   对方气泡只占消息区 1.23%，**没有任何一格被它主导** ⇒ 整张图看不到
   `rgb(47,47,48)`，一度得出「真机深色主题下对方消息没有气泡」。
   **是格子太粗，不是现象。** 裁出消息区直接看像素 + 在区内单独统计才对。
   —— 与 `attribute.rs:135` 那条「两侧气泡像素数常常打平，强行学反而引入不确定性」
   同族：**众数类量具对小目标系统性失明。**
2. **第一版结论没交叉验证就写进票**。「它不是任何测量会输出的值」这句话，
   只要先去看一眼 golden 测试的断言就会发现是错的。**否定结论必须由穷尽性查询支撑。**
