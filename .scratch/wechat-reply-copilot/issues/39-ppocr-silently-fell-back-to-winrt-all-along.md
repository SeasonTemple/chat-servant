# 39: PP-OCR 每帧都在失败并静默回落 WinRT——「下载模型」这条线到今天为止从没真正跑过

**What to build:** 决定 OCR 走哪条路。现在两条路的真实状态都不清楚，
而**过去所有关于「模型不准」的结论都是错的**——因为那条路根本没在跑。

**Status:** ready-for-human · **2026-10-15 已定位并修掉两个真 bug，但路还选不了**
· 关键决策在「该选哪条」一节

## ⚠ 先更正一条已经讲出去过的判断

2026-10-15 本会话里我给过用户这个结论：

> 「rec（识别）是准的，坏的全在 det 的框粒度」
> 「用户说的『准确度不高』本质是**排版 bug**，不是模型能力问题」

**这句话是错的，撤回。** 当时跑出来的那份输出（`还 有 30 分 钟 解 封`）
**根本不是 PP-OCR 的输出**——PP-OCR 每个宽度桶都在加载权重时失败，
整轮报错被吞成 `None`，然后回落到 WinRT。我量的是 WinRT 的逐字切词，
把它当成了 PP-OCR 的 det 行为。

## 根因：权重路径拼错 + 回落完全无声

- `ocr_pp_pipeline.rs` 的 `BucketCache::plan_path()` 拼出
  `ch_PP-OCRv4_rec_mobile_w{w}.onnx`，而磁盘上只有 `ch_PP-OCRv4_rec_mobile.onnx`。
  每个宽度桶的 `load_rec` 都在 `model_for_path` 失败 → 整轮报错 →
  吞成 `None` → `ocr.rs` 回落 WinRT。
- 加剧因素：`ocr.rs` 那条回落 warning 被 xtask 的
  `with_env_filter("xtask=debug,wgc=trace")` 丢掉（没给全局档位），
  **回落一条日志都没有**。

### 判据不是读日志，是**比耗时**

| 强制走的引擎 | 耗时 | 输出 |
|---|---|---|
| `CHATSERVANT_OCR=ppocr` | **13456 ms** | — |
| `CHATSERVANT_OCR=winrt` | **309 ms** | — |
| 两者输出 | — | **逐字节相同** |

⇒ 13.4 秒和 0.3 秒不可能是同一个引擎产出的。
PP-OCR 每帧全失败、回落到 309ms 的 WinRT，所以两边一样。

**「跑一次特别慢」这件事本身就是「它在失败」的信号**，
比任何一条日志都可靠——因为回落路径没有日志。

## 已修（子代理，代码在 `crates/capture/**` 与 `xtask/**`）

| 位置 | 改动 |
|---|---|
| `ocr_pp_pipeline.rs` `plan_path` | 指向真实的 rec 权重，分桶只缓存**编译结果**不缓存文件 |
| 同上 `det_plan` | 缓存改为记 `(h,w)`；原来不记形状，窗口改尺寸会复用错形状的图 |
| 同上 `DET_MAX_BOXES` | 从 `det_boxes`（行合并**前**）移到 `merge_into_lines` 之后，单位从「连通域」变「行」 |
| 同上 det `std` | 由 `[0.456,0.456,0.456]`（误抄 mean）改为 PaddleOCR 的 `[0.229,0.224,0.225]` |
| 同上 rec 归一化 | 改用自己的 `mean=std=0.5`，不再复用 det 的 ImageNet 常数 |
| 同上 DB 后处理 | 补上原本**完全缺失**的 `unclip` 外扩（ratio 1.5） |
| `ocr.rs` | 补文档：回落是静默的，判据是耗时量级 |
| `xtask ocr` | 新增 `--stats` / `--prob`，`probe_ocr` 增加成句性指标 |

新增/改写 6 条守卫，其中两条**自证过会响**（把修复回退后恰好这 2 条红，
报错是「权重路径指向一个不存在的文件」与「单字框在行合并之前就被截断了」）。

## PP-OCR 跑通之后：仍然不行，而且慢到不能用

修完 `plan_path` 后 PP-OCR 真的跑起来了，**但输出仍然不成句**。

| | 修前（其实是 WinRT） | 修后（PP-OCR 真跑） |
|---|---|---|
| 2× 单帧耗时（debug 构建） | — | **108.9 s** |
| 同条件 WinRT 耗时 | 0.18 ~ 0.51 s | — |

**⇒ PP-OCR 比 WinRT 慢 200~600 倍，而输出还不如现在这条好用。**

残留的真问题（子代理实测，证据在 `--prob` 的概率图上）：
**det 框纵向只盖住字形上半。** 同一帧同一行，源图墨迹 `y=292..303`（12px），
det 框 `y=286..294`（8px），概率图在 `286..293` 饱和（≥0.9）、`294..306` 全空（<0.1）——
**概率图确实响应在没有墨迹的地方**，所以降阈值无用。rec 因此拿到被削掉下半截的字。

已排除的三条路：阈值、深色主题（反相后概率图几乎不变）、输入分辨率（2×/4× 都不改善，4× 反而 245 s）。

## WinRT 这条路的真实水平（2026-10-15 实测，生产条件 2×）

**不是「这么差」。** 2× 下正文大部分读得对：

```text
命脉 / 难道说 / 文件传输助手 / 也不一定把 / https://studio.tripa3d.ai/zh
最好….语言".jpg / 在WarkBuddy里… / 04．2部署中
```

对照上一轮那份 `还 有 30 分 钟 解 封`，**差别来自跑的是 2×（生产条件）而不是 1×**。

### 剩下的三个问题都是具体的、可修的

| 问题 | 证据 | 性质 |
|---|---|---|
| **空格插错地方** | `直 送代版本名吗`、`不是前面讠 就豆了演进`、`三 付¥g．` | **检测把一个字拆成两个框**，中间留了 14px 间隙（比值 1.17）。空格判据本身是对的（阈值 0.5，实测相邻汉字比值 0.00~0.17），**是上游给了坏框** |
| **头像/图标被读成文字** | `0`、`1毳06`、`14丐0`、`14它6`、`1400`（30 行里有 7 行只有 1 个 token） | 头像与图标被检测成文本框 |
| **个别行仍乱码** | `安亘：臬吉片 放器 后过一` | 未查 |

⚠ **「空格是不是因为中文逐字切词」这个假设也是错的**：实测相邻汉字间隙
0~1px、字高 12px、比值 0.00~0.17，远够不到 0.5 的插空格阈值。
**中文之间根本没有插空格。**

## ⚠ 2026-10-18 订正：上面那些耗时是 **debug 构建**，真实差距小两个数量级

上面「108.9 s」「慢 200~600 倍」全部来自 **debug 构建**，而生产跑的是 release。
今天把 `xtask ocr` 加了 `--repeat`（冷/热分开报——生产是长驻进程，
第一遍要建会话、按形状编译图，**能不能踩进 `TICK` 看的是热调用**），
在 `--release` 下重测同一张图（425×198，`OCR_UPSCALE = 2` ⇒ 850×396）：

| 构建 | 冷启动 | **稳态中位** | 对 `TICK = 1000ms` |
|---|---|---|---|
| debug（原先记的） | — | 108 900 ms | **109 倍** |
| **release** | 1 996 ms | **1 679 ms**（1605~1693） | **1.68 倍** |

1× 对照（release）：冷 1 247 ms，**稳态 945 ms**（922~978）——差一点点就进预算了。

⚠ 而且上面那张图**远小于生产输入**。真实聊天窗夹具 `wechat-dark-myside.png`
（1262×958，2× ⇒ 2524×1916）：冷 6 989 ms，**稳态中位 5 294 ms** = **5.3 倍预算**。
（det 的耗时与图上有没有字无关——那个夹具本来就没文字，跑的仍是 PP-OCR。）

⇒ **订正**：
- 「慢 200~600 倍」是 debug 的产物。真实差距对 WinRT 是 **3~29 倍**
  （小图 1.68s vs 0.5s；真实尺寸 5.29s vs 0.5s）。
- 但「**今天这个实现进不了 1000ms 的 tick**」这条**仍然成立**，
  而且在真实尺寸上是 **5.3 倍**，不是差两个数量级——
  换构建档位已经用掉了，剩下的口子只有换推理后端（tract → ONNX Runtime）
  或把 det 降到 1×（而 1× 的准确率是另一笔没算过的账）。
- ⚠⚠ **原判断书里「追平需 218 倍」这个说法作废。**
  写它的时候把 debug 当成了生产；**那不是路线问题，是量错了构建档位**。
  与其否掉技术路线，不如把它改成「**还差 1.7~5.3 倍，缺的是后端不是方向**」。

## ⚠ 2026-10-18：det 错位定位到了（坐标映射），但**修完端到端仍是乱码**

之前那句「怀疑 ONNX 图的 Resize 坐标约定 `half_pixel` vs `asymmetric`」
**已被证伪**，别再当线索用。

### 已定位并修复：框的坐标换算用了错误的尺寸

`det_boxes` 用 `src_w/pw`、`src_h/ph` 回映射，而概率图属于**补齐后**的 det 输入
空间（帧 425×198 → det 输入 448×224，概率图实测也是 448×224）。
`det_input` 是原样拷贝 ⇒ **概率图像素与原图像素 1:1**，正确比例恒为 `det_w/pw`。
于是所有框朝原点缩，实测框下沿比墨迹下沿高 **−6 / −8 / −12 / −16 / −14 px**，
**误差随离原点的距离线性增大**（比例恰为 `198/224`）。

**决定性对照**：把帧裁成 416×192（32 倍数、不补边），同一批墨迹给出的框与
「补齐情形的框 ×224/198」**逐行吻合到 1px 以内** ⇒ 「按 det 输入换算」与
「让 det 不补边」数值等价，选前者（改动面最小，调用方两处）。

**顺带排除的两条**（都做过实验，不是推理）：
- **Resize 坐标约定**：ONNX 6 个 Resize 节点明写
  `coordinate_transformation_mode="asymmetric"` + `nearest_mode="floor"`，
  tract-core 0.23.8 正是这么实现的 ⇒ **tract 没做错**。
- **补边用复制而非补黑**：改成补黑，概率图亮区只从 65..71 变成 66..71（1 行），
  文本仍是乱码 ⇒ **排除**（已回退）。

### ⚠ 但端到端**仍然是乱码**，还有第二个缺陷

修完坐标后 `--prob` 显示：det 概率图对每一行只亮 **6~7 行**，而字形约 12~17 行
⇒ **概率图本身纵向欠覆盖**，这是坐标映射之外的另一个问题，**量到了但未定位到成因**。

⚠ **这个「12~17 行」不可信**：它是用亮度阈值量出来的，而那张图是**羊皮纸纹理底**，
阈值一放宽就把纹理和阴影算成墨迹。下一步应先用更严的阈值重测真实字形高度，
才能判断 6~7 行到底算不算欠覆盖。**别拿这组数去支撑任何结论。**

可能方向（**均未验证**）：① 按 PaddleOCR 的做法「先缩放到 32 倍数再补黑」
（现在是「不缩放 + 复制补边」）；② 问题在 rec 而不在 det；③ 换 ONNX 运行时
（tract → onnxruntime）。

### 🔴 一条工程陷阱：`target/release/xtask.exe` 陈旧会**静默换掉引擎**

排查时发现：改了 `models_dir()` 之后没重编 release 二进制，它仍去旧目录找权重，
找不到就静默回落 WinRT —— 而**输出看起来是正常的**。

**判据**：`CHATSERVANT_OCR=ppocr` 与 `CHATSERVANT_OCR=<随便乱填>` 输出**逐字节相同**
⇒ 说明两条路根本没分叉，你看到的是回落后的引擎。
⇒ **动过权重路径或引擎选择之后，先重编再测**；拿旧二进制的输出当基线，
  会把 WinRT 的表现记成 PP-OCR 的表现。

## 该选哪条（需要人拍板）

| | PP-OCR | WinRT |
|---|---|---|
| 现在能读出正文吗 | ❌ 不成句 | ✅ 大部分对 |
| 单帧耗时（debug / 2×） | **108.9 s** | 0.18~0.51 s |
| 对深色中文小字 | 未验 | 已验，大部分对 |
| 离线、无依赖 | ✅ 权重在 `<仓库>/target/models/`（2026-10-18 从 `%APPDATA%` 迁进项目） | ✅ 系统自带 |
| 剩余工作量 | 查明 det 纵向错位（怀疑 ONNX 图的 Resize 坐标约定 `half_pixel` vs `asymmetric`） | 修头像误检 + 拆字误检 |

**我的建议：先按 WinRT 修那三个具体问题，把 OCR 从「不准」提到「够用」；
PP-OCR 的 det 几何问题单独立票查，不要和准确率修复绑在一起。**

理由：观察循环要的是**每几秒一帧**，108.9 s 这一条就否掉了它；
而 WinRT 缺的只是两个具体的误检，各有明确的量。

⚠ 但这是**取舍不是事实**——如果后面要做的不只是单聊、还要更高准确率，
PP-OCR 的天花板更高，值得投入去查那个 Resize 约定。

### 2026-10-18：我的判断（不再只给选项）

**仍选 WinRT 做生产路径**，但**理由换了**，而且这一条要写清楚：
否掉的是「**今天这套实现**」，不是 PP-OCR 这条路线。

1. **PP-OCR 的精度天花板从来没被量过。** 今天所有「不成句」的输出都出自
   同一个 det 纵向错位（框只盖住字形上半），那是**一个 bug**，
   不是这个引擎的能力上限。**拿一个有 bug 的实现去代表整条路线，是拿对照组论证实验组。**
2. 而那条路要通，缺的东西是明确的、可点的：Resize 坐标约定
   （`half_pixel` vs `asymmetric`）+ 一个更快的后端。
   这两件都有确定的落点，不像 WinRT 那边的「拆字误检」还在飘。
3. 硬约束第 6 条（**静默期零调用**）不构成任何一边的好处——它管的是
   「对方没说话时零 token」，与用哪个引擎无关。

**PP-OCR 路径：留，但让它吵。** 缺权重时明确报「PP-OCR 未安装」，
不要静默回落（静默回落正是本票的起因）。
理由：它现在是唯一一条**精度天花板未被否证**的路；删掉等于把一次
未完成的实验当成结论固化进代码。

⚠ 这两条里，第 1 条是我今天才补上的——原先那张表把「不成句」直接当成
PP-OCR 的性质写进了对比，而那半边当时是**同一个 det bug**造成的。

## 量具上的坑（本轮）

1. **「模型不准」这个结论是在引擎没跑的情况下得出的。** 判据不是看日志
   （回落无日志），是**比耗时量级**。凡是要断言「某条路不准」，
   先证明那条路真的在跑。
2. **诊断时改过帧的呈现方式（1× → 2×）却沿用旧结论。** 1× 与 2× 的准确度
   差着一个量级，「不准」的结论在 1× 上成立、在生产条件 2× 上**不成立**。
   ⇒ 报准确率必须带 `放大 N×`。
