# 44: 候选动作行一整天没动过——它是**按钮几何套在正文上**，这是根因

**What to build:** 让候选动作行读起来是**纸上的候选项**，不是一排带边框的按钮。
现在它一整天零改动，用户原话：「还有这个候选回复的样式设计 还tm是这样吗？
一天过去了，0改动？你很满意？」

**Status:** 进行中 · **2026-10-16 四角与「读成方框」的根因已定位并修完；门禁全绿；两项复核仍未做**

## 现象

2026-10-15 真机截图：候选动作行是一个**通栏的描边矩形**，
左边一道墨色竖笔，文字「按这个」贴在左边。

![候选动作行现状](用户 2026-10-15 截图)

## 根因：§4.2c 定的是**按钮族**，候选行承载的是**整句正文**

`docs/设计规范.md` §4.2c（2026-10-13 定案，2026-10-15 进实现）写得很明确：

> 三种，共用同一套几何：**高 30 / padding 0 16 / radius 4 / 13px 600 / 全是 1px 描边**

而落地时又在同节第 3 条补了一条：

> 纵向用 `min-height` 而非 `height`。……动作行的备选要显示**整句正文**，压进 30px 会截掉。

⇒ **规范自己承认了冲突**，而当时选的处理是「那就用 min-height」。
结果就是：它既不是规范里的 30px 按钮（因为会截断），
也**不是正文排版**（因为套着按钮的框、圆角、字重、14px 内边距）。

**这是把两套要求硬拧在一起**，用户看到的正是这个拧巴：
一个通栏四边闭合的框，里面躺着一句要读的话。

## 方向：2026-10-16 由用户拍板

用户否掉了票面原来列的 A/B/C 三条，明确指定：

⇒ 候选行 = **从这张纸上撕下来的一片**。已按此落地。

### ⚠ 两条 CSS 缺陷（**已定位、没改，等你裁决**）

**1. `Auto` 档被勾中的那一条，正文是铅笔灰不是墨色。**
实测 `rgb(76,90,99)`，与两条备选**同色**。而 `PaperPanel.svelte:1860` 的注释白纸黑字写着

⇒ **根因是特异度**：Auto 档下 `actVariant()` 让首条也拿 `cs-act-red`，于是

⇒ **Auto 档下「首选 = 墨色正文」这条分工不存在，首选与备选只差一枚勾的颜色。**
1× 就看得见，不是放大才出现的。

⇒ 两条都是**代码与注释/意图不符**，不是新设计问题。

## 2026-10-16 收尾：四角与「读成方框」的六轮

用户红框标的「还是原生边框」是**两件叠在一起**的事。
下面每一条都有实测，且**每一条都不是上一轮写的那条原因**。

### 1. 四角：`flip_x` / `flip_y` **两个都是反的**

病根不在「分量顺序用错」，而在**四条带子在图里的朝向本来就不一致**：

| 带子 | 索引 0 是哪一侧 |
|---|---|
| 顶带 `top_mid` | row 0 = **外沿** |
| 底带 `bot_mid` | row 0 = **内侧** |
| 左边带 `left_mid` | col 0 = **外沿** |
| 右边带 `right_mid` | col 0 = **内侧** |

（`slice_bot` / `slice_right` 是从画布**远边** crop 的，所以读出来是「内→外」。）

而角瓦片贴在图上时，它自己的 `(0, 0)` **永远是最外侧那个角**。
⇒ 拿 flip 去「把带子转回来」，就得在两个方向上**分别记反、记正**，
极易只改对一处。实测就是这样：只有左上对，其余三个把纸放到了错的那一侧。

**修法：不翻转。** 带子被 `paste` 进去时朝向已经是对的（`paste` 的位置就是证明），
`build_corner` 直接按**图坐标**取样：

```python
h = hb.getpixel((CORNER_AT, y))      # 横边：厚度 = y
v = vb.getpixel((x, CORNER_AT))      # 竖边：厚度 = x
```

### 2. 角的判据本身是错的，而且**对「翻反了」完全免疫**

旧判据是「不透明像素 ≥ 45%」。两个问题：

- **几何上不可能达到**：不透明区恒为 `{x ≥ 深度x} ∩ {y ≥ 深度y}`，
  四条边实测深度 11~29 而 `band` 只有 32 ⇒ 算下来就是 5%~30%，
  顶角与底角**天生就在两档**（实测 27/22 与 6/5 正是区间两端）。
- **翻转只把不透明矩形挪到角的另一侧，面积一模一样** ⇒ 这条判据对
  「角翻反了」完全免疫。事实是第 ④ 轮里三个角正好反着，它却全绿。

**换成查位置**：① 紧邻纸芯的那个角点必须不透明；
② 沿两条「紧邻纸芯的行列」各量一次撕口深度，必须落在**该边自己中段实测的区间**内（±2）。
第 ② 条一并拦掉「取样轴用错」「取到纸的外角」「角整块透明」。

现读数（四角全 ✅）：

```
左上: 左边深 16[5~18]   顶边深 16[11~27]
右上: 右边深 15[7~18]   顶边深 16[11~27]
左下: 左边深 16[5~18]   底边深 21[18~26]
右下: 右边深 15[7~18]   底边深 21[18~26]
```

⚠ **写判据时自己踩了同族坑一次**：四个角瓦片贴到图上的**朝向各不相同**
（左上内角在 `(31,31)`、右上 `(0,31)`、左下 `(31,0)`、右下 `(0,0)`），
第一版统一按 `(31,31)` 当「紧邻纸芯」，于是三个好角误报「没连上」。
判据本身写对了，**量具的坐标假设错了** —— 改成按图坐标量才过。

### 3. `box-shadow` 画的是**边框盒**，撕口的透明区会漏出它的直边

这是四角修好之后**剩下的那条「原生边框」**。

实测（`target/probe/act-after.png`，1040×1520 @2x，`drafted` 档，
裁掉页面外框）：

```
x=203 一列，y=485~905 连续暗（185~205），邻列 x=202/204 = 198/227
x=225 一列 —— 纸的左边沿在这里
```

⇒ 中间那 22px 就是撕口的透明区，而 203 上那条约 2px 的线是投影的直边。

**换成 `filter: drop-shadow()`**（跟随渲染结果的 alpha 通道，即纸自己的轮廓），
同一条剖面复测：`199/186/176/196 → 223/224/217/220`，与邻列一致。

⚠ 换实现带出一个**回归**：`box-shadow` 在 forced-colors 下由 UA 强制 `none`，
`filter` **不会**。已在 HC 块里显式撤掉（理由同 `.cs-sheet` 撤纸纹：
不与 HC 互斥的东西要撤，不是留着赌它不碍事）。

### 4. 沿边取样窗口**不能取纸的正中间**

四角修好后出图，底边仍是**一条直线**。用 `ui/scripts/_straightscan.py` 量：

```
底边 y=630/749/868（每条候选的下沿）横线段长 224px、最深 47
右边 x=682（每条候选的右沿）       竖线段长 155px、最深 34
```

根因是**样本选得平**，不是裁剪做得平：正中间那 128px 恰好是**平台段** ——
底边深度 27~29（跨度 **2** 源 px = **1 CSS px**），
右边 14~18（跨度 4 = 2 CSS px）。1~2 CSS px 的起伏就是一条直线。

⚠ 旧判据（取值种数 ≥ 3）**抓不住它**：27/28/29 三种取值、渐变列 63/64，全过。
⇒ 判据改成**跨度**（`MIN_SPAN = 4` 源 px）。

改成按中段跨度滑窗择优（约束：深度 ≤ 30，保证带内每列还留着纸）。
跨度提高情况（源 px）：

| 边 | 正中间（原来） | 择优后 |
|---|---|---|
| 顶 | 14~20，跨度 6 | 11~27，跨度 **16** |

### 5. `check()` 里「没有一处硬跳 ⇒ 被平滑掉了」这条判据**已删除**
