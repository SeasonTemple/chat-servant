**What to build:** 让设置屏与主面板**同族**：同一张撕口纸、同一套墨与红铅笔。

**Status:** ready-for-human · **2026-10-16 第五轮：档位行红勾压住「只填入」——笔比字大 2.43 倍且与字同宽，长臂必然横扫整行读成「划掉」。加 `--ms`/`--mx` 两个旋钮（0.72 / 8px）后标签可读、勾仍盖在字上；结构冲突未解开，已列四档对照。真机仍未看过**

3. **规范 §1 / §5.1**：两条旧条标注作废，写明理由与「全屏同族」的新约束。
4. **删掉 `--cs-paper-sunken`**（见下），禁用态改用纸本身。

当时判为「⚠ 未决，需一次真机确认」。**现在有答案了，而且两个数都没记错，只是各指一样东西：**

```
<svg width="380" height="560" viewBox="0 0 380 560">
  <g filter="url(#sheetDrop)" transform="translate(16,0)">
    <image x="0" y="0" width="348" height="512" …>
```

### 滚动条为什么提到全局（而不是共享类）

病根不是「忘了复制」，是**做法本身允许忘**。共享类 `.cs-scroll` 解决不了——
下一个滚动容器照样可以不加。只有全局规则能让「新加一个滚动容器」不再是一个需要记得的决定。

顺带实测出一条**纠正**：`app.css` 原来同时写了标准属性与 `::-webkit-scrollbar`，
量到的槽宽是 **10px 而不是设计的 6px** —— 因为 CSS 滚动条模块规定
`scrollbar-width` 不为 `auto` 时 **Blink 会忽略 `::-webkit-scrollbar` 那一套**。
原注释写的「只写标准属性在 WebView2 不生效」**把因果说反了**：
不是标准属性不生效，是它接管之后 webkit 那套不生效。
⇒ 改成 `scrollbar-width: auto` + 只留 webkit 那一套，实测回到 **6px**。
本项目只发 Windows 包（WebView2 = Chromium），放弃 Firefox 支持的代价是 0。

**意外收益**：槽宽 10 → 6，多出的 4px 让首条候选从 4 行折回 3 行，
`drafted` 态的溢出从 81px 降到 59px。

### 勾的尺寸：不能缩（实测）

先按「主面板动作行是 20×12」把勾抄成 20×12，出图一看**几乎是空的**，
只看得见一抹极淡的红。原因是**笔性随尺寸变**：五层嵌套的羽化按 56 宽调，
每层边只有 1~2 个 viewBox 单位；压到 0.36× 之后每层羽化都落到亚像素，
芯与边叠在一起 = 墨被摊薄。**这不是 opacity 调错了，是把它当矢量图缩放了。**
⇒ 改回自然尺寸 56×34，并让它像主面板那样**溢出边界、盖在字上**（盖章式）。

⚠ 主面板动作行那枚 20×12 的勾**同样偏淡**，同一个病，那处还没改。

### 字体：不统一的真因不是「差得多」，是**没有一档是共用的**

收敛前实测（只读代码追继承链得到，含 `TierSwitch` 子组件）：

- **font-size 9 档**：10.4 / 10.88 / 11.2 / 11.5 / 11.52 / 12 / 12.48 / 12.5 / 12.8 px
- **line-height 4 档**：1.45 / 1.5 / 1.55 / **`normal`（14 个选择器根本没写）**
- **font-weight 3 档**：400 / 600 / **700（只有 `.cs-group-name` 一处）**

其中 11.5 与 11.52 差 **0.02px**、12.48 与 12.5 差 **0.02px** ——
肉眼绝无分别，却各自写着。**这才是「不统一」的真正来源**：
不是差得多，是每一处都自己写了一个数，没有一档是共用的。

`normal` 那条最隐蔽：它是「按字体算的」，不是某个数，
于是每个选择器的实际行高都不同，而且**没人知道是多少**。

收敛后 5 档，每档都有多个元素共用：12.8（分组标题）/ 12.5（小节标题、
字段标签、供应商名）/ 12（数值读数）/ 11.5（说明、按钮、输入框）/ 10.4（徽标）。
行高在 `.cs-set` 上设一次 `1.5`，全屏继承。

**字体族保留两套是有理由的**：雅黑 UI 栈走全部正文，
等宽栈只给 `.cs-input` 与 `.cs-slider output` —— 那两处显示的是 key 与数字，
等宽是为了对齐，不是没统一。

### 「说明要单独一行」：它的问题不是独占，是**无依无靠**

「全部改完立刻生效，不用重启面板。」原先在屏顶独占一行，
左边没有控件、右边没有分节，**它不属于任何东西**，读起来像一行飘着的脚注。
对照：档位下面那句「默认。填进输入框…」有左边线，明确挂在它那一节。

⇒ 挪到「发送档位」标题之下，并给同款左边线。
位置不是就近，是**该被看见的位置**：档位是安全相关、
也最需要先知道「改了立刻生效」的那一项。

⚠ 这里有个结构事实值得记：`.cs-set` 是 `display:flex; flex-direction:column`，
所以每个直接子 `<p>` 都是独立 flex item，**必占整行，与文字长度无关**。
这类「为什么它单独一行」的问题，先查容器是不是 flex 列，
而不是去调 `max-width`。

### 按钮族：上一轮确实在敷衍

上一轮只把 `.cs-btn-ink`（打开/关闭）换成撕边，
而 `.cs-btn-mini` 那一族（换一把 / 测连通 / 删除 / 保存 / 厂牌 chip）
**还是 1px 灰描边** —— 和刚改好的那颗并排时就是两个时代的东西。

这一族现在与 `.cs-btn-ink` 逐项同源：同一张 `strip.png`、
同一套 `slice 32 / 16px / 0 stretch`、同一条「高斯核上沿不得越进元素内侧」
的投影判据。禁用态重做（`border-image` 一生效，`border-style` 就画不出来，
原来的虚线禁用态**已经失效**两轮了）。外层 `.cs-group` 的 1px 描边盒也去掉 ——
它把已经是撕边纸条的按钮又关回一个描边盒子，等于同一个控件上了两层框。

**代价**：撕边上下各 16px，30px 的小按钮变成约 61px。这是照指定方向换材质
必然的尺寸变化，不是顺手调出来的。

### 黑边：查了三轮，前两轮都错在**量具只量了一半**

**第一轮**：认出 `drop-shadow(0 1px 1px 22%)` 那层贴边暗线，改完复量
**数值逐位不变**（173.5 → 173.3）⇒ 归因错了。
子代理后来用 `filter: none` 对照再验一次：y=257 仍是 124.7，**投影贡献为 0**。

**第二轮**：量了 `strip.png` 的 **alpha** 剖面（y=0..9 全透明、y=10 起爬升），
据此断言「位图没有暗像素」。
⇒ **只量了 alpha，没量 RGB。** 那些像素 alpha 是满 255、根本不透明，只是 RGB 很暗。

**第三轮**（两条独立路径都落到同一处）：

1. `probe-sheet.png` 在 x≈613~636、y=16~18 有一块**深色污斑**，最暗 87.7。
2. `stripgen.py` 的 `pick_window` 只按「撕口跨度」打分，**没有「带内不许有暗墨」**
   这条约束，选中的窗（start 573）正好把它裁进顶带。
3. 那块 24 源 px 的污斑落在九宫格中段里，被 `border-image` 的 `stretch`
   **横向放大 5.5 倍** ⇒ 12 CSS px 的小污斑变成 **120×3 CSS px 的硬横杠**，
   横贯每一条撕边纸条的顶部。

逐位闭合：源行 16 最暗 **112.3** = 截图 y=257 的 min **112.3**。

**修法**：不去「换个干净的取样窗」——底边只有 **1 个**合格窗口且自带
105.3 的暗斑，换窗对底边无效。改成生成后统一**去暗**：外圈像素向纸色插值、
**alpha 一律保留**，中央纸芯不碰。

为什么敢去暗：生成器自己的文件头写着「真撕口的可辨识度**几乎全部来自那
6~13 CSS px 的深度与两级 alpha 过渡**」——**暗色不承载信息**，
撕口的形状完全由 alpha 轮廓决定。

逐位复量（many 档，x=160..260；纸底 222 / 纸芯 ~232）：

| y | 修前 | 修后 |
|---|---|---|
| 257（顶） | **124.7** | **185** |
| 330（底） | **157** | **189** |

证据图：`target/probe/{seam-before,seam-after}.png`（6×）、
`{t44-shadow-fix,many-deshade}.png`（原图）、`strip.png` 的逐行读数。

### 这一轮我自己犯的两个量具错误（留着当反面教材）

1. **拿 `/studio/actrow` 当对照页**。那页的 `.cs-act` 是它**自己写的旧样式样板**
   （1px 黑边 + 「按这个 / 备选 N」标签），页面第二栏的「撕边纸」是自绘示意图，
   **不是真组件**。照它判「撕边没有黑边」⇒ 判错。
2. **只量 alpha 就下结论**（见上）。位图的暗不只藏在 alpha 里。

两条同族：**判据的量，必须覆盖被测对象的全部相关维度**。
另一条同族已在别处留档：「窄查询的零命中不是不存在」。

## 出图时撞见的另一处：档位行的红勾压住「只填入」

⚠ **这不在用户那轮的三条之内**，是出成品图时顺带量到的。

实测（`many` 态出图，1× 截图逐像素量）：

| 量 | 数值 |
|---|---|
| 「只填入」文字包围盒 | x 149–192、y 476–489（44×14） |
| 红勾包围盒 | x 138–202、y 466–499（65×34） |
| 落在勾包围盒内的文字墨点 | **128 / 128 = 100%** |

⚠ 笔比被标的东西还大：勾的墨迹有字的 **2.43 倍**高（34 对 14）。
「盖章式压在字上」是对的（2026-10-13 用户定的案），但**笔宽 65px 与字宽 44px
几乎一样宽，而勾的长臂斜向右上** ⇒ 它必然从第一个字扫到最后一个字，
于是读成**划掉**，而不是「这一档被批了」。

⚠ 另有一处**注释与实况不符**：「盖住字不会读成删除线，圈是包围，拓扑不同」
——那句话说的是**圈字环**，而默认发的是**勾**，勾的长笔画斜穿出去，
拓扑更接近删除线而不是包围。

### 第五轮：`--ms` / `--mx` 两个旋钮

`--ms` = 标记相对档位字的缩放，`--mx` = 在笔心对齐之外再往左挪多少。
`--ms 0.72` + `--mx 8px`：勾的墨迹降到 46×19（1.36 倍字高），
长臂收在「填」上，**「入」露出来**，标签可读，勾仍盖在字上。

⚠⚠ **`top` 不跟着 `--ms` 等比缩**：笔心对齐公式是
`top = 字心y − 1.1 − 笔心y`，而 `字心y` 与 markbox 高度**不缩**。
照抄等比缩放会让笔心整体上移 ——「标一个东西却没对准它」，
与当初 `margin-left:-21px` 被推翻是同一类错。所以四条分支都写成
`46.4px×tk − 笔心y×ms×tk`（`46.4 = 47.5 − 1.1`），
改 `--ms` 一个数，对齐自动保持。

⚠⚠ **四条分支都必须自带 `--ms` / `--mx`** —— 特异度问题，见下面「量具教训」。

### 剩余的结构冲突（没解开，只是不再恶化）

| 方案 | 结果 |
|---|---|
| `--ms 1.0`（原值） | 勾读得出，标签被压 |
| `--ms 0.72` + `--mx 8` | 标签可读、勾仍盖在字上 —— **当前定案** |
| `--ms 0.55` | 笔缩成一团红疙瘩，五层羽化读不出是铅笔 |
| `--ms 0.72` + `--mx 16` | 跑到字左边，读成「旁边一个勾」＝2026-10-13 被否掉的形态 |

⇒ 笔宽与字宽同量级，「盖章」与「可读」只能取折中。真正要解开只有两条路，
都超出本轮：① 档位名改短（会动到硬约束第 5 条的措辞）；
② 标记换窄笔画（要在 `marks.js` 重生成，与候选条共用那一支）。

### 量具教训：本轮卡了整整一轮的那个坑

⚠⚠ **`margin-left` / `top` 改了数值而出图零变化** ——
依次排除了缓存、HMR、calc 嵌套语法，**全都猜错**。真因是 **CSS 特异度**：

- 本机**默认发的是 `data-shape="tick" data-ring="big"`**（`--dump-dom` 实测），
  不是文件注释里写的 `base`；
- 命中 `.cs-tick[data-shape='tick'][data-ring='big']`，特异度 (0,3,0)，
  **压过基规则 `.cs-tick` 的 (0,1,0)**；
- 而 `--ms` 当时**看着生效了**，因为 `width`/`height` 只写在基规则里 ——
  「有的旋钮有效、有的完全无效」这个症状把人引向了错误方向。
⇒ 判据：**改 `margin-left` / `top` 之前先 `--dump-dom` 看清命中哪一条**。

⚠⚠ **我自己用 PS 5.1 的 `Set-Content -Encoding UTF8` 写坏了一次源文件**（写了 BOM），
正是 `AGENTS.md` 明令禁止的那条。改中文文件一律用 `edit` 工具。
判据同样来自量具：出图字节数与上一张**完全相同**（哈希一致），
而缓存与时序都不该产生这种「一模一样」——一模一样通常意味着根本没变。

## 第四轮：用户指着 chip 问「这个框什么意思呢？里面颜色也和边缘不一致？」

不是观感问题，是**位图本身的结构错位**，量出来三条硬数字：

| 区（`strip.png` 128×128） | RGB | R−B |
|---|---|---|
| 核心 `fill` 区 64×64 | (249.7, 236.4, 198.9) | 50.8 |
| 紧邻核心的外圈带 | (239.1, 221.7, 176.3) | 62.8 |

核心比紧邻它的外圈**亮 R +10.6 / B +22.6**。而
`border-image: url('/strip.png') 32 fill / 16px / 0 stretch` 里的 **`fill`**
正是把中央 64×64 纸芯画进元素内容盒的那一位 ⇒ 「里面」与「边缘」在同一张位图里，
用户一眼就能比出来。那不是撕边纸片，那是一个**贴了浅色底的框**。

⚠ 旧实现 `deshade()` 只动外圈、注释明写「中央的纸芯一个像素都不动」，
**这就是台阶的来处**。三轮里前两轮一直在调 `DESHADE_KEEP`，方向本来就错了。

**改法两处一起**：
① 目标色从 `(238,220,174)` 换成面板自己的 `--cs-paper` `(243,230,192)`；
② 纸芯也处理，但按「只搬均值、保留纸纹起伏」——实测纸芯 sd R 1.84 / B 5.99、
   面板纸 sd R 6.4 / B 7.0，全压平会让内芯比周围的纸更死。
`DESHADE_KEEP` 随目标色变亮从 0.12 降到 0.08，保持残留暗像素等价。

**结果**（渲染图，chip 内中位数 − 整屏面板纸中位数）：
**改前 (+3, +6, +8) → 改后 (−4, 0, 0)**，落进面板自身 sd 之内。
`strip.png` 的 alpha 逐像素**零变化**（16384 px 全等）⇒ 撕口轮廓可证未动。
三类撕边元素（`.cs-act` 候选条 / `.cs-btn-ink` / `.cs-btn-mini`）走同一条
`border-image`，一处修全部受益。

⚠⚠ **本轮我犯的第二个量具错误**：查残余色差时拿**紧贴 chip 的那块纸**当参照，
而它落在 chip 自己的 `drop-shadow` 里，测出来比真纸暗 5~6 个蓝通道，
于是我一度以为「还差 5 没修干净」并准备再调一轮。
**参照必须取整屏中位数**（120k 像素，median (246,230,191)），
且要意识到「紧邻被测物」天然被它的投影污染。
