# 49: PP-OCR 计划缓存的**两个形状问题**——桶缓存不跨帧，det 持锁编译

**What to build:** 让计划缓存真的产生复用收益，并让 det 编译不堵住别人。

**Status:** ready-for-agent · **2026-10-17 票 47 做完后记档。两条都是票 47 的
「已知且接受」或「不在本票范围」项，本机（Windows + Rust 1.94.1）编得过**

## 1. `det_plan` 在**持锁期间**编译 det 图

`crates/capture/src/ocr_pp_pipeline.rs` 的 `det_plan(h, w)`：

```rust
let mut slot = det_plan_slot().lock().unwrap();      // 拿锁
if let Some((ph, pw, p)) = slot.as_ref() { ... }      // 命中判断
let p = ocr_pp::load_det(...)?;                       // ⚠ 在锁内编译，十几秒级
*slot = Some((h, w, Arc::clone(&p)));                 // 才写回
```

⇒ 它**不会重复编译**，但**会堵住所有其它 det 调用者**整段编译时间。
这正是票 46 方案 1 明确不接受的那个形状——票 47 选了方案 2（每键 `OnceLock`）
来修 `BucketCache`，`DET_PLAN` 这个更早的同类**没跟着改**。

⚠ 同一条路现在用的是 `lock_recover`（票 47 加的中毒恢复 helper），
所以中毒这半边已经对了；**剩下的是「编译期间不持锁」这半边**。

**修法方向**（与票 47 同构，不要引入新依赖）：
`DET_PLAN` 换成 `OnceLock<...>` 或「取/建 cell 与编译分离」，
让不同形状的 det 各编各的、不互相堵。⚠ 但它**只缓存一份**是有意的
（注释：`det 的输入尺寸随帧变，编一个几十毫秒，而一帧只跑一次`）——
改成按形状分桶会**改变内存占用**，属设计决定，需要人拍。

## 2. 桶缓存**每帧新建**，几乎不产生复用收益

`BucketCache::new` 全仓只有两处：`recognize_in:751`（**每次识别新建一个**）与一个测试。

⇒ 缓存的生命周期 = 一帧。而 `recognize_with` 里 `for (w, group) in by_w` 是**串行**的，
`by_w` 已按宽度分组 ⇒ **一轮里每个宽度只取一次图**，缓存根本来不及复用。

️ 这有两层含义，第二层是本票真正要解决的：

1. 票 47 修的那个竞态**今天不可达**（已在票 47 里记档）。修法仍值得做，
   因为它把不变量钉住了——把缓存提成 `static`（`DET_PLAN` 已经是那样）
   是一次重构之差，那时这个 bug 立刻变活。
2. ⚠ **但既然「缓存要跨帧存活」才是收益的前提，那修法 2 就不是完整答案。**
   要真拿到复用收益，得让桶缓存跨帧存活。

**为什么当初不直接提 `static`**（推测，非实测）：诊断桶缓存存在的原因是
**PP-OCR 静默回落**（票 39）——`load_rec` 在 `model_for_path` 上失败，
错误被吞成 `None`，于是回落 WinRT。分桶缓存的是**编译结果**而非文件。
⇒ 把缓存提成全局 static 之前，得先确认**形状失效**（`max_buckets` 的「清一半」）
在跨帧场景下是否仍然正确，以及**权重文件被换掉**时缓存要不要跟着失效——
这两个问题在「每帧新建」的现状下**根本不存在**，提 static 会把它们变成真问题。

⚠ **这不是能顺手改的**。它需要人先拍板缓存的失效语义。

## 验收项（两条分开验，别混）

- [ ] `det_plan` 编译 det 图期间**不持有** `det_plan_slot` 的锁，
      且并发调不同 `(h, w)` 时**互不阻塞**（守卫：与票 47 同构的并发用例，
      判据取「同时在编的峰值 ≥ 2」而不是耗时）
- [ ] 桶缓存若改成跨帧存活（`static` 或提到调用方持有）：
      - [ ] 权重文件被替换 / 删除时，缓存**会**失效并重编
            （否则用户更新模型后永远用旧的）
      - [ ] `max_buckets` 的「清一半」在跨帧下仍成立
      - [ ] **明确写下失效语义**，别让它停在「没人想过」的状态——
            票 47 的教训正是「默认 `unwrap()` 等于没表态」
