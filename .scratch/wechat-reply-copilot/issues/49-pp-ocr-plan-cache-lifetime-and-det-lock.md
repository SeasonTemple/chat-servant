# 49: PP-OCR 计划缓存的**两个形状问题**——桶缓存不跨帧，det 持锁编译

**What to build:** 让计划缓存真的产生复用收益，并让 det 编译不堵住别人。

**Status:** done · **2026-10-18 两条都做完**（det 不再持锁 + 桶缓存跨帧存活）
· 2026-10-17 前半条（`det_plan` 编译不再持锁）已改已验过门禁
· 2026-10-18 后半条（桶缓存跨帧 + 失效语义）已实现，4 条守卫、自证会响

## 前半条：已做（2026-10-17）

`DET_PLAN: OnceLock<Mutex<Option<(h,w,Plan)>>>` → `DetSlots<P>`，槽里存
`HashMap<DetKey, Arc<OnceLock<Slot<P>>>>`，**编译在锁外**，锁只护「取/建 cell」。

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 键 | `DetKey = (usize, usize)`，两个分量都要 | 少一个就会拿错形状的图，而 `run` 拿到形状不匹配的输入只报错、整轮回落 WinRT，现场分不出来 |
| 容量 | `DET_SLOT_CAP = 1`，**写死在 `Default` impl 里**，不是各调用点传的参数 | 调用点没有口子能顺手把它改成按形状分桶——**「要分桶」这个动作必须先改那个常量**，而那是需要人拍板的设计问题 |
| 复用 | `DetSlots::get` 一行委托给票 47 的 `get_or_compile`（键泛型化成 `K: Eq+Hash+Copy`） | 两张表共用同一份同步逻辑与同一批守卫，**不存在第二份实现**；也没第二个锁 helper |
| 为什么用 HashMap | 容量 1 走清桶分支时 `max_buckets/2 == 0` 即「全清」，与老实现 `*slot = Some(..)` **逐字等价** | 零新代码的复用，不是分桶 |

新增 4 条守卫（全部注入桩——本机无权重，真跑模型的测试会 `return` 跳过 = 没守）：
`det_shapes_compile_concurrently_instead_of_queueing_on_the_lock`、
`one_det_shape_is_compiled_exactly_once_under_concurrency`、
`the_det_slot_still_keeps_only_one_shape`、
`concurrent_det_shape_churn_never_serves_the_wrong_plan`。

⚠ **变红验过两种反向形状**：
① 退回「持锁编译」⇒ 3 条红（峰值=1、驻留 2 份、驻留 5 份超上限）；
② 改成票 47 的老形状「锁外编译+无条件写回」⇒ `同一个形状编了 8 遍  left: 8 right: 1`。

capture **79 → 83**，0 failed；连续 5 轮重跑无抖动；`clippy -D warnings` exit=0。

### 实测收益

同一个 200ms 桩编译窗口，两个不同形状并发：

| | 墙钟 | 同时在编的峰值 |
|---|---|---|
| 改前（持锁编译） | 401.5 ms | **1** |
| 改后（锁外编译） | 200.6 ms | **2** |

⚠ 401.5→200.6 是**桩模拟的数字**，不是真 det 编译的耗时——本机没装 det 权重，
**真 det 编译（十几秒级）的墙钟收益未实测**。按结构事实报：**峰值 1 → 2，不同形状互不阻塞**。

### ⚠ 已知缺口（如实留白）

**守卫盖的是 `DetSlots::get`，不是 `det_plan` 本身。** 真 `PlanBody` 必须有 ONNX 权重
才造得出来（tract 的 `SimplePlan::new` 需要一个 `Graph`），无权重下没法真编。
⇒ **若有人绕过 `DetSlots::get`、把持锁编译直接内联回 `det_plan`，这 4 条守卫不会红。**
缓解面只有一条：容量住在类型里，改容量必须动 `DetSlots`。

另两处行为差异已写进注释：失败时槽会空掉（老实现留着上一份形状）；
并发换形状时某形状可能被再编一遍（`Arc` 保证不悬垂，代价小）。

## 后半条：~~仍需人拍板~~ · **2026-10-18 已做，见验收项**

桶缓存跨帧存活 / 提 `static` **一行没碰**。提上去之前得先定失效语义：
权重被替换/删除时缓存**要不要失效**——在「每帧新建」的现状下这个问题**根本不存在**，
提 `static` 会让它变成真问题。

## 1. `det_plan` 在**持锁期间**编译 det 图

`crates/capture/src/ocr_pp_pipeline.rs` 的 `det_plan(h, w)`：

```rust
let mut slot = det_plan_slot().lock().unwrap();      // 拿锁
if let Some((ph, pw, p)) = slot.as_ref() { ... }      // 命中判断
let p = ocr_pp::load_det(...)?;                       // ⚠ 在锁内编译，十几秒级
*slot = Some((h, w, Arc::clone(&p)));                 // 才写回
```

⇒ 它**不会重复编译**，但**会堵住所有其它 det 调用者**整段编译时间。
这正是票 46 方案 1 明确不接受的那个形状——票 47 选了方案 2（每键 `OnceLock`）
来修 `BucketCache`，`DET_PLAN` 这个更早的同类**没跟着改**。

⚠ 同一条路现在用的是 `lock_recover`（票 47 加的中毒恢复 helper），
所以中毒这半边已经对了；**剩下的是「编译期间不持锁」这半边**。

**修法方向**（与票 47 同构，不要引入新依赖）：
`DET_PLAN` 换成 `OnceLock<...>` 或「取/建 cell 与编译分离」，
让不同形状的 det 各编各的、不互相堵。⚠ 但它**只缓存一份**是有意的
（注释：`det 的输入尺寸随帧变，编一个几十毫秒，而一帧只跑一次`）——
改成按形状分桶会**改变内存占用**，属设计决定，需要人拍。

## 2. 桶缓存**每帧新建** ~~几乎不产生复用收益~~ · **2026-10-18 已修**

`BucketCache::new` 全仓只有两处：`recognize_in:751`（**每次识别新建一个**）与一个测试。

⇒ 缓存的生命周期 = 一帧。而 `recognize_with` 里 `for (w, group) in by_w` 是**串行**的，
`by_w` 已按宽度分组 ⇒ **一轮里每个宽度只取一次图**，缓存根本来不及复用。

️ 这有两层含义，第二层是本票真正要解决的：

1. 票 47 修的那个竞态**今天不可达**（已在票 47 里记档）。修法仍值得做，
   因为它把不变量钉住了——把缓存提成 `static`（`DET_PLAN` 已经是那样）
   是一次重构之差，那时这个 bug 立刻变活。
2. ⚠ **但既然「缓存要跨帧存活」才是收益的前提，那修法 2 就不是完整答案。**
   要真拿到复用收益，得让桶缓存跨帧存活。

**为什么当初不直接提 `static`**（推测，非实测）：诊断桶缓存存在的原因是
**PP-OCR 静默回落**（票 39）——`load_rec` 在 `model_for_path` 上失败，
错误被吞成 `None`，于是回落 WinRT。分桶缓存的是**编译结果**而非文件。
⇒ 把缓存提成全局 static 之前，得先确认**形状失效**（`max_buckets` 的「清一半」）
在跨帧场景下是否仍然正确，以及**权重文件被换掉**时缓存要不要跟着失效——
这两个问题在「每帧新建」的现状下**根本不存在**，提 static 会把它们变成真问题。

⚠ **这不是能顺手改的**。它需要人先拍板缓存的失效语义。

## 验收项（两条分开验，别混）

- [x] `det_plan` 编译 det 图期间**不持有** `det_plan_slot` 的锁，
      且并发调不同 `(h, w)` 时**互不阻塞**
      ——守卫 `det_shapes_compile_concurrently_instead_of_queueing_on_the_lock`，
      判据取「同时在编的峰值 ≥ 2」而不是耗时。**变红已验**（退回持锁编译 ⇒ 峰值=1 变红）
- [x] 同形状 `(h, w)` 的并发请求**仍然只编一次**
      ——守卫 `one_det_shape_is_compiled_exactly_once_under_concurrency`，
      8 线程同形状只调 1 次编译器且全拿到**同一个 Arc**。
      **变红已验**（改成票 47 老形状 ⇒ `left: 8 right: 1`）
- [x] 缓存容量**不增加** ——守卫 `the_det_slot_still_keeps_only_one_shape`
      （6 个形状走一遍槽里始终 1 份）+ `DET_SLOT_CAP` 住在类型里、调用点无口子改
- [x] 桶缓存改成跨帧存活（2026-10-18 已做）——**没有直接动 `BucketCache` 本身**
      ——测试里大量地方直接 `BucketCache::new` 并依赖它是干净实例，
      把 `buckets` 提成 `static` 会让它们互相污染。
      改为另加一张进程级的 `Arc<BucketCache>` 表（`shared_rec_cache`），
      `BucketCache` 的形状与语义一字未动。
      守卫 4 条（**纯函数、不碰权重 ⇒ CI 上真会跑**）：
      `the_same_dir_and_weight_stamp_reuses_one_cache_across_calls`（守的是
      `Arc::ptr_eq`，**不是「表里有一条」**——后者在每帧新建的表上也会成立，
      那就白守了）、`a_changed_weight_stamp_gets_a_fresh_cache`、
      `an_unreadable_weight_still_gets_a_cached_entry`、
      `the_shared_rec_cache_table_stays_bounded`。
      **变红已验**：把「命中就复用」那两行退掉 ⇒ exit=101。
      ⚠ 表由**调用方传入**（`shared_rec_cache_in`），生产那张才是 `OnceLock`——
      否则 `cargo test` 多线程共享进程态，这四条会互相干扰。
      - [x] 权重文件被替换 / 删除时，缓存**会**失效并重编
            （键 = **(权重目录, 权重文件 mtime+字节数)**，换权重自动换键，
            **不必重启进程**；权重被删 ⇒ stamp 记 `None`，与「能读到」是不同键，
            且 `load_rec` 会报错 ⇒ 回落 WinRT 并 `warn!`）
      - [x] `max_buckets` 的「清一半」在跨帧下仍成立
            ——逻辑一字未改，而它**现在才第一次真的被长期触发**：
            一帧里宽度高度重复，很少摸得到 32 个桶，所以「超限清一半」在
            每帧新建的现状下几乎是死代码。
      - [x] **明确写下失效语义**，别让它停在「没人想过」的状态——
            票 47 的教训正是「默认 `unwrap()` 等于没表态」。
            失效语义连同**已知代价**（文件系统 mtime 粒度粗时，
            「同一秒内替换同尺寸权重」理论上撞键，代价是**用旧权重跑**，
            不崩不串目录）写在 `shared_rec_cache_in` 的文档注释里。

### 收益实测（A/B：同一条命令、同一帧、同一后端、release）

`xtask ocr target\probe\chat-only.png --scale 1 --repeat N`
（856×587 消息区裁剪，10 行，`CHATSERVANT_OCR=ppocr` + `BACKEND=ort`）

| | 改前 | 改后 |
|---|---|---|
| 冷启动（第 1 遍） | 677 ms | 660 / 679 / 769 ms |
| **稳态中位** | **582 ms** | **488 / 486 / 485 ms**（三次独立进程） |
| 稳态 min / max | 574 / 603 | 453 / 536 |

⇒ **每帧省约 94 ms，占改前 16%。** 改后三次独立进程中位数 488/486/485，
**可复现**；且**区间不重叠**（改后 max 536 < 改前 min 574）⇒ 不是噪声。

⚠ **冷启动那档几乎没动（677 → 660~769），这正是改动的签名**：
第 1 遍两边都要编 det + rec，缓存都是空的；从第 2 遍起才分道扬镳。
**若冷启动也跟着大降，那说明改动落在了别的地方，该怀疑这个数。**

⇒ 反推：**rec 会话创建 ≈ 582 − 488 = 94 ms**，
而 det 计划编译 ≈ 677 − 582 = 95 ms。两者量级相近，
所以**「det 有缓存、rec 没有」这件事以前看不出来**——它藏在每帧的固定开销里。

⚠ **口径**：报的是**稳态中位**，且带 `放大 1×`；两遍都输出 10 行（识别结果未变，
本改动只碰缓存，不碰识别逻辑）。别把它当「OCR 变快了 16%」——
它是**每帧固定开销**的削减，字准那条线不受影响。

### ⚠ 决定这件事的是一条**代码形状证据**，不是性能推测

`buckets` 是 `BucketCache` 的普通字段（`Mutex<HashMap<..>>`，**不是 `static`**），
而 `recognize_in` 每次调用都 `BucketCache::new` ⇒ **rec 图每帧从零重编**，
`OnceLock` 只在**同一帧内**去重。

⇒ 票面第 2 节那句「**一帧里每个宽度只取一次图，缓存根本来不及复用**」
**只说对了一半**：轮内确实不重复，但**轮与轮之间全部重来**，
而生产恰恰是轮与轮之间在跑。

**旁证**：`max_buckets = 32` 与「超限清一半」这套淘汰逻辑，
**只在长命缓存上才有意义**。它的存在说明**按帧新建是接线疏漏，不是设计选择**。

⚠ 票面原写「`BucketCache::new` 全仓只有两处：`recognize_in:751` 与一个测试」——
行号已漂，**位置对、数量对**；读的时候按名字找，别按行号。
