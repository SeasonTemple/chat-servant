# 50: OCR 认字准不准，只存在于票里的文字里——改坏了没有任何东西会红

**What to build:** 让「正文认字准」变成会红的东西。
现在它是一张表，不是检查：换引擎、改预处理、调阈值、动后处理，
`cargo test` 都不会响。

**Blocked by:** None（验收项 1、2 可立即做；验收项 4 的实测部分需要真帧在手）

**Status:** done · 2026-10-18 · 验收项 **10/10** · L3 已落地且三向自证过

## 现象（票据级证据，不是推测）

票 30 在「定线」那一节钉了三个数，并注明「低于这些就算回归」：

| 指标 | 下限 | 当时的实测（2026-10-14，WinRT） |
|---|---|---|
| 消息召回率 | ≥ 80% | 85.7% |
| 整条全对率 | ≥ 50% | 57.1% |
| 字符准确率 | ≥ 75% | 77.3% |

⚠ `cargo test` **不检查这三个数**——它们只写在 `.scratch/` 的正文里。

2026-10-18 这一轮在这条链上做了：换引擎（WinRT → PP-OCRv6 small）、
修掉三个 det/rec 后处理 bug、默认后端翻成 ort、默认值翻成 PP-OCR。
**每一格按上面的线都算「回归或持平」，而门禁从头到尾一声没吭。**

⚠ 这不是「当时恰好没退化」。同一轮里已经出现过一次真实退化：
修后处理之前 Rust 侧 CER 是 **18.60%**，而参照实现是 **0.79%**——
**18 倍的差距，没有任何一个测试报出来**，是靠人肉 diff 读数才发现的
（ADR-0006 第（四）节记了整段）。

## ⚠ 先承认能力边界：便宜的守卫守不住真帧字准

**没有任何一种便宜方法能在 CI 里守住「真机微信帧上的字准」**：

| 办法 | 为什么不够 |
|---|---|
| 合成图 + 答案键 | 字的渲染、抗锯齿、字距、颜色对比都不是微信的；测不到 det 漏检，也测不到气泡布局 |
| 真帧脱敏后入库 | 打码会毁掉字形本身；不打码则是真人会话内容（本项目纪律禁止入库） |
| 只守结构（行数、几何、归类） | 这类已有夹具在做，但**结构对而字错**正是票 30 的原始症状——结构全绿而字是乱码 |

⇒ 所以这票**不承诺**「CI 守住真帧字准」。它承诺两件能真做到的事：
**(a) 把能守的那一类守住**（算法级回归），**(b) 把守不住的那一类变成流程要求**。

## 验收项

## ⚠ 守什么、要什么条件、现在有没有——先把这张表对齐

查过 `crates/capture/src/ocr_pp_pipeline.rs` 的 tests，现状是三层：

| 层 | 断的是 | 需要 ONNX 权重？ | 现状 |
|---|---|---|---|
| **L1** det 整链路 | 二值化 → 连通域 → unclip 的**像素级**结果（含外扩量） | **否** | ✅ **已有** `a_single_bright_block_becomes_one_unclipped_box` |
| **L2** rec 预处理 | 裁剪 → resize → 归一化后的**张量内容** | **否** | ❌ **缺** |
| **L3** rec 解码 | 推理 → CTC 解码 → 认出的字 | **是** | ❌ 缺，且 CI 上不可能有 |

⚠ **更正本票下面验收项 1 的说法**：「CI 上必然跳过」**只对 L3 成立**。
L1/L2 是纯函数，**本来就不需要权重**——把它们放进 CI 没有障碍。
原话把「整条链路」整个划到 CI 之外，那是我写宽了。

### L2 的缺口具体在哪（照着 [`rec_input`] 的实现推的）

现有 rec 侧守卫只有四条，夹具**全是 `flat(...)` 纯色帧**：

- `the_rec_input_has_the_right_length` —— 只断 `out.len() == 3*H*W`
- `boxes_larger_than_the_frame_are_clamped` —— 只断长度
- `the_rec_input_width_keeps_the_boxes_aspect_ratio` —— 断**宽度函数**，不碰张量
- `the_rec_width_is_rounded_up_to_a_multiple_of_8_with_a_floor` —— 同上

⇒ **纯色帧过任何仿射仍是纯色**，所以下面这些改动现有守卫**一条都不会红**：

| 能过的改动 | 后果 |
|---|---|
| 公式里的**系数**被改（`(p/255-M)/S` → `p/127.5`） | 偏离训练分布，识别乱码；而长度对、无 NaN |
| 布局写成 `out[o * 3 + c]`（**HWC**，现在是 `[c*h*w + o]` CHW） | 识别全崩，长度同样对 |
| `sx = bx + (out_w - 1 - x) * bw / out_w`（左右翻转） | 识别全崩 |
| 三通道都读 `p[0]` | 颜色信息全丢，仍无 NaN |

⚠⚠ **写这张表时差点又写错一条**：「归一化去掉 mean/std」看着像崩法，
**但 v6 的 rec 常量就是 `REC_MEAN=0 / REC_STD=1`**
（`the_normalization_constants_match_the_active_model` 已钉住），
所以在当前常量下那是**等价变换**——既不崩，也不红。
⇒ 能过守卫的是**系数被改**，不是「某一项没写」。
⚠ 判据：任何「去掉某一步」的改法，先拿当前常量代进去算一遍——
  等价的改法不是 bug，把它列进「崩法表」就是自己骗自己。

⚠ 另：**常量错由 `the_normalization_constants_match_the_active_model` 守**，
它断 `REC_MEAN[0]==0` / `REC_STD[0]==1`。⚠ 但那条守的是**常量**不是**公式**——
把公式改成 `p/127.5` 而常量不动，那条仍然绿（2026-10-18 实测过）。
这正是要补 L2 的原因，两条**不重叠**。

⇒ **L2 的守卫要断「像素值」而不是「长度」**。可直接落地的三条断言
（一条测试里一起验，都不需要权重）：

1. **通道独立**：夹具用**颜色**帧（例如 R 沿 x 从 0 递增、G 恒 128、B 恒 0），
   断言 `out[c*H*W + 0] != out[(c+1)*H*W + 0]` 且各自单调
   ⇒ 堵「通道写串 / 三通道读同一个字节」。
2. **布局方向**：断言通道 0 的第一行**随 x 单调递增**，最后一行递减
   ⇒ 堵 CHW↔HWC 搞反与左右翻转（两者都会让这个单调性反转）。
3. **值域**：按 `(v/255 - MEAN[c]) / STD[c]` 手算期望值逐点比对
   ⇒ 堵「归一化系数被改」。⚠ 注意本轮 A/B 证明 rec 归一化**取哪种都只差 1 个配对**，
   所以这条守的是**「系数没被乱改」**，不是「哪种才对」——别把它写成正确性断言。

## 验收项

- [x] **L2**：一条测试按上面三条断言验 rec 预处理产物。
      ⚠ **不需要权重**，所以它会真在 CI 上跑（这是它比 L3 值钱的地方）。
      夹具用**颜色**帧而不是纯色帧——纯色帧过任何仿射仍是纯色，守不住上面四条里的任何一条。
      → 2026-10-18 落地：`ocr_pp_pipeline::tests::`
      `the_rec_input_keeps_channel_separation_and_black_to_white_contrast`。
      ⚠ **纯函数，不碰权重**，`cargo test -p chatservant-capture` 就跑。
- [x] **该守卫自证过会响**：逐条退回四种「能过」写法（见上表），
      每次当场红并贴输出；恢复后全绿。
      ⚠ 判据用**退出码**，不用输出文本匹配
      （PS 5.1 的 `-match` 默认不区分大小写，见 ADR-0006）。
      → 2026-10-18 四条全退全红（判据均为**退出码 101**）：

      | 退回的写法 | 退出码 | 报错指向 |
      |---|---|---|
      | `out[o*3+c]`（HWC） | **101** | 「索引是 `c*h*w + o`（CHW）还是 `o*3 + c`（HWC）」 |
      | `sx = bx + (out_w-1-x)*bw/out_w` | **101** | 同上（单调性反转） |
      | 三通道都读 `p[0]` | **101** | 「通道 G 本该沿 x 恒定，却变了」 |
      | 公式改成 `p/127.5` | **101** | 「黑白跨度 = 2，按 REC_STD[0]=1 应该是 1」 |

      ⚠ **分工也被验到了**：退第 4 条（改公式）时，
      `the_normalization_constants_match_the_active_model` **仍然绿**
      ——常量错由那条报、公式错由新守卫报，两条不重叠。
      恢复后 `cargo test -p chatservant-capture` **92 passed / exit=0**，
      且 `git diff --stat` 是 **100 insertions / 0 deletions**（没碰生产代码）。
- [x] **L3**（可选，价值低于 L2）：一条 `cargo test` 跑完整 rec 推理并断言字准。
      ⚠ **权重在 `target/models/`、是 gitignored 的 31 MB，CI 上没有**
      ⇒ 这条在 CI 上**必然跳过**，与 `crates/perceive/tests/golden.rs`
      「缺件即跳过」是同一模式；定位是「**本地每次改 OCR 都该跑**」，
      **不是**「CI 守线」。这一条必须写在测试旁边，
      否则下一个人会把 CI 绿读成「验过了」——票 30 末尾踩过这个坑。
      ⚠ 真帧字准**不要**试图做成这条测试的一部分：见上面「能力边界」。
      → **2026-10-18 落地**：`crates/capture/tests/ocr_accuracy.rs`

      ⚠ 夹具是 `scripts/ocrbench/gen_corpus.py` 的**合成语料**

      **不是**真帧——这正是上面「能力边界」那节要的取舍。
      ⚠ 尺子照 `bench_lib` 逐字复刻（NFKC → 删全部空白 → 小写，

## 顺带记一条（本轮实测，不属于本票范围）

### 交付前在当前 HEAD 上重跑了一次真帧 CER（2026-10-18，HEAD = `003b0f6`）

这次重跑**不是**为了验这个票，是为了确认「给 ocrbench 整族补 `reconfigure`」没改掉读数——
改编码归一化是会动到数字的，所以必须前后各跑一次同一个台架。

| 读数 | 值 |
|---|---|
| 生产链路 `ort` 整表 | **CER 2.38%**（编辑 3 / 真值 126 字符，命中 17/17 行） |
| 同上，剔除贴纸区 `V6` 虚检行 | **CER 0.79%**（编辑 1 / 126） |
| 参照实现 rapidocr（同一段配对代码、同一把 ±30px 尺子） | **CER 0.79%** |

⚠ 3 个编辑的构成，逐条来自 `--explain`：
- `wechat-chat` 1 个：真值 y=185 那行只配到 1 个字的误读（读数 '贯？'）
- `gws-chat` 2 个：贴纸区真值 y=16 那一行被一个 `V6` **虚检**行抢走配对

⚠ **归因结论今天仍然成立，且是逐字相等而不是「差不多」**：
`--drop-line V6` 丢掉 `1/11` 行后，`ort` / `tract` / `rapid` 三者**全部 0.79%**。
判据锚在「丢掉几行」这个计数上（`1/11`，非 0）；若是 `0/11`，说明片段没匹配上，
此时数字变好只能说明别的行也变好了，结论作废。

⇒ 所以「本仓 ort 比参照实现差 1.59 个百分点」这句话，今天的准确说法是：
**差的不是识别，是那一个把贴纸上的字读出来的虚检框**。
其余部分与参照实现逐字一致。

⚠⚠ 这**仍然不是**一道会红的门禁。本票 L3 那条验收项未做，
而这张表依旧只存在于票据正文里——**下一个人改 OCR 之后仍然要人工跑这个台架**。
本节记的是「交付这一刻的读数」，不是「以后会自动守住这条线」。

2026-10-18 装包验证时发现：**回落类失败不体现为非零退出码**——
PP-OCR 不可用时会打 `WARN` 但退出码仍是 0。
⇒ 任何以退出码判成败的批量脚本，在这套工具上都会**全绿**。
详见 ADR-0006 那一节的「量具自检」。
