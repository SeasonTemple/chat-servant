## 评审工具本身的三个坑（本轮踩到，先记下来）

1. ⚠ **`fullPage` 截图对内部滚动容器无效。** `.cs-set` 是 `overflow-y: auto`，
   `fullPage` 只截到视口那 560px，后面六节（发送档位/外观/窗口/上下文/图片/代理）
   **全丢**——而「fullPage 没报错」这件事本身就会让人以为已经看全。
   出图前必须把滚动容器展开（`height:auto` + `overflow:visible`），
   宽度不动（380 取景框是定稿）。
2. ⚠ **内置浏览器这轮「渲染正常但 DOM 通路是空的」**：`query(kind:'dom')`
   返回 body 里只有一个空 div、`inspect` 报 0 元素，而截图完全正常。
   ⇒ 量几何只能走 `playwright-core` + 本机 Chrome 取 `getBoundingClientRect`
   （`target/probe/measure-settings.mjs`）。
   ⚠ 主机名必须写 `localhost` 而不是 `127.0.0.1`：vite dev 只绑前者，
     写后者会 `ERR_CONNECTION_REFUSED`，而同一时刻内置浏览器访问完全正常，
     于是看起来像「服务挂了」。
3. ⚠ **不能拿不同容器的控件比高度。** 我一度据「输入框 62 / 按钮 55.5」
   判「等高不成立」，而 `.cs-form` 是 flex + 默认 stretch，
   输入框高度本就由同行按钮决定 ⇒ 等高成立，是我的量法跨了容器。
4. ⚠ **展开滚动容器后出的图，纸面位图会在某一处断掉**（本轮约 y=1400）。
   那是量具的 artifact，不是产品缺陷——出图时别把它当成回归。

## ① ⛔ 手绘红勾盖住小字 —— 已修（`SegSlider` 摘掉勾，改墨洗药丸）

**实测**（`target/probe/shot-seg.mjs` 逐个裁出三组控件，出图看过）：
`TICK_VIEW` 是 **56×34**，比整组（高 **31.7**）还高，而选项文字只有 **12.48px**：

| 控件 | 勾盖字的后果 |
|---|---|
| 「只填入」/「自动发送」 | 三字被盖到只剩半只「只」+ 一道划穿「入」的笔画 |
| 「勾」/「圈」 | **一个字都读不出来** |
| 「退出」/「收进托盘」 | 「退出」被划穿 |

**为什么不是「给它配一枚小一号的勾」**：`.cs-tick` 原注释自己量过——
五层嵌套的羽化按 56 宽调，缩到 20 宽只剩一抹极淡的红。
⇒ **这一枚勾没有一个能用的尺寸**：够大盖字，够小看不见。

**为什么不是「把勾移到文字旁边」**：要给它一格 46px 的沟，
而「退出」整颗才 49px 宽 ⇒ 分段控件会被推到面板放不下。

**最终改法**：勾从 `SegSlider` 整个删掉，选中态改由药丸承载——
**12% 墨洗（`tier-ink` 混纸，1.258 : 1）+ 1px `--cs-edge` 描边（3.04 : 1）**
+ 原有 `font-weight: 600`。三处候选是算出来的，出图否掉了一处：

| 混比 | 底 vs 纸 | 选中字 vs 底 | 出图 |
|---|---|---|---|
| 8% | 1.163 : 1 | 12.13 : 1 | 2026-10-10 已判「撑不住」 |
| **12%** | **1.258 : 1** | **11.22 : 1** | ✅ 取这档 |
| 20% | 1.468 : 1 | 9.61 : 1 | ❌ **数值更显眼，出图却读成一块灰绿 chip** |
| 24% | 1.599 : 1 | 8.82 : 1 | 没试 |

⇒ **数字达标 ≠ 读起来对**。20% 那档是**出图**退回的，不是算出来的。
计算脚本留在 `target/probe/mix.py`。

**「盖章式」没有被推翻**：主面板档位行的勾一个字没动
（`PaperPanel.svelte` 的 `.cs-pick-slot` / `.cs-tick`，那里字 20px 上下、
勾有自己的取景框）。差别是**那里字大到盖得住**。

⚠ 顺带修掉一处会随改动一起烂掉的断言：`ui/static/budget.html` 的
`pencil_defs` 判据，理由写的是「设置屏的勾跨组件引用 `#pencil`」。
勾删了之后理由不成立，但**判据本身要留**（主面板每天在用那个滤镜，
丢了不报错，勾会静悄悄退化成矢量）⇒ 改了理由，删了旧断言。

## ② 同屏五种控件高度 —— 已修（全族统一 46）

修之前实测五种：**62 / 58.5 / 55.5 / 46 / 44**。根因两条，都不是目测得来的：

1. ⚠ **`min-height: 30px` 一直是空转的。** `box-sizing: border-box` 下
   `min-height` 量的是**总高**，而光撕边就有 `16×2 = 32px` ⇒ 这个值从未生效，
   各族于是各按自己的 padding 走。代码注释里「min-height: 30px + 16px 边
   ⇒ 三者逐项相等」**在 border-box 下根本推不出 30px 的内容盒**，是错的。
2. ⚠ 撕边 **16px 比内容盒 30px 还厚**（占 53%）。16px 是照抄主面板 `.cs-act`
   来的，而那一行字 20px 上下、内容盒 40px，撕边只占 40%。
   ⇒ **按内容盒重算**，不是按主面板抄。

现值：**撕边 10px + 内容 26px = 46**，`min-height: 46px`（真值）。
实测全族（输入框 / 11 颗 `.cs-btn-mini` / `.cs-btn-ink`）**逐项 46**。

- 输入框 205×62（高宽比 **1 : 3.3**，用户说的「长宽明显不合理」）
  → **217×46（1 : 4.7）**。
- `slice 32` **没改**（slice 量源图像素、width 量画到边框盒多宽），
  ⇒ **不需要重跑 `stripgen.py`**。
- ⚠ **撕边 10px 那一格是出图看的，不是算出来的**：`stripgen.py` 那条
  「纸芯最早只内缩 ~5.5 CSS px」是相对 16px 说的，按同比例换算 10px 下是 3.4px。
  若哪天撕口开始啃进内容区，往回调。
- ⚠ 「打开 46 / 重试 44」原来被本票标成「独立变体，非主按钮族」——
  **方向反了**：它们走 `.cs-btn` / `.cs-btn-mini` 同一族，
  44 是 `.cs-set`（列向 flex）默认收缩压出来的（本轮统一后不再出现）。

## ③ `app.css` 九支行内对比度注释是假的 —— 已订正

先按本票原计划**查成因**再改数，结果成因查不出，但**错法本身有诊断价值**：

| token | 注释自称 | 实测 | 订正后 |
|---|---|---|---|
| `--cs-live` | 5.95「越过 AA 正文」 | **4.28** | 4.28，**不达 AA** |
| `--cs-live-dim` | 7.18 | 5.15 | 5.15 |
| `--cs-tier-ink` | 17.71 | 12.48 | 12.48 |
| `--cs-pencil-red` | 5.90 | **4.56** | 4.56 |
| `--cs-ink` | 18.05 | 14.11 | 14.11 |
| `--cs-mark` | 3.00 | 3.51 | 3.51 |
| `--cs-pencil` | 5.10 | 5.73 | 5.73 |
| `--cs-pencil-2` | 6.13 | 6.69 | 6.69 |

⚠ **成因（已排除，结论是「不是按任何底色算的」）**：把 5.95 / 17.71 / 7.18
反解出的背景亮度**全部 > 1**，超过对纯白的理论上限（5.32 / 15.51 / 6.40），
**数学上不可能**；另三支需要 L≈0.67–0.72，互相矛盾。
已试：旧冷灰 `rgb(237 240 241)`、`paper-raised`、`surface-sunken`、纯白、
git 历史里所有 `--cs-paper`。另：`git show 16ae8d5` 证实那次提交里
`--cs-paper` **还是旧冷灰**，注释却已写「on rgb(243 230 192)」——
**声明的底色当时还不存在**。⇒ 这批数字是凭空写的，不是算错的。

**连带订正**：文件头第 31–43 行、`docs/设计规范.md` §5.2 表格、§5.3 整节。
§5.3 的结论（「红 = 警告不是对比度能定输赢的」）**方向仍成立**
——两支都掉出 AA 4.5，亮度差不足以定输赢——但「几乎相同 / 打平」不成立，
实测差 **6.5%**（4.56 vs 4.28）。
⚠ 教训：**同一支 token 在两个文件里各写一个数时，
两处都要回唯一出处核一遍**。`app.css` 文件头 §5.5b 是对的，
token 行内那批是错的，而「正确的文件写了订正」不能覆盖
「错误的文件里的结论」。

## ④ `.cs-btn-mini.primary` 用警报红承载可逆动作 —— 已修

全文 **8 处** `.primary`（保存 key / 应用路由 / 提交模型名 / 存供应商 /
用它）**全部可逆**，而 `.danger`（删除 / 忘记）才是不可逆那个。
两族共用 `color: var(--cs-live)` ⇒ 同一行里「保存」与「删除」红得一模一样，
**可逆与不可逆在界面上读不出区别**（出图确认：那行只有「保存」是红的，
红色已经不再表示危险）。撞 §1 第 3 条。

改法：`.primary` → `var(--cs-ink)`。
⚠ 原票担心的「换墨色就与未选中那颗完全一样、失去辨识度」——
**实测未选中那颗本来就是墨**（`rgb(20,26,31)`），所以 `.primary` 从来
就没有独立的颜色通道；这一屏每个动作都写着自己的字
（保存 / 删除 / 测连通），靠字就认得出来，不需要颜色再分一遍。
删除仍然是全屏唯一那颗红的（`.danger`），语义重新收拢到一处。
