# 72: 产品读帧路径手抄了一份 OCR 配方 —— 真机上「看得见行、归成 0 条消息」

**What to build:** 产品读帧路径必须与端到端探针走**同一个入口**
（`chatservant_perceive::read_lines`）；OCR 看到的**画面**与**放大倍数**由**引擎**决定，
不许在调用方手抄一份。

**Status:** done · **2026-10-20 真机复验通过（真模型出 3 条候选、点正文行真填进微信输入框）；
门禁十六步全绿**

## 起因：票 21/68/20 的真机项要真模型出候选，而真机上一条都读不出来

票 71 修完（闸能认「小号」了）之后，下一步是让 app 在真机上**真的读出对方的消息**。
真机上的微信停在会话「小号」，小号在手机上发来了新消息。
⇒ app 应当起草 ⇒ 票 21/68/20 的真机项才有得验。

而 app 的日志每圈都写着同一行：

```text
roi=Rect { x0: 0, y0: 60, x1: 852, y1: 587 } ocr总行=56 本轮行=10 归类=10 消息=0
```

拆开看：**OCR 读到了 56 行**，ROI 内 **10 行**，归类也做了 **10 条**，
**消息 0 条**。

⇒ 水位线不推进 ⇒ 不推理 ⇒ 面板永远停在「对方说完话，这里才落笔。」

## 定位：帧没问题，是**产品运行时那一路**有问题

同一台机器、同一扇窗口、同一个引擎：

| 入口 | 走的代码 | 结果 |
|---|---|---|
| `cargo xtask perceive` | `perceive::read` | **3 条**对方消息 |
| app 的观察循环 | `watch.rs` 里手写的一段 | **0 条** |

⇒ 帧是好的、OCR 引擎是好的，**分叉在代码里**。

## 根因一：产品路径手抄了 **WinRT** 的配方，而默认引擎是 **PP-OCR**

`ui/src-tauri/src/watch.rs` 里那段 OCR 是手写的：

```rust
let sc = chatservant_perceive::OCR_UPSCALE;   // = 2
let view = frame.upscaled_nearest(sc)?;       // 整帧
let ocr = chatservant_capture::ocr::recognize(&view)?;
```

它上面那段注释写着「配方与 `perceive::read_lines` 完全一致」——
**那是一句假话**，而且假了很久。

`perceive::read_lines` 的配方是一个结构体 `ViewPlan`，**由引擎自己决定**：

| | 画面 | 放大 | 依据（实测） |
|---|---|---|---|
| WinRT | **必须整帧** | 2× | 裁掉侧边栏后那条消息消失；1× 读不到对方短消息 |
| **PP-OCRv6（本仓默认引擎）** | **只给消息区** | **1×** | 整帧 1146ms/50 行 vs 裁剪 455ms/5 行，且逐字更准 |

⇒ 手抄的那份是 **WinRT** 的那一组，而默认引擎要的是**反过来**的那一组。

后果（实测，聊天区 x 370..540 的 det 框）：

```text
1×  → 8 个框
2×  → 只剩 4 个（少了 4 个）
```

PP-OCR 的 det 在 **2 倍整帧**上把**头像和正文框进同一块** ⇒ 外圈探针采到头像的杂色
⇒ `purity < RING_PURITY_MIN` ⇒ 判成「图里的字」（`NoiseClass::ImageText`）
⇒ 而 `group` 只收 `NoiseClass::Text` ⇒ **消息 0 条**。

### 为什么它不报错

整条链每一环都「正常工作」：OCR 读到了行、归类给出了结果，
**只是结果全是噪声**。门禁全绿、探针全绿、夹具全绿。
⇒ 「配方对不对」这件事，此前**没有任何机器判据**。

## 根因二：坐标系也不匹配（自证时才暴露出来）

`classify_all(&lines, frame, &palette)` 里，**行框是消息区相对坐标**，
而**帧是整帧** ⇒ 外圈探针采到的是**侧边栏**的像素。

自证 S2 的实测结果比「读不到」更凶：

```text
配方 ChatPane：对方那条没被读出来——[(..., Me)]
```

⇒ 采错地方时，那条**对方**的消息被判成了 **「我说的」（Me）**
（`classify` 里「在气泡里且是饱和色 = 我的气泡」这一支，采到侧边栏的彩色头像就命中了）。

⇒ 这不只是「读不到」，还会把**对方的话塞进「我方」的语料**（口吻样本、历史）。

## 修法（三处，方向都唯一）

1. **产品路径改走 `chatservant_perceive::read_lines`**：
   画面与倍数由引擎决定，配方**只留一处**。
2. **归类时用消息区裁剪件**（`pane`），与行框同一坐标系。
3. **开销账归到一处**：新增 `perceive::ocr_input_pixels`，
   口径 = **真正送进 OCR 的那张图的面积**（整帧 ×4 或 消息区 ×1）。
   原来在 `watch.rs` 手写的 `frame.width() * frame.height() * OCR_UPSCALE`
   **两处都算错**：2 倍放大是 ×**4** 不是 ×2；PP-OCR 看的是**消息区**不是整帧。
   报成整帧面积 ⇒ 用户以为「调小 ROI 就能省 OCR」，而 ROI 只决定**读哪几行**。
4. **抽成 `read_round()`**：配方写在 `step()` 里面的时候，
   **没有任何机器判据能发现它写错了**——那段代码「看起来」完全合理。
   抽出来之后，「产品路径 ≡ 探针路径」才成为一条可测的判据。

## 守卫（四条）

| 测试 | 位置 | 锁住哪一条 |
|---|---|---|
| `the_product_read_path_hands_ocr_the_view_the_engine_asks_for` | `watch.rs` | 引擎**收到的那张图** = 配方规定的那张；且对方那条真的被读出来、面板上的灰字不进消息流 |
| `the_product_read_path_agrees_with_the_probe_path` | `watch.rs` | 产品路径与 `perceive::read`（**探针那条路**）逐字一致：条数、说话人、正文、位置 |
| `the_watch_layer_does_not_hand_roll_the_ocr_recipe` | `watch.rs` | 生产代码不许自己拼配方（接线层面） |
| `the_ocr_cost_is_the_area_of_the_view_actually_sent` | `perceive` | 开销账 = 真正递进去的那张图的面积；两条路必须不相等 |

### 夹具：侧边栏画成「满的」，不是纯色

⚠ **第一版夹具把侧边栏画成纯色，于是自证 S2 打不动**：
采错地方也一样「干净」⇒ 守卫永远绿 ⇒ 又一条自毁型守卫。

真机上那一列是**满的**（联系人名、头像、消息预览），颜色不统一 ⇒
采错地方时外圈纯度掉到阈值以下 ⇒ 判成「图里的字」。

⇒ 夹具改成**横条纹**。**条纹不是装饰，是让错误看得见。**

### 自证（拆掉修复 ⇒ 对应测试红）

| 组 | 拆什么 | 结果 |
|---|---|---|
| S1 | `read_round` 退回旧配方（整帧 + 2 倍） | 两条守卫**都红**：① 引擎收到 `(1600,1200)` 而不是 `(608,400)`；② 产品路径读到 **0** 条、探针路径读到 **1** 条 —— **与真机症状逐字相同** |
| S2 | `classify_all` 改用整帧 | 两条守卫**都红**：① 「对方那条没被读出来——[(..., Me)]」；② 说话人不同（Me vs Them） |

恢复后：`chat-servant-app` **108 passed**、`chatservant-perceive` **94 passed / 0 failed / 2 ignored**。

## 遗留与边界

- ⚠ **读会话名那一处仍手写着 2 倍放大**（`peer_name_from_header`）。
  它是**另一件事**（读名字不是读消息），本票没动它。
  ⇒ 守卫第三条因此**不能一刀切**禁 `upscaled_nearest`，只禁在 `read_round` 里。
- ⚠ 本票保证的是「配方由引擎决定」+「产品路径 ≡ 探针路径」。
  **真机上 OCR 读得准不准**是另一件事（PP-OCR 在深色主题下的逐字准确率没量过）。
- ⚠ 票 20 的 `Auto` 档真机项（「点一下即发」）**仍未验**——
  它要求真往真人会话**发**一条消息，属于外部可见动作，需要明确放行。
