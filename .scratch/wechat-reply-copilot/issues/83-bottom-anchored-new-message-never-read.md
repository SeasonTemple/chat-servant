# 83: 同一会话里对方来了新消息，面板不更新——底部对齐的窗里，增量 ROI 结构性读不到

**Status:** done（2026-10-23 定位、修复；真机夹具复验通过；三组反向自证）

## 一、现象

微信发来新消息后，**面板不更新**。

⚠ 这是主线 P0（票 18 修的那条）的**同一个症状**，但**根因完全不同**，
所以票 18 的修复（`merge_into_lines` 的间隙判据）**没有也不可能**修好它。

票 18 修的是「**首读**把对方消息判成标题丢弃」——首读完之后面板确实显示 7 条
（真机实测）。但**第二条消息到达时**，面板依然不动。

## 二、量化（2026-10-23 真机夹具复验）

夹具手法见 `AGENTS.md`「『切会话』这类路径怎么在真机上验」：
`CHATSERVANT_FIXTURE=<png>` 每轮重读那个文件 ⇒ **换文件 = 屏幕内容变了**。

两张**真机帧**，同一会话（「小号」），B 帧比 A 帧晚：对方又发了 4 条，
**视口整体上移 265px**（微信底部对齐）。

### 修复前

```text
第 1 圈  roi=Rect { x0: 0, y0: 60,  x1: 856, y1: 587 }  本轮行=14  消息=5
换帧后  roi=Rect { x0: 0, y0: 569, x1: 856, y1: 587 }  本轮行=0   消息=0
         emit readout tick=11 phase=read peer="小号" messages=5
```

⇒ **一条新消息都没进来**（`本轮行=0`），面板停在 5 条。

### 修复后

```text
第 1 圈  roi=Rect { x0: 0, y0: 60, x1: 856, y1: 587 }  本轮行=14  消息=5  本轮新到=0
换帧后  roi=Rect { x0: 0, y0: 60, x1: 856, y1: 587 }  本轮行=17  消息=8  本轮新到=2
         emit readout tick=12 phase=drafting peer="小号" messages=10
```

⇒ 面板从 5 条涨到 **10 条**，且进入了「正在起草」。

### 顺序修复后（最终）

```text
第 1 圈  roi y0=60  本轮行=14  消息=5  本轮新到=5  本轮记到y=Some(569)
换帧后  roi y0=60  本轮行=17  消息=8  本轮新到=5  本轮记到y=Some(567)
        emit readout tick=11 phase=drafting peer="小号" messages=10
```

⇒ `本轮新到` 从 2 变 **5**（真正新增的 5 条对方消息），
且 `本轮记到y` 指向**最新那条**（567），不是旧消息的位置。

## 三、根因：**几何**，不是分类

`xtask perceive` 逐条读出两帧的消息矩形（消息区局部坐标）：

| 帧 | 最后一条的下沿 | 新增的消息在 |
|---|---|---|
| A（早） | **569** | —— |
| B（晚） | 567 | y = **130..567** |

⇒ B 帧新增的那几条**全部落在 569 之上**，而旧增量 ROI 是
`[水位线=569, 消息区底部=587)` ⇒ **空带** ⇒ 一条都读不到。

**为什么会有这个几何**：微信的消息列表是**底部对齐**的 ——
对话变长时**视口整体上移**，最新的那条始终贴在输入框上方。
⇒ 「新消息永远从底部出现 ⇒ 新增带在水位线以下」这条推理**对微信是错的**。

⚠ 而旧代码里还有第二条捷径，**在这个软件上恰恰是最坏情况**：

```rust
// 变的全在水位线以上：滚出旧消息、顶部公告条在滚。一样不读。
Some(prev) if same_pixels(prev, pane, top.max(self.watermark), bottom) => Decision::Quiet,
```

新消息到达时，**变动的正是水位线以上那一段** ⇒ 永远判 `Quiet` ⇒ **连读都不读**。

## 四、修法

**增量判据从「像素行」改成「内容身份」。**

1. **ROI 覆盖整块消息区**（`perceive::stream`）
   —— 底部对齐的窗里没法用像素划出「新增带」；
   而「变没变」仍由**整块逐字节比对**决定 ⇒ **静默期零调用**这条硬约束不受影响。
   ⚠ ROI 变大**不增加 OCR 成本**：`read_lines` 送进 OCR 的本来就是整帧/整块消息区，
   ROI 只决定「读哪几行」（见 `perceive::pipeline::ocr_input_pixels` 的注释）。

2. **「哪几条是新的」由内容身份判定**（`perceive::merge::novel_messages`）
   —— 消息身份 = **说话人 + 正文**。
   ⇒ 「只是滚动、翻出旧消息」也不再算新的 ⇒ **不会对旧消息重复推理**
   （票 82 那类风险被这一条一起关掉）。

3. **「读到哪了」这个位置保留，但不再划 ROI**（`PaneWatcher::commit`）
   —— 它现在是**诊断信息**（打进日志）。
   ⚠ 留着它不是为了兼容，是因为**守卫要能复现旧机制**才能证明自己抓得住回归
   （见第五节）。

### ⚠⚠ 顺序也是承重的：「先算新颖度，再并入流」

第一版把「新颖度」算在了「并入流」**之后** ⇒ 算的时候**本轮消息已经在流里**
⇒ 它们被判成「不新」⇒ **真正新到的对方消息不会触发推理**。

真机夹具实测（那个顺序下）：

```text
换帧后  本轮行=17 消息=8  本轮新到=2   ← 按「先并后算」推算恰好是 2
        emit readout messages=10          ← 面板倒是涨了（merge 干的）
        phase=drafting                    ← 靠两条**旧**消息误触发
```

⇒ 真正新增的 5 条对方消息**一条都没被判成新**，推理反而被两条旧消息触发。

**修法**：两步收进一个生产函数 `absorb_round`（`ui/src-tauri/src/watch.rs`），
**先算后并**的顺序固化在里面。

⚠ **合成帧夹具暴露不了这个**：每一轮都是**新画面** ⇒ 两种顺序结果**一样**
⇒ 守卫假绿。只有「本轮的消息在上一轮之后已经在流里了」才分岔
—— 所以守卫要**连着 absorb 两轮**才测得出来
（`novelty_is_computed_against_the_stream_before_this_round`）。

## 五、守卫与反向自证

| 守卫 | 钉住什么 |
|---|---|
| `perceive::merge::novel_messages` 三条 | 新到的才算新；旧消息重读不算新；同一句正文、说话人不同 ⇒ 两条消息 |
| `perceive::stream::a_bottom_anchored_new_message_triggers_a_read` | 底部对齐的新帧 ⇒ 必须触发读（**两轮形态**：先读完一轮，水位线推进过） |
| `perceive::stream::only_the_ignored_top_band_is_excluded_from_the_diff` | 顶部公告条滚动 ⇒ 不读（与上面那条成对：只放宽顶部会漏新消息，只放宽底部会一直读） |
| `watch::a_bottom_anchored_new_message_survives_the_product_read_path` | **端到端**：旧形态的 ROI 读不到新消息（前提），产品路径的 ROI 读得到（结论） |

### 反向自证

| 组 | 注入的缺陷 | 结果 |
|---|---|---|
| ① | `novel_messages` 不看内容身份（读到的都当新的） | **2 条守卫红** ✔ |
| ③ | `observe` 用 `committed` 划 ROI（旧机制整套装回） | **端到端守卫红** ✔（"产品路径没读到新到的那条：[]"） |
| ④ | `absorb_round` 里改回「先并后算」 | **顺序守卫红** ✔ |

⚠ **反证②（只改引擎层）没红，原因是「守卫量的是谁」**：
旧形态横跨两个 crate（引擎划 ROI → `read_round` 过滤行），
只在引擎层测**抓不住它**（拆掉水位线之后，引擎那一层压根不知道
「水位线以上」是什么）⇒ 守卫必须落在**产品路径**上。
⚠ 守卫还必须**推进水位线**（复现 `step()` 的真实行为），
否则旧机制下 ROI 不收窄 ⇒ **守卫假绿**（这个坑踩过两轮，见提交历史）。
