# 86: 排序那步回查失败 ⇒ 候选整个被替换掉——面板上少显示回复选项

**Status:** done（2026-10-23 真机撞出、定位、修复；一条守卫；真机复验通过）

## 一、现象（真机 22:26，用户发了一条消息之后）

面板**更新了**（主线 P0 闭环 ✓），但**只出了 1 条候选**——起草明明给了 3 条。

```text
22:26:05.227  emit readout tick=1107 phase=drafting peer="小号" messages=9 candidates=0
22:26:08.416  模型调用完成 stage=Judge ms=3256 ok=true
22:26:12.995  模型调用完成 stage=Draft  ms=4577 ok=true
22:26:17.318  模型调用完成 stage=Rank   ms=4322 ok=true
22:26:17.319  WARN 排序里出现了不在候选中的文本，已丢弃
22:26:17.319  WARN 排序里出现了不在候选中的文本，已丢弃
22:26:17.319  WARN 排序里出现了不在候选中的文本，已丢弃
22:26:17.544  emit readout tick=1107 phase=drafted peer="小号" messages=9 candidates=1
```

⇒ 起草 3 条 → 面板 1 条。

## 二、根因：**两份机制叠在一起**

1. `transport.rs` 的 `rank()`：按 order 里的**原文**回查候选，
   **回查失败就把那一项丢掉**（不许凭空造候选——这条规矩本身是对的）。
2. `seam.rs` 的 `turn()`：`ranked` **整个替换** `draft.candidates`。

⇒ 模型给排序时**改写了原文**（加引号/句号/多一个字）⇒ 回查逐字对不上
⇒ ranked 里只剩逐字相同的那几条 ⇒ **替换之后候选就变少了**。

⚠ 「模型改写原文」是**常态**，不是意外：提示词里写了「原样复制候选文本，
不要改写」，而模型**照样改**。⇒ 判据不能建立在「模型会听话」上。

## 三、修法：**排序最多只能改顺序，不能改条数**

- order 里**逐字对得上**的 → 按 order 排；
- order 里**对不上**的 → 记一条 warn（模型改写了原文），**不造新候选**（规矩不变）；
- **order 根本没提到的候选** → 原样补在后面（顺序按起草时的）。

⇒ 候选数**恒等于**起草给的数。

⚠ 顺带修了一个更隐蔽的：旧写法用 `find` 回查，**同一条候选可能被 order 匹配两次**
⇒ 出现重复候选。现在用 `used` 标记，每条候选最多被排一次。

## 四、守卫

`a_rank_that_rewrites_the_text_keeps_every_candidate`（走**产品路径**：
假上游 + `crate::turn`）——order 里一条逐字相同、一条被改字 ⇒ 断言：

- 候选**仍是 2 条**（不是 1 条）；
- 逐字对得上的那条**仍排第一**（否则「保住条数」会退化成「顺序也不要了」）；
- 被改字那条**留下的必须是原文**（不能用模型改写后的字）。
