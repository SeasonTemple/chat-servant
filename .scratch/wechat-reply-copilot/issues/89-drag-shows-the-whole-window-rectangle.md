# 89: 拖动窗口时看到的是**整个窗口矩形**——那是 Windows 原生拖动的轮廓

**Status:** done（2026-10-24 用户报出 + 截图 ⇒ 定位 ⇒ 改法 ⇒ 待真机复验）

## 一、现象（用户原话 + 截图）

> 「目前窗口拖动时看到的窗体还是原本的矩形，能否处理？」

截图上：纸的撕边是清楚的，但**外面套着一个细白矩形框**（从左上到右下）。

## 二、根因：**原生标题栏拖动**

拖动带用的是 Tauri 的 `data-tauri-drag-region`
（`ui/src/lib/PaperPanel.svelte` 的 `.cs-topbar`）⇒ 它走的是
**Windows 原生标题栏拖动**（`WM_NCLBUTTONDOWN` + `HTCAPTION`）
⇒ **Windows 自己画一个矩形拖拽轮廓**
⇒ 透明窗口的轮廓 = **整个窗口矩形**（撕边是**内容**的形状，轮廓是**窗口**的形状）。

⇒ 也就是说：**那个矩形不是我们画的，是系统的** ⇒ 改 CSS 改不掉它。

## 三、改法：**不用系统的拖动，自己搬窗口**

- 前端：拖动带改成**自己的指针处理**
  （`onpointerdown/move/up` + `setPointerCapture`），
  把**指针在屏幕上的位移**发给 Rust；
- Rust：新增 `commands::drag_window_by(dx, dy)` ⇒ **直接搬窗口**
  （`position()` + `scale_factor()` → `set_position()`）⇒
  **系统的拖动机制压根没启动** ⇒ 没有轮廓。

### ⚠ 两个坑（写下来免得再踩）

1. **位移必须取 `screenX/screenY`，不能取 `clientX`。**
   窗口一动，**指针下方的内容也跟着动** ⇒ `clientX`（相对窗口的坐标）
   **几乎不变** ⇒ 用它算位移 ⇒ **窗口原地不动**。
   `screenX` 才是鼠标真的走了多远 ⇒ 窗口 1:1 跟着走，
   且指针下的内容点保持不变（与原生拖动手感一致）。
2. **逻辑 px → 物理 px 要乘 `scale_factor`**（本机 125%）
   ⇒ 不乘的话窗口会「跟不上」指针。

### 顺带：ACL 少一条权限

`core:window:allow-start-dragging` 现在**没有调用方**了
⇒ 删掉（留着它 = 留一个「以后谁又挂上 `data-tauri-drag-region`
也不会被发现」的口子）⇒ `capabilities/default.json` 的描述里记着这件事。

## 四、代价（说清楚）

- **失去 Windows 的边缘吸附**（拖到屏幕边缘自动贴边）——自绘拖动没有这套。
- **多一层 IPC**：每个 `pointermove` 发一次（每次只是挪一下窗口，很轻）。
- 演示态（`IS_DEMO`，没有 Tauri）⇒ `invoke` 失败被吃掉 ⇒ 演示页拖不动（那里也不需要）。
