# ADR-0002：帧调理管线的顺序，以及为什么不做"降噪"

- 状态：已接受
- 日期：2026-10-06

## 背景

原始问题：「在截图交给 OCR/VLLM 前，应该通过一个工具来降噪以降低识别开销？」

这个问法里隐含一个假设：开销主要来自**噪声像素**，把噪声去掉就省了。
这个假设在神经 OCR 和 VLM 上是**错的**。需要先把成本模型摆正。

## 成本模型

**视觉 token 成本与图像面积成正比。**

以 Qwen2-VL 为例（**举它是因为它的参数是公开的，不代表本项目选它**）：
它把图像缩放到边长为 28 的倍数，ViT 切 14×14 patch，
再由 patch merger 把 2×2 合并成一个 token —— 所以**一个 visual token
覆盖 28×28 = 784 像素**。

| 图像 | 视觉 token |
| --- | --- |
| 1024×1024 | 1369 |
| 512×512 | 361 |
| 256×256 | 约 100 |

token 数对**面积**线性、对**边长**二次。宽度给到两倍，token 花四倍。

这条规律是 ViT 系视觉模型的通性，不依赖具体厂商：分块尺寸不同，
但"成本随面积线性增长"这条不变。本项目**不绑定任何一家模型**，
预算是一个抽象的"视觉 token 数"，在接具体模型时才换算成它的参数
（不同厂商的参数名不一样：有的叫 `max_pixels`，有的叫分块上限，
有的直接给"最多几张图/多大图"）。

由���得到本 ADR 的核心结论：

> **省开销的唯一有效手段是"少送像素"，不是"把像素弄干净"。
> 一张被噪声糊住的干净小图，比一张干净的整屏大图便宜两个数量级。**

`min_pixels` / `max_pixels` 直接以 token 数表达（`256*28*28` = 256 token，
`1280*28*28` = 1280 token），所以"送多大"是一个可以用 token 直接算的决策，
不是一个模糊的"画质设置"。

## 决策

建立一个独立的 `FrameConditioner`。

**它要做的事其实只有一件：在不影响文字可读性的前提下，少送像素。**
下面的五级不是五个独立目标，而是"少送像素"的五种不同手段，按杠杆排序：

| 手段 | 作用 | 收益 | 是成本还是准确率 |
| --- | --- | --- | --- |
| 1 变化门控 | 帧没变就一点都不送 | ~100× | 成本（消除调用） |
| 2 增量 ROI | 只送水位线以下的新增带 | 10–50× | 成本（缩小面积） |
| 3 语义遮罩 | 抠掉头像/表情包/时间戳等 | 3–10× | **准确率为主**，省成本是副作用 |
| 4 尺度归一 | 缩到模型预算内 | 2–4× | 成本（缩小面积） |
| 5 几何规整 | 贴边裁剪 | <20% | 成本（缩小面积） |

**第 3 级是唯一一个主要目的不是省成本的级别。** 抠掉噪声区域的首要收益是
"不把头像里的字当成对方说的话"；它顺带减少了要送的面积，那只是副产品。
把它和其余四级并列成"降噪五级"会掩盖这个区别——早期版本正是这么写的，
导致第 3 级的验收标准被写成了成本指标而不是识别正确率指标。

### 1. 变化门控（收益 100×）

只在帧内容真正变化时才继续。WGC 每秒送若干帧，但聊天窗口大部分时间是静止的。
比较对象是**上一帧的 `ChatPane` 区域**，不是整帧。

聊天场景还有一个更强的约束：参考项目已经实测到，公告条会滚动，
把它算进 diff 会导致画面**永远停不稳**。所以门控必须只看消息区，
且排除会自己动的区域。

### 2. 增量 ROI（收益 10–50×）

新消息**永远从底部出现**。维护一条"已提交水位线"（watermark），
每帧只对水位线以下的新增带做识别，已识别的部分不重跑。

这一级的收益依赖第 1 级先把静止帧挡掉。两者是配套的。

**不要自己写脏矩形。** `windows-capture` 的 `DirtyRegionSettings` 原生提供
变化区域（见 ADR-0003），第 1、2 级应该建立在它的回调之上。
自己实现比较像素差不仅多一份代码，还会在缩放、动画、
多显示器 DPI 变化这些场景下重复踩坑。

### 3. 语义遮罩（收益 3–10×）

#### 占用判据不能用「异于面板底色」

这一级里有两个不同的判据，**不能共用一个思路**：

- **平直度**（精确色种数）在**图片**上很灵：平表面 1~2 种，图片 830~2658 种。
- **占用**（「这一条异于面板底色」）在**图片**上很钝：照片内部那些只有 3 种色的
  深色背景与面板底色 `rgb(30,30,31)` 几乎一样，于是被判成**空带**，区域被
  切碎、每片都够不到最小尺寸，**整张图漏检**。

真实帧实测（`target/probe/text-chat.png`）：换成「该条是否**不平直**」之后，
检出从 0 个变成 4 个，其中一条与独立测量（`scripts/scancol.ps1`）吻合。

这与本 ADR 开头记的「图片区 51% 纯黑背景」是**同一个病根**：
一张大片深色背景的图片，对「异于底色」天然隐形。

#### 区域级检测（`perceive::media`）

遮罩是**逐行**的，对「OCR 一行字都没读出来」的图片完全看不见——实测帧里
对方发的那张照片就是如此。所以还需要一层**区域级**检测把「这里有一张图」
这件事记下来。

**最坏情况已实测排除**：真实帧上文字行/归并消息是 **11~12 px 高、整块约 30 种色**，
而检出的候选是 **84~120 px 高、830~2658 种色**——高度差 7~10 倍、色种数差 28~88 倍。
所以「候选其实是文字气泡」这一类可以排除；剩下的未知只是卡片/链接预览/
引文块会被归成 `Photo`，而那**都是对方发来的视觉内容，不是私密文字**。

> 顺带一条否定结果：**彩度不能用来区分照片与卡片**。实测确认是照片的那条
> 彩度均值只有 1.7、59% 是纯灰，而另外三条是 18.9~32.6。这张照片本身
> 就是近灰度暗图，所以「照片有彩色」这个前提在本帧上不成立——真加一道
> 彩度闸会把真照片挡掉。**判据要能在已知为真的那一类上量出量级差**，
> 而不是靠人眼分辨。

丢掉根本不是消息的区域：头像、表情包、图片里的文字、时间戳、引用块、
群里的发言人名、链接卡片、置顶公告、系统提示。

这才是"降噪"在本产品里的真正含义 —— **不是把像素磨干净，是把不该读的东西
从图里抠掉**。它同时降低 token、降低误识别、降低延迟，三头收益。

判定依据见参考项目已实测的规则，可以直接继承假设、再在 Rust 里重新标定：

- 框内众数颜色占比 < 45% → 文字落在不平底色上 → 图片里的字（头像、照片、表情包）
- 底色 == 自己的气泡色 → `Me`
- 文字对底色对比度 ≥ 150 → `Them`；其余（80–95）→ 灰字 → 过滤
- 字号显著小于首帧中位数（< 0.6×）→ 图片消息里的字 → 过滤

### 4. 尺度归一（收益 2–4×）

归一到模型最优区间：按 DPI 缩放到逻辑布局，再按 token 预算缩放。
125%/150% DPI 下同样的逻辑布局在物理像素上是 1.5–2.25 倍面积，
不归一就是白送 2–3 倍 token。

注意方向：**大图要缩到预算内，小图不要盲目放大**。

#### 两条计费公式（抄自供应商文档，不是猜的）

`core::scale` 只认这两个形状，因为两家的公开文档就是这么定义的：

| 供应商 | 形状 | 公式 |
| --- | --- | --- |
| Anthropic | patch | 28×28 px = 1 视觉 token，`⌈w/28⌉ × ⌈h/28⌉`；标准档上限 1568 |
| OpenAI tile | 底账 + tile | `base + ⌈w/512⌉ × ⌈h/512⌉ × per_tile`；`gpt-4o-mini` 是 **2833 / 5667** |

来源：
<https://platform.claude.com/docs/en/build-with-claude/vision>、
<https://platform.openai.com/docs/guides/images-vision>。
测试用 Anthropic 自己表格里的三行复算（200×200→64、1000×1000→1296、
1092×1092→1521），不是拿自己的推断当自己的事实。

**`gpt-4o-mini` 的底账 2833 与图的大小无关**——一个 64×64 的表情包和一张
1200×1200 的照片底账一样。这有两个后果：

1. 预算低于底账时**无解**。这时要**如实告诉用户**，不能悄悄发一张然后超支。
2. 视觉链路的选型不该由「哪个模型便宜」决定。默认档模型 B 是
   `gpt-4o-mini` 时，每轮光图片就 2833 起。

**滑块上界必须按供应商给。** 早先把它写死成 1568（Anthropic 的上限），
于是在 `gpt-4o-mini` 上滑块永远到不了 2833——图片功能在默认模型上完全
不可用，而界面上看不出任何异常。判据：**上界必须 ≥ 该供应商的底账**，
否则那是用户永远解不开的死结。
放大不增加信息量，只增加 token。

### 5. 轻度几何规整（收益 < 20%，最后做）

- 贴边裁剪到紧贴文字的 `Bubble`
- 背景合成到纯色（去掉头像等透明叠加）
- 灰度化（仅当下游是无彩色特征的匹配器时）

## 明确**不做**的事

这是本 ADR 最重要的部分。以下操作在传统图像预处理里常见，但对**神经**识别
是负收益或零收益，放进管线只会引入 bug：

| 做法 | 为什么不做 |
| --- | --- |
| 高斯/双边模糊降噪 | 抹掉抗锯齿边缘。神经 OCR 的检测器正是靠边缘定位文本框，先糊后识会降低召回。 |
| 二值化 / Otsu / 自适应阈值 | 丢掉灰度过渡，把粗体、彩色文字、抗锯齿直接损伤。对**传统** OCR 有用，对 DB/Paddle 类检测器是净损失。 |
| 锐化 / 去噪后再放大 | 放大不产生新信息，只放大噪声并线性增加 token。 |
| 去色 / 直方图均衡 | 颜色是第 3 级语义遮罩的**判据**（气泡底色区分 Me/Them）。先转灰度等于把判据扔掉。 |
| 形态学开闭运算做文本行分割 | 这类操作能把噪声压掉，但也可能把相邻行的字粘成一团，制造**假的多行**。ROI 由第 2 级给出，不需要形态学猜。 |

**如果下游换成传统模板匹配或 Tesseract 管线，第 5 级应该反过来做二值化。**
这个判断依赖于"下游是神经网络模型"这个前提，改下游就要重评。

## 备选方案

### A. 不做调理层，直接把整屏喂 VLM

最省事。代价：整屏 2560×1440 ≈ 4.1 万 token（远超多数 VLM 的 `max_pixels`，
会被强制压缩，效果反而更差），且每条消息都要重新读一遍全屏。
参考项目的判断链路已经是两次模型调用，再叠上这个成本不可接受。
**否决。**

### B. 只做变化门控，不做其余四级

成本最低的改法，对静态聊天窗口有效。但滚动、切会话、大图消息、
高 DPI 这几种情况仍会退化成整屏识别。**作为第一期落地可以，作为终态不够。**
**部分采纳**：按 M1→M5 分阶段实现。

### C. 跳过 OCR，全程交给 VLM 读图

省掉整个调理层和 OCR 引擎。但失去三样东西：零 token 的常驻轮询能力、
逐条的 `Attribution` 可解释性（调试视图要靠它）、以及离线可用性。
而且轮询场景下 VLM 成本随帧数线性增长，OCR 只在 1、2 级命中时才付费。
**否决** —— 但保留 `VisionBridge`：仅在**用户选的回复生成模型是纯文本 LLM**
时，作为它的可选视觉补充，处理**对方发的图片消息**那一小段 `Bubble`，
而不是整个窗口。回复生成模型本身具备视觉能力时，这条链路完全不存在。

## 影响

- `FrameConditioner` 是独立 crate，有自己的单元测试，用录制下来的真实帧做夹具。
- **每级的验收标准必须按它到底是成本还是准确率来写。**
  成本级的验收是"送的像素/token 变少了"；准确率级的验收是
  "头像里的字不再被当成消息了"。用同一个指标衡量全部五级，
  会让第 3 级被优化成一个纯粹的省钱步骤，而它真正的价值在别处。
- 每一级的**拒绝理由**也进调试视图：某个区域为什么没被送进识别。
  只有一个总耗时数字的话，识别不对时无法定位是哪一级的问题。
- 第 1、2 级建立在 `windows-capture` 的 `DirtyRegionSettings` 之上，不自己实现
  脏矩形逻辑（见 ADR-0003）。
- token 预算是一个**模型无关的抽象值**（单位就是视觉 token 数），接具体模型时
  才换算成它家的参数。设置里给"识别精度/成本"一档滑块，底层就是这个数字。
  它可以直接换算成钱，所以界面上要显示数字，不是只显示"高/中/低"。

## 补记（2026-10-07）：OCR 的输入不能是裁剪后的消息区

### 现象

对方发了一条只有一个「乐」的气泡（19x19 px 白字灰底）。整条链路读不到它，
于是产品把对方说的话整段丢掉——**这直接命中核心功能**。

### 两个独立的必要条件

用 `cargo xtask ocr <帧.png> --scale N`（只跑 OCR，不锚定不归类）
做了对照实验，源图是真实帧 1161x893：

**条件一：必须放大。** 所有配置下 1x 一律读不到。

```text
整帧 1x   26 行  无「乐」
整帧 2x   40 行  有「乐」
整帧 4x   32 行  有「乐」   （4644x3572，没撞上尺寸上限）
```

**条件二：左侧必须有真实文字上下文。** 同一帧、同为 2x，
只改裁剪的左边界：

```text
裁剪 x0=0    （含侧边栏）2x -> 有「乐」
裁剪 x0=190  （含侧边栏）2x -> 有「乐」
裁剪 x0=210  （含侧边栏）2x -> 无「乐」
裁剪 x0=304  （纯消息区）2x -> 无「乐」   <- 原来是这一档
```

排除掉的解释：**不是**图像太窄（右补 400 px 无效），**不是**离左边缘太近
（左补 400 px 无效），**不是**贴底边（下边界放到 760 无效），**不是**紧框问题
（紧贴气泡的小框在任何倍数、任何位置都读不到）。补白一律无效，
必须是**真实文字**才起作用。

⚠ **机制至今未查清。** 数据只支持「放大 + 左侧文字上下文」两个条件同时成立，
这是按实测兜住的行为，不是按原理推导出来的结论。

### 决策

OCR 的输入改成**放大 2 倍后的整帧**，读出来的行坐标换算回消息区坐标系，
并**丢掉与消息区没有重叠的行**。

丢行这一步不可省：OCR 现在吃整帧，侧边栏的联系人名、标题栏、输入框里
用户自己打的字全都会被读出来。联系人名混进消息流，产品就会凭空
「听到」并不存在的话——那是正确性事故，不是精度问题。

代价：OCR 输入变大、变慢（223ms -> 480ms）。但变化门控保证只在画面
**变化**时才 OCR，静默期不付这份成本。

### 方法论

`xtask e2e` 原本**自己复制了一遍**「裁剪 + OCR」，产品管线改了它不跟着改，
于是探针还在测一条已经不存在的旧路，并且报出「归类阈值失效」——
把排查方向指到了完全错误的地方（真实原因是 OCR 根本没读到那一行）。

这与 ADR-0004 里记的「`probe frame` 默认路径指向坏实现」是同一类病：

> **诊断命令必须和产品走同一条代码路径，否则它证明不了任何事。**
> 探针复制生产逻辑的那一刻，它就开始撒谎。

已把取文本框这段抽成 `read_lines`，产品管线与端到端探针共用同一个入口。
