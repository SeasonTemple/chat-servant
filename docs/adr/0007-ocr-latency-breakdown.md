# ADR-0007：OCR 延迟拆分、冷启动澄清、tiny vs small、线程配置

- 状态：**已出数**（2026-10-17 实测）。**其中「最优线程数」是这台机器上的结论，不是通用结论**——换机器必须重测。
- 日期：2026-10-17
- 取代：无。ADR-0006 仍然有效，本 ADR 只做**加法**：把 0006 里「B 的延迟构成未知」「冷启动口径可疑」这两个未验证项填上。
- 相关：ADR-0006（引擎选型）、ADR-0003（依赖策略）
- 口径继承：放大倍数、规范化、编辑距离、配对规则全部沿用 `scripts/ocrbench/bench_lib.py`，**本轮不重新定义尺子**。

## 背景

ADR-0006 结束时有三个悬着的问题，本轮就是来填它们的：

1. **延迟构成未知**：只量到「818~897 ms」这个端到端总数，不知道钱花在哪一环。
   而这直接决定优化该往哪使劲——如果大头在图像处理，调 `limit_side_len` 有意义；
   如果大头在 ONNX 推理本身，那就只能换模型或换线程，加图像预处理是白费力气。
2. **冷启动口径可疑**：上一轮报过「冷启动 602 ms、稳态中位 897 ms」——
   **冷比热快**，物理上说不通。当时的假设是「RapidOCR 在构造时就建好了会话，
   所以第一次推理其实是热的」。这个假设**方向反了**，见下面「冷启动澄清」。
3. **PP-OCRv6 只有 small 一档**：官方 tiny 约是 small 的 1/3 耗时，
   但换速度要付多少准确率没量过。

⚠ **放大倍数本轮全部固定 1×。** 0006 已实测：PP-OCRv6 small 在 1× 已零漏检
（两帧真帧 7/7、10/10），2× 只是更慢。⇒ 再动倍数就是同时动两个变量，无法归因。


产物：`target/probe/ocrbench/latency-breakdown-small-t-1.json`

| 阶段 | wechat-chat 855×545 中位 / P95 (ms) | gws-chat 865×545 中位 / P95 (ms) |
|---|---|---|
| 预处理（LoadImage + 限边缩放） | **0.0** / 1.5 | **0.0** / 0.2 |
| **det 纯推理** | **337.2** / 539.4 | **405.1** / 570.7 |
| det 预处理 + DB 后处理 | 38.8 / 61.5 | 36.1 / 263.7 |
| det 裁剪（透视切图） | 19.4 / 21.4 | 22.2 / 31.3 |
| **cls 纯推理** | 7.1 / 186.1 | 8.1 / 113.1 |
| **rec 纯推理** | **398.4** / 531.4 | **331.4** / 867.1 |
| rec 缩放归一 + CTC 解码 | 6.4 / 9.0 | 9.1 / 12.4 |
| 后处理（框回映射 + 空串过滤） | **0.2** / 0.3 | **0.3** / 1.3 |
| 端到端 `engine(arr)` | **700.3** / 1360.9 | **984.5** / 1229.1 |
| 噪声幅度 (max−min)/中位 | 107.2% | 75.5% |

### 这张表能回答的：「818 ms 花在哪一环」

**95% 以上在两次 ONNX 推理里。** 两帧加起来，
det 推理占端到端的 47%/41%，rec 推理占 57%/34%；
图像预处理 0.0 ms、结果后处理 0.2~0.3 ms，**加起来不到 0.5%**。

⇒ **推论（对本项目直接有用）**：ADR-0006 里那条
「先降 `Det.limit_side_len` 强升采样，看能不能压进 TICK」的假设，
**按本表看是在打空气**。降 `limit_side_len` 改的是 det 的**输入尺寸**，
那确实能减少 det 推理量——但它治不了 rec，而 rec 本身占 34%~57%。
真要压延迟，可动的只有三处：**换更小的 rec 模型、线程配置、量化**。

### 两处方法学上的坑（都已修，写在这里防止下一个人重犯）

1. **`rapidocr` 没有对外的分阶段计时接口**，但 `RapidOCR.__call__` 的函数体只有六步，
   本轮逐字照抄这六步并各自计时。三个 ONNX 会话的纯推理时间由
   `OrtInferSession.__call__` 上的计时壳给出——那是 det/cls/rec **唯一**的推理入口，
   不会有漏网的路径。
2. **等价性自检不能比耗时**。第一版用「逐段求和 vs 原生 e2e 差 < 3%」当判据，
   直接失败（669 vs 1029 ms，差 35%）。查下来**不是抄错了函数体，是这台机器的噪声就有 ±50%**。
   ⇒ 自检改成**语义等价**：逐段路径与原生路径的 `boxes`/`txts` 必须逐项相同。
   输出相同就说明走同一条代码路径；耗时差只可能是机器噪声。
   墙钟偏差仍然报在 `wallclock_drift_pct`（27.0% / 14.6%）里，**不藏，但不当判据**。
   ⇒ 另外逐段与原生**交替**采样（每轮顺序对调），否则「谁先跑」会系统性偏便宜。

## 冷启动澄清

### 结论：真正的冷启动 = **构造 10.9 ms + 会话建立 317.3 ms = 328 ms**，之后才是推理

实测（同一进程内分段计时，`latency_breakdown.py`）：

| 段 | 实测 | 说明 |
|---|---|---|
| `RapidOCR(params=...)` 构造 | **10.9 ms** | 几乎不花钱 |
| 会话建立 det | **102.4 ms** | 惰性 |
| 会话建立 cls | **102.0 ms** | 惰性 |
| 会话建立 rec | **112.9 ms** | 惰性 |
| **会话建立合计** | **317.3 ms** | |
| 建立后第一次推理（wechat-chat） | **1158.9 ms** | 检出 8 框 / 7 真值行 |
| 建立后第二次图的首推（gws-chat） | **861.2 ms** | 检出 10/10 |

### 「我上轮那个数为什么反常」——明确结论

**两处错叠在一起，都不是 RapidOCR 的问题：**

1. **假设方向反了。** 上一轮以为「RapidOCR/ONNX Runtime 在构造引擎时就已经建好了会话，
   所以第一次推理其实是热的」。实测 `rapidocr/main.py:70-80`：
   `__init__` 里 `self.text_det = None`、`self.text_cls = None`、`self.text_rec = None`——
   **一个模型都不建**，三个会话都是首次 `__call__` 里由 `_load_det_model()` /
   `_load_cls_model()` / `_load_rec_model()` **惰性**建立的。
   ⇒ 那个「冷启动」**是真的冷**，只是被贴错了标签。
2. **标签本身贴错了。** `route_b_on_real_frame.py:89-93` 打完 3 次调用后
   `times.sort()`，然后把 `times[0]` 印成 `cold`。
   **那是 3 次里的最小值，不是第 1 次。** 于是报出去的是「最快的那一次」，
   必然低于同批的中位数——**602 < 897 完全是这么来的，与冷热无关。**

⇒ **这个脚本的 `cold` 字段目前是错的**（打印的是最小值）。
本轮不改它（本轮的文件所有权不含它，且改了会动上一轮的产物口径），
**但凡是引用过那个 602 ms 的地方都应该作废**。修正方式见「留下的坑」。

### 顺带查出一条可省的钱（未实测，只作为线索）

`use_cls` 默认是 `true`，所以冷启动会建**第三个**会话（102.0 ms），
而每帧稳态还要跑一次方向分类（7~8 ms）。
本项目的输入是**正立的微信窗口截图**，方向分类没有可纠正的对象。
⇒ `Global.use_cls: false` 理论上能省下 102 ms 冷启动 + 7~8 ms/帧。
⚠ **这只是读配置得出的推断，本轮没有实测，不作为结论。**

## ONNX Runtime 线程配置

**先确认图优化已开启**：`inference_engine/onnxruntime/main.py:82`
把 `graph_optimization_level` **硬编码**成 `ORT_ENABLE_ALL`，
没有开关也不需要配——所以这条不是变量，是既定事实。
真正能动的只有 `intra_op_num_threads`。

命令（每档一个独立进程，因为 `SessionOptions` 在建会话时就定死了）：

```
foreach ($t in 1,2,4,8) {
  target\bench-venv\Scripts\python.exe scripts\ocrbench\latency_breakdown.py `
      --model small --threads $t --repeat 10 --warmup 3
}
```

| intra_op | wechat 中位 / P95 (ms) | 噪声幅度 | gws 中位 / P95 (ms) | 噪声幅度 | 两帧合计 |
|---|---|---|---|---|---|
| 1 | 1464 / 1514 | 5% | 1555 / 1621 | 6% | 3019 |
| 2 | 860 / 870 | 4% | 902 / 931 | 6% | 1762 |
| **4** | **559 / 570** | **7%** | **596 / 619** | **9%** | **1155** |
| 8 | 1265 / 1923 | 87% | 1353 / 1729 | 73% | 2617 |
| 默认 `-1`（ORT 自选） | 700 / 1361 | 107% | 984 / 1229 | 76% | 1685 |

### 结论：**这台机器上的最优值是 4**

- 比 ORT 默认**快 1.46×**（两帧合计 1685 → 1155 ms），
- 而且**噪声幅度从 107% 降到 7%**——这不是巧合：默认档在 12 逻辑核上开满线程，
  与常驻后台负载互相抢核；收到 4 之后既快又稳。
- **8 线程反而掉回 2617 ms 且立刻失稳（73~87%）**：本机只有 **6 个物理核**，
  8 已经超订阅，再叠上动画壁纸/Chrome/微信就崩。
- 1/2/4 三档都很稳（4~9%），**≥8 立刻失稳**。这个转折点与物理核数一致。

⇒ **可操作的一条：显式设 `EngineConfig.onnxruntime.intra_op_num_threads = 4`，
不要用 ORT 默认。**
⚠ **这是本机结论。** 换机器必须重测，且大概规律是「物理核数的 2/3 附近」，
但「大概」不是数字，别拿它当结论。

⚠ 顺带记一个**没动**的旋钮：rapidocr 自带配置里
`EngineConfig.onnxruntime.enable_cpu_mem_arena: false`。
本轮遵守「一次只动一个变量」，没有改它，所以它的影响完全未知。

## tiny vs small

### 权重出处（可复现，带校验）

`scripts/ocrbench/fetch_tiny.py` 从**本机 venv 里 rapidocr 3.10.0 的
`default_models.yaml`**（官方模型表）取 URL 与 SHA256，不在脚本里硬编：

| 文件 | 大小 | SHA256 | 核对 |
|---|---|---|---|
| `PP-OCRv6_det_tiny.onnx` | 1.83 MB | `f42c0fbd294d95eac1a550e131b277dac97462c8025fa4b6c3cec1b7894bd3d5` | **与官方表一致** |
| `PP-OCRv6_rec_tiny.onnx` | 4.49 MB | `e16e242de5937ad92609223f19bc2aff3727ee40b095f996907c24749bad251b` | **与官方表一致** |
| `ppocrv6_dict.txt` | 74.9 KB | `b5f2bfe2bdd9448429e3e82b51c789775d9b42f2403d082b00662eb77e401c5d` | 与 small 共用同一份 |

small 侧那两个权重的 SHA256 本轮也重核了一遍，**与官方表逐字节一致**。

### 复核过那一条漏检（`scripts/ocrbench/verify_det_miss.py`，只报 y 不报文本）

tiny 在 wechat-chat 上**连跑 3 遍都漏 y=185**，框清单显示它**少给了一个框**：

```
tiny  框(y0,y1,h) = (71,138,67) (231,253,22) (289,307,18) (343,364,21) (399,421,22) (456,476,20) (512,532,20)
small 框(y0,y1,h) = (71,138,67) (178,193,15) (232,252,20) (289,307,18) (344,362,18) (398,420,22) (456,476,20) (512,532,20)
                                                                        ^^^^^^^^ tiny 没有这个框
```

漏掉的是一条**框高 15px 的短行**（其余命中行框高 18~22px）。
所以这是 **det 的灵敏度差异**，不是配对判据或行组装的问题。

### 「tiny 换来的速度，代价是掉了多少准确率，值不值」——**不值（当前不可替换）**

三条理由，按重要性排：

1. **差异只出现在真帧上，而真帧正是产品的输入。** 两档在 60 张合成语料上
   都是 0.00% 漏检，**零区分力**；一进真帧 tiny 就少一条。
   ⇒ 现有语料**不能**用来判这一档，把它当依据是危险的。
2. **漏的是短行。** 短消息（「好」「嗯」「收到」）是聊天里最常见的形态，
   而漏掉一条消息对这个产品是直接的功能缺失，不是精度打折。
3. **2.6× 提速是真的**（306 vs 789 ms），但拿「偶尔看不见一条消息」换它不划算。

⚠ **样本量必须说清：2 帧、1 条漏检。**
这**不足以**外推成「tiny 必然漏检」，但**足以**否掉「tiny 可以直接替换 small」。
⚠ 本对照固定在 ORT **默认**线程下做的（对称才可归因），
所以 `tiny @ 4 线程` 的真实延迟**未知**，只会更低。

## ⚠ 2026-10-18 订正：上面那条结论**归错了因**，「tiny 不值」要改成「tiny 的 det 不值」

上一节比较的是「tiny 全家」对「small 全家」——**det 和 rec 一起换了**，
所以那次实验根本没有分离出「是小 det 漏的」还是「是小 rec 漏的」。
而 ADR-0007 自己列的未做项里就有 `det=small + rec=tiny` 混搭，
**它一直没人跑**。

跑了（`scripts/ocrbench/hybrid_compare.py`，1×，ORT 4 线程，
两张真帧各 5 遍取中位，报 `n/N` 与 `P95`）：

| 组合 | det | rec | cls | 帧1 检出 | 帧2 检出 | 帧1 ms | 帧2 ms | 合计 |
|---|---|---|---|---|---|---|---|---|
| A 基线 | small | small | 开 | 7/7 | 10/10 | 613 | 722 | 668 |
| **B 混搭** | **small** | **tiny** | 开 | **7/7** | **10/10** | **571** | **576** | **573** |
| C 关 cls | small | small | 关 | 7/7 | 10/10 | 586 | 599 | 592 |

⇒ **B 是三者里最快的，而且一条都没漏。**
把 tiny 换成 **rec** 单独使用，拿到了 2.6×→1.17× 的提速（668→573 ms），
**零检出代价**；而 tiny 的代价**全部来自 det**——
它「稳定漏 y=185」那一帧，根因是 det 灵敏度，不是 rec。

⚠ **所以本 ADR 上一节「tiny 不值（当前不可替换）」要按这个读**：
不可替换的是 **det=tiny**，**rec=tiny 是好的**。
这条订正的前提是它当时没把 det 单独固定住——
**「A 差于 B ⇒ 某个部件不好」推不出「是哪一个」，而两个部件一起换只能得出「别一起换」。**

另有一条顺带的数：`use_cls: false` 在这两帧上省 **76 ms**（668→592）、
检出不变。⚠ 但**没有测过竖排/倒置的图**，而 cls 正是管方向的——
微信聊天里用户可以发旋转过的图片，**未测就等于风险未知，不要据此关掉**。

## 结论（2026-10-17，四项都拿到数之后）

1. **延迟的 95% 以上在两次 ONNX 推理里**：det 推理占端到端 47%/41%，
   rec 推理占 57%/34%；图像预处理 **0.0 ms**、结果后处理 **0.2~0.3 ms**。
   ⇒ **优化只能从「模型规格 / 线程 / 量化」三处入手。**
   ⚠ ADR-0006 留下的那条「先降 `Det.limit_side_len` 强升采样看能不能压进 TICK」
   ——它只能压 det 那一半，**治不了占一半以上的 rec**。该假设按本表看是半个错法。
2. **真冷启动 = 构造 10.9 ms + 会话建立 317.3 ms = 328 ms**，之后才是第一次推理
   （1159 ms）。上一轮那个「冷启动 602 ms」是 3 次调用的**最小值**，标签贴错，**作废**。
3. **线程最优 = 4**（本机）。比 ORT 默认快 **1.46×**，噪声从 ±107% 压到 ±7%。
4. **tiny 暂不替换**：速度 2.6×，但真帧漏一条短行，且现有语料对它零区分力。
5. **顺带解掉 ADR-0006 的一个悬案**：small + 4 线程在两帧上是
   **559 / 596 ms**（P95 570 / 619 ms），**两帧都在 `TICK = 1000ms` 内，余量 44% / 40%**。
   ⇒ ADR-0006 里「B 跑不进 TICK」的那个担忧，**在 1× + CPU 推理 + 4 线程下已不成立**。
   ⚠ 只在这三个前提下成立；换机器或接上 GPU 都要重量。

## 复现

```bash

# 线程扫描（每档一个独立进程）

# tiny vs small
target\bench-venv\Scripts\python.exe scripts\ocrbench\model_compare.py --model tiny
```

## 没做到的部分（逐条列，不许用近似值冒充）

1. ~~**没有测 `Global.use_cls: false`**~~ → **2026-10-18 已实测**：
   两帧上省 76 ms（668→592 ms）、检出不变。但**竖排/倒置图仍未测**，
   而 cls 管的就是方向，所以**不据此关掉它**。
1b. **`hybrid_compare.py` 的键名必须写 `EngineConfig.onnxruntime.*`**：
   写成 `Global.intra_op_num_threads` 会被 rapidocr 直接 `ValueError` 拒掉，
   而且是**第一次跑就崩**，不会静默用默认值——这点比报错本身更值得记。
2. **没有测 tiny @ 4 线程。** tiny 对照固定在默认线程下（对称才可归因），
   所以 tiny 的最优延迟未知。
3. **没有测 `inter_op_num_threads`**，也没测非 2 的幂次（如 3、6）。
   ORT 默认不启用并行图执行。
4. **完全没碰量化（INT8/FP16）。** 而这是唯一可能把**占一半以上的 rec**
   也压下去的手段——按结论 1，它才是真正对症的那一枪，本轮缺席。
5. **没有测「det 留 small + 只把 rec 换成 tiny」这种混搭。**
   而这恰恰是最可能「拿到 tiny 的速度又不丢检出」的组合——
   因为观察到的那条漏检是 **det** 造成的，不是 rec。本轮只做了整档替换。
6. **没有修 `route_b_on_real_frame.py` 的 `cold` 标签**（结论 2 已指出它是错的）。
   本轮文件所有权不含它，需要父代理裁决是否改口径。
7. **没有在安静机器上复测。** 本机常驻动画壁纸 + Chrome + 微信，

8. **tiny 的漏检样本量只有 2 帧 1 条**，见上文。
