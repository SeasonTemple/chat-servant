### A/B 对照：同一个循环，只差一行 `rewind()`

点不动微信的会话列表，所以用应用本来就有的 `CHATSERVANT_FIXTURE=<png>`——
它每圈重读同一张 PNG，于是「切走 / 切回」退化成**替换那个文件**，
进程不重启、`PaneWatcher` 不重建，走的是和真切换完全相同的路径。

素材是 `xtask probe frame` 抓的真实帧；「另一个会话」那张只改了标题栏一小块
（字形不同、亮度相同，墨迹 61 → 96，同一量级）。

| 二进制 | 会话 A | 切到 B | 切回 A |
|---|---|---|---|
| **摘掉 `rewind()`** | `messages=2` | `tick=21 messages=0` | **80 秒内、直到 `tick=101` 一条 readout 都没有** |
| **带修复** | `messages=2` | `tick=38 messages=0` | `tick=60 messages=2` ✅ |

对照组同时坐实了「消息回不来」和「不会自愈」。

### 要在真微信上人工点一次的话，跑法

1. `pnpm tauri dev`，微信停在一个**对方说过话**的会话上。
2. 等面板上消息条数稳定（记下 N）。
3. 在微信里切到**另一个**会话，面板应立刻变成「不认这个人，就不动手」，
   消息清空。
4. **切回原来那个会话。**
5. 期望：消息条数回到 **N**，不是 N-2。

### 顺手可以一起看的两件事

| 看什么 | 期望 |
|---|---|
| 面板上的「OCR 调用」计数 | 停在别的会话那段时间**不增长**（闸关着就不该识别） |
| 切回后的前两三秒 | 条数可能短暂偏少然后自己长回来——水位线只推进到**实际读到**的底边 |

### 🔧 抓到并修掉的假控件：面板拖不动

`ui/src/routes/+page.svelte` 的 `<header class="cs-head" data-tauri-drag-region>`
一直挂着，注释还写着「抓手就是这两个字」，`WinCtl.svelte` 也认真地用
`data-no-drag` 把按键排除在拖拽区之外——**做得很完整，但拖动根本没生效**。

实测：按表头空白处拖 220×120，`GetWindowRect` 位移 `dx=0 dy=0`。

根因不在前端，在 ACL：`ui/src-tauri/capabilities/default.json` 的
`permissions` 只有三条 `listen` / `unlisten` / `close`，
**没有 `core:window:allow-start-dragging`**。Tauri 2 对 `data-tauri-drag-region`
的处理是前端调 `plugin:window|start_dragging`，权限不在表里就**静默拒绝**。

这条值得单独立规矩：**ACL 缺一条权限，界面上只会表现为「控件点不动 / 拖不动」，
控制台不冒泡、任何静态检查都不报**。它和记忆里那条「`probe_key` 恒 `Ok(false)`」
是同一族——上一轮的欠账。

顺带把同一文件里已经失效的 `"settings"` 窗口标签删了（那个窗口 2026-10-10
就删了，设置搬进了面板；`settings` 现在只是托盘菜单的 id，不是窗口）。

修完实测：`dx=220 dy=120`，与拖动量逐像素一致。

### ⚠ 环境事实：Win11 溢出区不暴露可信的 UIA 坐标

托盘图标在 Win11 上默认进**溢出区**（`TopLevelWindowForOverflowXamlIsland`，
class 不是常见的 `Xaml_WindowedPopupClass`）。更麻烦的是它给图标报的
`BoundingRectangle` 不可信——同一时刻按钮 rect 是 `(2010,1251,166x32)`，
而 popup 自己 rect 是 `(2057,1278,234x114)`，**按钮整个跑到 popup 外面去了**。
按那个坐标右键，落点打在下面别人的窗口上，点了等于没点。

可靠做法是从 popup 矩形反推网格：溢出区图标 40px 步长、起点比 popup 左上角
各多 17px，于是首格中心 = `popup 左上 + (37,37)`，与逐项枚举的结果逐像素吻合。

还有一个更早的坑：**展开按钮是 toggle**。脚本里连点两次，第二次会把已经展开的
溢出区又关掉，于是「第二次跑什么都没查到」。先问一次再决定要不要点。

> 这三条都是「同一个量至少两个独立实现交叉验证」那条规矩的应用：
> 坐标是这么定位的，不是照着 UIA 报的值试出来的。

### ✅ 门禁：**已按惯例修绿**


### 🔴「关闭时 = 收进托盘」但面板没有 `−`：根因（2026-10-10 实测钉死）

症状：`close_behavior.txt` 实测就是 `tray`，托盘日志也是「托盘图标已就绪」，
但面板启动后只有 `更多` 和 `×`。

**根因：`tauri.conf.json` 里定义的窗口在 `.setup()` 之前就创建并开始加载。**
面板会在 `build_tray` 跑之前就发出它的第一个 IPC。原来的判断是
`app.tray_by_id(TRAY_ID).is_some()`，而它把**「托盘还没建好」和
「托盘建失败了」当成同一件事**，于是用户的设置被悄悄降级成 `Exit`。

前端探针实测（同一进程内）：

```
read_close_behavior: file="tray" tray_available=false   <- 面板问（托盘还没建）
get_close_behavior from window="main"     -> Exit
read_close_behavior: file="tray" tray_available=true    <- 228ms 后设置窗口问
get_close_behavior from window="settings" -> Tray
```

**修复**：`TRAY_STATE` 改三态（`Pending` / `Ready` / `Failed`），
由 `build_tray` 显式报结果。**只有明确 `Failed` 才降级**——
`Pending` 算可用，因为 `build_tray` 是 `.setup()` 的第一件事，它一定会跑完；
万一真失败，`read_close_behavior` 下次读时会降回 `Exit`。

修复后实测（release 二进制，非 dev）：**启动第一帧**就是
`更多 | 收进托盘 | 退出 | …`，点 `−` → 面板隐藏 → **进程存活** → 清理干净。
